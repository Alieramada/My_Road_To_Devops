# Урок 4.3.2.

## Введение <a href="#sec.4.3_02-in" id="sec.4.3_02-in"></a>

После изучения программ и их конфигурационных файлов в этом уроке мы узнаем, как команды выполняются в виде процессов. Кроме того, мы поговорим о системных сообщениях, использовании кольцевого буфера ядра(kernel ring buffer) и о том, как появление `systemd` и его демона журнала — `journald` — изменило подход к системным журналам.

## Процессы <a href="#processes" id="processes"></a>

Каждый раз, когда пользователь вводит команду, запускается программа и создаётся один или несколько процессов.

Процессы существуют в виде иерархии. После загрузки ядра в память при запуске инициируется первый процесс, который, в свою очередь, запускает другие процессы, которые, в свою очередь, могут запускать другие процессы. Каждый процесс имеет уникальный идентификатор (`PID`) и идентификатор родительского процесса (`PPID`). Это положительные целые числа, которые присваиваются в последовательном порядке.

`top` также может предоставить нам информацию о потреблении памяти и процессора всей системой, а также каждым процессом.

`top` позволяет пользователю осуществлять некоторое взаимодействие.

По умолчанию вывод сортируется по проценту времени процессора, используемого каждым процессом, в порядке убывания. Это поведение можно изменить, нажав следующие клавиши в `top`:

`M`

Сортировка по использованию памяти.

`N`

Сортировка по идентификационному номеру процесса.

`T`

Сортировка по времени выполнения.

`P`

Сортировка по проценту загрузки процессора.

Для переключения между порядком убывания / возрастания просто нажмите `R`.

## **Моментальный снимок процессов: `ps`**

Ещё одна очень полезная команда для получения информации о процессах — `ps`. В то время как `top` предоставляет динамическую информацию, `ps` предоставляет статическую информацию.

Если `ps` вызывается без параметров, вывод будет довольно кратким и будет относиться только к процессам, подключённым к текущей оболочке:

```bash
$ ps
 PID TTY ВРЕМЯ CMD
 2318 pts/0 00:00:00 bash
 2443 pts/0 00:00:00 ps
```

Отображаемая информация связана с идентификатором процесса (`PID`), терминалом, в котором выполняется процесс (`TTY`), временем, затраченным процессом на обработку (`TIME`), и командой, запустившей процесс (`CMD`).

Полезный переключатель для `ps` is `-f`, который показывает полноформатный список:

```bash
$ ps
 PID TTY TIME CMD
 2318 pts/0 00:00:00 bash
 2443 pts/0 00:00:00 ps
```

В сочетании с другими переключателями `-f` показывает взаимосвязь между родительским и дочерним процессами:

```bash
$ ps -uf
USER       PID %CPU %MEM    VSZ   RSS TTY      STAT START   TIME COMMAND
carol       2318  0.0  0.1  21336  5140 pts/1    Ss   08:38   0:00 bash
carol       2492  0.0  0.0  38304  3332 pts/1    R+   08:51   0:00  \_ ps -uf
carol       1780  0.0  0.1  21440  5412 pts/0    Ss   08:28   0:00 bash
carol       2291  0.0  0.7 305352 28736 pts/0    Sl+  08:35   0:00  \_ emacs index.en.adoc -nw
(...)
```

Аналогичным образом `ps` может показывать процент используемой памяти при вызове с помощью переключателя `-v`:

```bash
$ ps -v
  PID TTY      STAT   TIME  MAJFL   TRS   DRS   RSS %MEM COMMAND
 1163 tty2     Ssl+   0:00      1    67 201224 5576  0.1 /usr/lib/gdm3/gdm-x-session (...)
 (...)
```

{% hint style="info" %}
Ещё одна визуально привлекательная команда, которая показывает иерархию процессов, — `pstree`. Она поставляется со всеми основными дистрибутивами.
{% endhint %}

## Информация о процессах в каталоге /proc

Мы уже видели файловую систему`/proc` .`/proc` включает в себя пронумерованный подкаталог для каждого запущенного процесса в системе (номер — это `PID` процесса):

```sh
carol@debian:~# ls /proc
1 108 13 17 21 27 354 41 665 8 9
10 109 14 173 22 28 355 42 7 804 915
103 11 140 18 23 29 356 428 749 810 918
104 111 148 181 24 3 367 432 75 811
105 112 149 19 244 349 370 433 768 83
106 115 15 195 25 350 371 5 797 838
107 12 16 2 26 353 404 507 798 899
(...)
```

Таким образом, вся информация о конкретном процессе содержится в его каталоге. Давайте перечислим содержимое первого процесса — того, чей `PID` равен `1` (вывод был сокращён для удобства чтения):

```sh
# ls /proc/1/
attr cmdline environ io mem ns
autogroup comm exe limits mountinfo numa_maps
auxv coredump_filter fd loginuid mounts oom_adj
...
```

Вы можете проверить, например, исполняемый файл процесса:

```sh
# cat /proc/1/cmdline; echo
/sbin/init
```

Как видите, двоичный файл, запустивший иерархию процессов, был `/sbin/init`.

{% hint style="info" %}
Команды можно объединять с помощью точки с запятой (`;`). Смысл использования команды `echo` выше заключается в том, чтобы создать новую строку. Попробуйте выполнить просто cat /proc/1/cmdline и посмотрите на разницу.
{% endhint %}

## **Загрузка системы**

Каждый процесс в системе потенциально может потреблять системные ресурсы. Так называемая системная нагрузка пытается объединить общую нагрузку системы в один числовой показатель. Текущую нагрузку можно увидеть с помощью команды `uptime`:

```
$ uptime
 22:12:54 up 13 days, 20:26,  1 user,  load average: 2.91, 1.59, 0.39
```

Три последние цифры указывают на среднюю нагрузку системы за последнюю минуту (`2.91`), за последние пять минут (`1.59`) и за последние пятнадцать минут (`0.39`).

Каждое из этих чисел указывает на то, сколько процессов ожидало либо ресурсов процессора, либо завершения операций ввода-вывода. Это означает, что эти процессы были готовы к запуску, если бы получили соответствующие ресурсы.

## Ведение системного журнала и обмен системными сообщениями <a href="#system_logging_and_system_messaging" id="system_logging_and_system_messaging"></a>

Как только ядро и процессы начинают выполняться и взаимодействовать друг с другом, генерируется много информации. Большая её часть отправляется в файлы — так называемые файлы журналов или просто _логи_.

Без ведения журналов поиск события, произошедшего на сервере, доставлял бы системным администраторам немало головной боли, поэтому важно иметь стандартизированный и централизованный способ отслеживания любых системных событий. Кроме того, журналы играют важную роль в устранении неполадок и обеспечении безопасности, а также являются надёжными источниками данных для понимания системной статистики и прогнозирования тенденций.

## **Ведение журнала с помощью демона syslog**

Традиционно системные сообщения обрабатывались стандартным средством ведения журналов — syslog — или любым из его производных — syslog-ng или rsyslog. Демон ведения журналов собирает сообщения от других служб и программ и сохраняет их в файлах журналов, обычно в `/var/log`. Однако некоторые службы сами заботятся о своих журналах (например, веб-сервер Apache HTTPD). Аналогичным образом ядро Linux использует кольцевой буфер в памяти для хранения своих сообщений в журналах.

**Регистрируйте файлы в `/var/log`**

Поскольку журналы — это данные, которые меняются со временем, они обычно хранятся в `/var/log`.

Если вы изучите `/var/log`, то поймёте, что названия журналов в определённой степени говорят сами за себя. Вот несколько примеров:

`/var/log/auth.log`

В нем хранится информация об аутентификации.

`/var/log/kern.log`

В нем хранится информация о ядре.

`/var/log/syslog`

В нем хранится системная информация.

`/var/log/messages`

В нем хранятся системные данные и данные приложения.

{% hint style="info" %}
Точное название и содержимое файлов журналов может различаться в разных дистрибутивах Linux.
{% endhint %}

## Logrotate

Файлы журналов могут сильно разрастаться в течение нескольких недель или месяцев и занимать всё свободное место на диске. Для решения этой проблемы используется утилита `logrotate`. Она реализует ротацию или циклическую обработку журналов, что подразумевает такие действия, как перемещение файлов журналов под новое имя, архивирование и/или сжатие, иногда отправка их по электронной почте системному администратору и, в конечном итоге, удаление по мере устаревания. Соглашения, используемые для именования этих перемещаемых файлов журналов, разнообразны (например, добавление суффикса с датой); однако обычно просто добавляется суффикс с целым числом:

```sh
# ls /var/log/apache2/
access.log error.log error.log.1 error.log.2.gz other_vhosts_access.log
```

Обратите внимание, что `error.log.2.gz` уже был сжат с помощью gzip (отсюда суффикс `.gz`).

## **Кольцевой буфер ядра**

Буфер кольцевого буфера ядра — это структура данных фиксированного размера, которая записывает сообщения о загрузке ядра, а также любые текущие сообщения ядра. Функция этого буфера — очень важная — заключается в регистрации всех сообщений ядра, генерируемых при загрузке, когда `syslog` ещё не доступна. Команда `dmesg` выводит буфер кольцевого буфера ядра (который раньше также сохранялся в `/var/log/dmesg`). Из-за расширения кольцевого буфера эта команда обычно используется в сочетании с утилитой фильтрации текста `grep` или пейджером, таким как `less`. Например, для поиска сообщений о загрузке:

```sh
$ dmesg | grep boot
[    0.000000] Command line: BOOT_IMAGE=/boot/vmlinuz-4.9.0-9-amd64 root=UUID=5216e1e4-ae0e-441f-b8f5-8061c0034c74 ro quiet
[    0.000000] smpboot: Allowing 1 CPUs, 0 hotplug CPUs
[    0.000000] Kernel command line: BOOT_IMAGE=/boot/vmlinuz-4.9.0-9-amd64 root=UUID=5216e1e4-ae0e-441f-b8f5-8061c0034c74 ro quiet
[    0.144986] AppArmor: AppArmor disabled by boot time parameter
(...)
```

{% hint style="info" %}
По мере того как буфер кольцевого буфера ядра со временем заполняется новыми сообщениями, самые старые сообщения будут исчезать.
{% endhint %}

## **Системный журнал: systemd-journald**

В 2015 году systemd заменила SysV Init в качестве _фактического_ системного и сервисного менеджера в большинстве основных дистрибутивов Linux. Как следствие, демон журнала — journald — стал стандартным компонентом ведения журналов, заменив syslog в большинстве аспектов. Данные больше не хранятся в виде обычного текста, а в двоичной форме. Таким образом, для чтения журналов необходима утилита `journalctl` . Кроме того, journald совместим с syslog и может быть интегрирован с ним.

`journalctl` Это утилита, которая используется для чтения и запроса базы данных журнала systemd. При вызове без параметров она выводит весь журнал:

```sh
# journalctl
-- Logs begin at Tue 2019-06-04 17:49:40 CEST, end at Tue 2019-06-04 18:13:10 CEST. --
jun 04 17:49:40 debian systemd-journald[339]: Runtime journal (/run/log/journal/) is 8.0M, max 159.6M, 151.6M free.
jun 04 17:49:40 debian kernel: microcode: microcode updated early to revision 0xcc, date = 2019-04-01
Jun 04 17:49:40 debian kernel: Linux version 4.9.0-8-amd64 (debian-kernel@lists.debian.org) (gcc version 6.3.0 20170516 (Debian 6.3.0-18+deb9u1) )
Jun 04 17:49:40 debian kernel: Command line: BOOT_IMAGE=/boot/vmlinuz-4.9.0-8-amd64 root=/dev/sda1 ro quiet
(...)
```

Однако при вызове с переключателями `-k` или `--dmesg` это будет эквивалентно использованию команды `dmesg`:

```sh
# journalctl -k
[    0.000000] Linux version 4.9.0-9-amd64 (debian-kernel@lists.debian.org) (gcc version 6.3.0 20170516 (Debian 6.3.0-18+deb9u1) ) #1 SMP Debian 4.9.168-1+deb9u2 (2019-05-13)
[    0.000000] Command line: BOOT_IMAGE=/boot/vmlinuz-4.9.0-9-amd64 root=UUID=5216e1e4-ae0e-441f-b8f5-8061c0034c74 ro quiet
(...)
```

Другие интересные варианты для `journalctl` включают:

`-b`, `--boot`

Здесь отображается информация о загрузке.

`-u`

Он показывает сообщения об указанном модуле. Грубо говоря, модуль можно определить как любой ресурс, обрабатываемый systemd. Например, `journalctl -u apache2.service` используется для чтения сообщений о `apache2` веб-сервере.

`-f`

Он показывает самые последние сообщения в журнале и продолжает печатать новые записи по мере их добавления в журнал — почти как `tail -f`.\

## Краткие сведения <a href="#sec.4.3_02-su" id="sec.4.3_02-su"></a>

В контексте хранения данных в этом уроке были рассмотрены следующие темы: управление процессами, системные журналы и обмен сообщениями.

Что касается управления процессами, то мы узнали следующее:

* Программы генерируют процессы, а процессы существуют в иерархии.
* У каждого процесса есть уникальный идентификатор (`PID`) и идентификатор родительского процесса (`PPID`).
* `top` Это очень полезная команда для динамического и интерактивного изучения запущенных процессов в системе.
* `ps` можно использовать для получения снимка текущих запущенных процессов в системе.
* Каталог `/proc` содержит каталоги для каждого запущенного в системе процесса, названные в соответствии с их идентификаторами PID.
* Концепция средней нагрузки на систему — очень полезная функция для проверки использования/перегрузки процессора.

Что касается ведения системного журнала, мы должны помнить, что:

* Журнал — это файл, в котором записываются системные события. Журналы незаменимы при устранении неполадок.
* Традиционно логирование осуществляется с помощью специальных служб, таких как syslog, syslog-ng или rsyslog. Тем не менее, некоторые программы используют собственные демоны логирования.
* Поскольку журналы — это переменные данные, они хранятся в `/var` и — иногда — их названия могут дать вам представление об их содержимом (`kern.log`, `auth.log` и т. д.)
* Большинство журналов записываются в виде обычного текста и могут быть прочитаны в любом текстовом редакторе, если у вас есть соответствующие разрешения. Однако некоторые из них являются двоичными и должны быть прочитаны с помощью специальных команд.
* Чтобы избежать проблем с дисковым пространством, _ротация журналов_ выполняется с помощью утилиты logrotate.
* Что касается ядра, то оно использует циклическую структуру данных — кольцевой буфер, — в котором хранятся сообщения о загрузке (старые сообщения со временем удаляются).
* Система и менеджер служб systemd заменили System V init практически во всех дистрибутивах, а journald стал стандартной службой ведения журналов.
* Для чтения журнала systemd необходима `journalctl` утилита.
