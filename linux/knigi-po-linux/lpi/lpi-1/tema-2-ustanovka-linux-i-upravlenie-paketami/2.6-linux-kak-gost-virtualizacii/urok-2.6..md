# Урок 2.6.

## Введение <a href="#sec.102.6_01-in" id="sec.102.6_01-in"></a>

Одной из сильных сторон Linux является его универсальность. Одним из аспектов этой универсальности является возможность использовать Linux в качестве средства для размещения других операционных систем или отдельных приложений в полностью изолированной и безопасной среде. В этом уроке мы рассмотрим концепции виртуализации и контейнерных технологий, а также некоторые технические детали, которые следует учитывать при развёртывании виртуальной машины на облачной платформе.

## Обзор виртуализации <a href="#virtualization_overview" id="virtualization_overview"></a>

Виртуализация — это технология, которая позволяет программной платформе, называемой _гипервизором_, запускать процессы, содержащие полностью эмулированную компьютерную систему. Гипервизор отвечает за управление ресурсами физического оборудования, которые могут использоваться отдельными виртуальными машинами. Эти виртуальные машины называются гостевыми. Виртуальная машина эмулирует многие аспекты физического компьютера, такие как BIOS системы и контроллеры жёстких дисков. Виртуальная машина часто использует образы жёстких дисков, которые хранятся в виде отдельных файлов, и имеет доступ к оперативной памяти и процессору хост-машины через программное обеспечение гипервизора. Гипервизор разделяет доступ к аппаратным ресурсам хост-системы между гостевыми системами, что позволяет запускать несколько операционных систем на одной хост-системе.

Обычно используемые гипервизоры для Linux включают:

Xen

Xen — это гипервизор первого типа с открытым исходным кодом, то есть он не зависит от базовой операционной системы. Гипервизор такого типа называется _гипервизором без операционной системы_, поскольку компьютер может загружаться непосредственно в гипервизор.

KVM

Виртуальная машина ядра — это модуль ядра Linux для виртуализации. KVM — это гипервизор как первого, так и второго типа, потому что, хотя для его работы требуется обычная операционная система Linux, он может отлично работать как гипервизор, интегрируясь с работающей установкой Linux. Виртуальные машины, развёрнутые с помощью KVM, используют `libvirt` демон и связанные с ним программные утилиты для создания и управления.

VirtualBox

Популярное настольное приложение, которое упрощает создание виртуальных машин и управление ими. Oracle VM VirtualBox является кроссплатформенным приложением и работает на Linux, macOS и Microsoft Windows. Поскольку для работы VirtualBox требуется базовая операционная система, это гипервизор второго типа.

Некоторые гипервизоры позволяют динамически перемещать виртуальную машину. Процесс перемещения виртуальной машины с одного гипервизора на другой называется _миграцией_, и используемые при этом методы различаются в зависимости от реализации гипервизора. Некоторые миграции можно выполнять только после полного выключения гостевой системы, а другие — во время работы гостевой системы (так называемая _миграция в реальном времени_). Такие методы могут быть полезны во время обслуживания гипервизоров или для обеспечения отказоустойчивости системы, когда гипервизор перестаёт работать и гостевую систему можно перенести на работающий гипервизор.

## Типы виртуальных машин <a href="#types_of_virtual_machines" id="types_of_virtual_machines"></a>

Существует три основных типа виртуальных машин: _полностью виртуализированная_ гостевая, _паравиртуализированная_ гостевая и _гибридная_ гостевая.

Полностью виртуализированная

Все инструкции, которые должна выполнять гостевая операционная система, должны быть способны работать в полностью виртуализированной операционной системе. Это связано с тем, что в гостевой системе не устанавливаются дополнительные программные драйверы для преобразования инструкций в имитацию или реальное оборудование. Полностью виртуализированная гостевая система — это система, в которой гостевая система (или аппаратная виртуальная машина) не знает, что она является запущенным экземпляром виртуальной машины. Чтобы этот тип виртуализации работал на оборудовании на базе x86, в системе, где установлен гипервизор, необходимо включить расширения Intel VT-x или AMD-V. Это можно сделать в меню конфигурации BIOS или UEFI.

Паравиртуализированая&#x20;

Паравиртуализированая гостевая (или PVM) — это гостевая ос, операционная система которой знает, что она работает на виртуальной машине. Такие гостевые ос используют модифицированное ядро и специальные драйверы (известные как _гостевые драйверы_), которые помогают гостевой операционной системе использовать программные и аппаратные ресурсы гипервизора. Производительность паравиртуализированой гостевой ос часто выше, чем у полностью виртуализированной, благодаря преимуществам, которые обеспечивают эти программные драйверы.

Гибрид

Паравиртуализация и полная виртуализация могут быть объединены, чтобы позволить немодифицированным операционным системам работать практически с такой же производительностью ввода-вывода, как у полностью виртуализированных операционных систем, за счёт использования паравиртуализированных драйверов в полностью виртуализированных операционных системах. Паравиртуализированные драйверы содержат драйверы устройств хранения данных и сетевых устройств с повышенной производительностью дискового и сетевого ввода-вывода.

Платформы виртуализации часто предоставляют готовые драйверы для виртуализированных операционных систем. KVM использует драйверы из проекта _Virtio_, а Oracle VM VirtualBox использует _Guest Extensions_, доступные в загружаемом файле образа ISO.

## **Пример `libvirt` виртуальной машины**

Мы рассмотрим пример виртуальной машины, которая управляется `libvirt` и использует гипервизор KVM. Виртуальная машина часто состоит из группы файлов, в первую очередь из XML-файла, который _определяет_ виртуальную машину (например, её аппаратную конфигурацию, подключение к сети, возможности отображения и т. д.), и связанного с ним файла образа жёсткого диска, который содержит установку операционной системы и её программного обеспечения.

Для начала давайте рассмотрим пример XML-файла конфигурации виртуальной машины и её сетевой среды:

```bash
$ ls /etc/libvirt/qemu
total 24
drwxr-xr-x 3 root root 4096 Oct 29 17:48 networks
-rw------- 1 root root 5667 Jun 29 17:17 rhel8.0.xml
```

{% hint style="info" %}
Часть `qemu` в пути к каталогу относится к базовому программному обеспечению, на которое опираются виртуальные машины на базе KVM. Проект QEMU предоставляет гипервизору программное обеспечение для эмуляции аппаратных устройств, которые будет использовать виртуальная машина, таких как контроллеры дисков, доступ к процессору хоста, эмуляция сетевой карты и многое другое.
{% endhint %}

Обратите внимание, что есть каталог с именем `networks`. Этот каталог содержит файлы определений (также в формате XML), которые создают сетевые конфигурации, которые могут использовать виртуальные машины. Этот гипервизор использует только одну сеть, поэтому есть только один файл определения, содержащий конфигурацию для сегмента виртуальной сети, который будут использовать эти системы.

```bash
$ ls -l /etc/libvirt/qemu/networks/
total 8
drwxr-xr-x 2 root root 4096 Jun 29 17:15 autostart
-rw------- 1 root root  576 Jun 28 16:39 default.xml
$ sudo cat /etc/libvirt/qemu/networks/default.xml
<!--
WARNING: THIS IS AN AUTO-GENERATED FILE. CHANGES TO IT ARE LIKELY TO BE
OVERWRITTEN AND LOST. Changes to this xml configuration should be made using:
  virsh net-edit default
or other application using the libvirt API.
-->

<network>
  <name>default</name>
  <uuid>55ab064f-62f8-49d3-8d25-8ef36a524344</uuid>
  <forward mode='nat'/>
  <bridge name='virbr0' stp='on' delay='0'/>
  <mac address='52:54:00:b8:e0:15'/>
  <ip address='192.168.122.1' netmask='255.255.255.0'>
    <dhcp>
      <range start='192.168.122.2' end='192.168.122.254'/>
    </dhcp>
  </ip>
</network>
```

Это определение включает в себя частную сеть класса C и эмулируемое аппаратное устройство, которое выступает в качестве маршрутизатора для этой сети. Кроме того, гипервизор может использовать диапазон IP-адресов с реализацией DHCP-сервера, которые могут быть назначены виртуальным машинам, использующим эту сеть. В этой конфигурации сети также используется _преобразование сетевых адресов_ (NAT) для пересылки пакетов в другие сети, например в локальную сеть гипервизора.

## **Пример дискового хранилища виртуальной машины**

Образ жёсткого диска этой виртуальной машины находится по адресу `/var/lib/libvirt/images/rhel8`. Вот сам образ диска на этом гипервизоре:

```bash
$ sudo ls -lh /var/lib/libvirt/images/rhel8
-rw------- 1 root root 5.5G Oct 25 15:57 /var/lib/libvirt/images/rhel8
```

Текущий размер этого образа диска занимает всего 5,5 ГБ на гипервизоре. Однако операционная система в гостевой системе видит диск размером 23,3 ГБ, о чём свидетельствует вывод следующей команды из работающей виртуальной машины:

```bash
$ lsblk
NAME          MAJ:MIN RM  SIZE RO TYPE MOUNTPOINT
vda           252:0    0 23.3G  0 disk
├─vda1        252:1    0    1G  0 part /boot
└─vda2        252:2    0 22.3G  0 part
  ├─rhel-root 253:0    0   20G  0 lvm  /
  └─rhel-swap 253:1    0  2.3G  0 lvm  [SWAP]
```

Это связано с типом подготовки диска, используемого для этой гостевой системы. Существует несколько типов образов дисков, которые может использовать виртуальная машина, но два основных типа:

COW

Копирование при записи (также называемое _тонким резервированием_ или _разреженными образами_) — это метод, при котором файл диска создаётся с заранее заданным предельным размером. Размер образа диска увеличивается только по мере записи на него новых данных. Как и в предыдущем примере, гостевая операционная система видит заранее заданный предел в 23,3 ГБ, но записала в файл диска только 5,5 ГБ данных. Формат образа диска, используемый для примера виртуальной машины, — `qcow2` — это формат файлов QEMU COW.

RAW

_Необработанный_ или _полный_ тип диска — это файл, в котором заранее выделено всё пространство. Например, необработанный файл образа диска размером 10 ГБ занимает 10 ГБ фактического дискового пространства на гипервизоре. Этот тип диска обеспечивает более высокую производительность, так как всё необходимое дисковое пространство уже существует, поэтому базовый гипервизор может просто записывать данные на диск без снижения производительности, связанного с мониторингом образа диска, чтобы убедиться, что он ещё не достиг своего предела, и расширением размера файла по мере записи в него новых данных.

Существуют и другие платформы для управления виртуализацией, такие как _Red Hat Enterprise Virtualization_ и _oVirt_, которые могут использовать физические диски в качестве резервных хранилищ для операционной системы виртуальной машины. Эти системы могут использовать сеть хранения данных (SAN) или сетевые хранилища (NAS) для записи данных, а гипервизор отслеживает, какие хранилища принадлежат каким виртуальным машинам. Эти системы хранения данных могут использовать такие технологии, как управление логическими томами (LVM), для увеличения или уменьшения размера дискового хранилища виртуальной машины по мере необходимости, а также для создания моментальных снимков хранилища и управления ими.

## Работа с шаблонами виртуальных машин <a href="#working_with_virtual_machine_templates" id="working_with_virtual_machine_templates"></a>

Поскольку виртуальные машины, как правило, представляют собой просто файлы, работающие на гипервизоре, их легко создавать в виде _шаблонов_, которые можно настраивать для конкретных сценариев развёртывания. Часто виртуальная машина имеет базовую установку операционной системы и некоторые предварительно настроенные параметры аутентификации, которые упрощают запуск системы в будущем. Это сокращает время, необходимое для создания новой системы, за счёт уменьшения объёма часто повторяющейся работы, такой как установка базовых пакетов и настройка локали.

Этот шаблон виртуальной машины впоследствии можно будет скопировать в новую гостевую систему. В этом случае новая гостевая система будет переименована, для её сетевого интерфейса будет сгенерирован новый MAC-адрес, а также могут быть внесены другие изменения в зависимости от предполагаемого использования.

## **Идентификатор машины D-Bus**

Во многих установках Linux используется идентификационный номер машины, генерируемый во время установки и называемый _идентификатором машины D-Bus_. Однако если виртуальная машина _клонируется_ для использования в качестве шаблона для других виртуальных машин, необходимо создать новый идентификатор машины D-Bus, чтобы системные ресурсы гипервизора направлялись в соответствующую гостевую систему.

Следующую команду можно использовать для проверки наличия идентификатора D-Bus для работающей системы:

```bash
$ dbus-uuidgen --ensure
```

Если не отображается никаких сообщений об ошибках, значит, для системы существует идентификатор. Чтобы просмотреть текущий идентификатор устройства D-Bus, выполните следующие действия:

```bash
$ dbus-uuidgen --get
17f2e0698e844e31b12ccd3f9aa4d94a
```

Отображаемая строка текста — это текущий номер идентификатора. Никакие две системы Linux, работающие на гипервизоре, не должны иметь одинаковый идентификатор D-Bus.

Идентификатор устройства D-Bus находится по адресу `/var/lib/dbus/machine-id` и символически связан с `/etc/machine-id`. Не рекомендуется изменять этот идентификатор в работающей системе, так как это может привести к нестабильности и сбоям системы. Если у двух виртуальных машин один и тот же идентификатор устройства D-Bus, выполните описанную ниже процедуру, чтобы создать новый:

```bash
$ sudo rm -f /etc/machine-id
$ sudo dbus-uuidgen --ensure=/etc/machine-id
```

Если `/var/lib/dbus/machine-id` не является символической ссылкой на `/etc/machine-id`, то `/var/lib/dbus/machine-id` необходимо удалить.

## Развертывание виртуальных машин в облаке <a href="#deploying_virtual_machines_to_the_cloud" id="deploying_virtual_machines_to_the_cloud"></a>

Существует множество поставщиков IaaS (_инфраструктуры как услуги_), которые используют системы гипервизоров и могут развертывать виртуальные гостевые образы для организаций. Практически у всех этих поставщиков есть инструменты, которые позволяют администратору создавать, развертывать и настраивать собственные виртуальные машины на основе различных дистрибутивов Linux. У многих из этих компаний также есть системы, которые позволяют развертывать и переносить виртуальные машины, созданные в организации клиента.

При оценке развёртывания системы Linux в среде IaaS администратор должен учитывать несколько ключевых элементов:

Вычислительные инстансы

Многие поставщики облачных услуг взимают плату за использование в зависимости от «количества вычислительных ресурсов» или от того, сколько процессорного времени будет использовать ваша облачная инфраструктура. Тщательное планирование того, сколько времени обработки данных потребуется приложениям, поможет контролировать расходы на облачное решение.

Под вычислительными инстансами также часто понимается количество виртуальных машин, подготовленных в облачной среде. Опять же, чем больше инстансов систем работает одновременно, тем больше будет общая стоимость процессорного времени для организации.

Блочное хранилище

У поставщиков облачных услуг также есть различные уровни блочных хранилищ, доступных для использования организациями. Некоторые предложения предназначены просто для хранения файлов в сети, а другие относятся к внешнему хранилищу для виртуальной машины, предоставляемой облаком, для размещения файлов.

Стоимость таких предложений зависит от объёма используемого хранилища и скорости хранения данных в центрах обработки данных поставщика. Более быстрый доступ к хранилищу обычно стоит дороже, и наоборот, хранение данных «в состоянии покоя» (например, в архивном хранилище) часто обходится очень дёшево.

Создание сетей

Одним из основных компонентов работы с поставщиком облачных решений является настройка виртуальной сети. У многих поставщиков IaaS есть веб-утилиты, которые можно использовать для проектирования и реализации различных сетевых маршрутов, подсетей и конфигураций брандмауэра. Некоторые даже предоставляют DNS-решения, чтобы общедоступные FQDN (_полные доменные имена_) можно было назначать вашим системам, подключенным к интернету. Существуют даже «гибридные» решения, которые позволяют подключить существующую локальную сетевую инфраструктуру к облачной инфраструктуре с помощью VPN (_виртуальной частной сети_), тем самым объединяя две инфраструктуры.

## **Безопасный доступ к гостевым ос в облаке**

Наиболее распространённым способом доступа к удалённому виртуальному гостю на облачной платформе является использование программного обеспечения OpenSSH. В системе Linux, работающей в облаке, будет запущен сервер OpenSSH, а администратор будет использовать клиент OpenSSH с предварительно настроенными ключами для удалённого доступа.

Администратор должен выполнить следующую команду

```bash
$ ssh-keygen
```

и следуйте инструкциям по созданию пары открытого и закрытого SSH-ключей. Закрытый ключ остаётся в локальной системе администратора (хранится в `~/.ssh/`), а открытый ключ копируется в удалённую облачную систему. Это тот же метод, который используется при работе с сетевыми компьютерами в корпоративной локальной сети.

Затем администратор должен выполнить следующую команду:

```bash
$ ssh-copy-id -i <public_key> пользователь@cloud_server
```

Это позволит скопировать открытый ключ SSH из только что созданной пары ключей на удалённый облачный сервер. Открытый ключ будет записан в файл `~/.ssh/authorized_keys` на облачном сервере, и для него будут установлены соответствующие разрешения.

{% hint style="info" %}
Если в каталоге `~/.ssh/` есть только один файл открытого ключа, то переключатель `-i` можно не использовать, так как команда `ssh-copy-id` по умолчанию будет использовать файл открытого ключа в каталоге (обычно это файл с расширением `.pub`).
{% endhint %}

Некоторые поставщики облачных услуг автоматически генерируют пару ключей при создании новой системы Linux. Затем администратору необходимо будет загрузить закрытый ключ для новой системы от поставщика облачных услуг и сохранить его в своей локальной системе. Обратите внимание, что разрешения для ключей SSH должны быть `0600` для закрытого ключа и `0644` для открытого ключа.

## **Предварительная настройка облачных систем**

Полезным инструментом, упрощающим развёртывание виртуальных машин в облаке, является утилита `cloud-init` . Эта команда вместе с соответствующими файлами конфигурации и заранее подготовленным образом виртуальной машины представляет собой нейтральный по отношению к поставщику метод развёртывания гостевой ОС Linux на множестве поставщиков IaaS. Используя текстовые файлы YAML (_YAML — это не язык разметки_), администратор может предварительно настроить параметры сети, выбор программных пакетов, конфигурацию SSH-ключей, создание учётных записей пользователей, настройки локали и множество других параметров для быстрого создания новых систем.

При первой загрузке новой системы `cloud-init` считывает настройки из файлов конфигурации YAML и применяет их. Этот процесс необходимо применять только при первоначальной настройке системы, что упрощает развертывание парка новых систем на платформе поставщика облачных услуг.

Синтаксис файла YAML, используемый с `cloud-init` называется _cloud-config_. Вот пример файла `cloud-config`:

```bash
#cloud-config
timezone: Africa/Dar_es_Salaam
hostname: test-system

# Update the system when it first boots up
apt_update: true
apt_upgrade: true

# Install the Nginx web server
packages:
 - nginx
```

Обратите внимание, что в верхней строке нет пробела между символом решётки (`#`) и термином `cloud-config`.

{% hint style="info" %}
`cloud-init` Это касается не только виртуальных машин. Набор инструментов `cloud-init` также можно использовать для предварительной настройки контейнеров (например, контейнеров LXD Linux) перед развёртыванием.
{% endhint %}

## Контейнеры <a href="#containers" id="containers"></a>

В некоторых аспектах контейнерная технология похожа на виртуальную машину, в которой вы получаете изолированную среду для простого развёртывания приложения. В то время как при использовании виртуальной машины эмулируется весь компьютер, в контейнере используется ровно столько программного обеспечения, сколько необходимо для запуска приложения. Таким образом, накладные расходы гораздо меньше.

Контейнеры обеспечивают большую гибкость по сравнению с виртуальными машинами. Контейнер приложения можно перенести с одного хоста на другой так же, как виртуальную машину можно перенести с одного гипервизора на другой. Однако иногда виртуальную машину нужно выключить перед переносом, в то время как контейнер приложения всегда работает во время переноса. Контейнеры также упрощают развёртывание новых версий приложений параллельно с существующей версией. Когда пользователи завершают работу с запущенными контейнерами, эти контейнеры могут автоматически удаляться из системы с помощью программного обеспечения для управления контейнерами и заменяться новой версией, что сокращает время простоя.

{% hint style="info" %}
Для Linux доступно множество контейнерных технологий, таких как _Docker_, _Kubernetes_, _LXD/LXC_, _systemd-nspawn_, _OpenShift_ и другие. Точная реализация программного пакета для контейнеров выходит за рамки экзамена LPIC-1.
{% endhint %}

Контейнеры используют механизм _групп управления_ (более известный как _cgroups_) в ядре Linux. Cgroup — это способ разделения системных ресурсов, таких как память, процессорное время, а также пропускная способность диска и сети, для отдельного приложения. Администратор может напрямую использовать cgroups для установки ограничений системных ресурсов для приложения или группы приложений, которые могут существовать в рамках одной cgroup. По сути, это то, что программное обеспечение для контейнеров делает для администратора, а также предоставляет инструменты, упрощающие управление и развёртывание cgroups.

## Упражнения с руководством <a href="#sec.102.6_01-ge" id="sec.102.6_01-ge"></a>

1. Какие расширения процессора необходимы для аппаратной платформы на базе x86, которая будет запускать полностью виртуализированных гостей?
2. Для критически важной серверной установки, требующей максимальной производительности, скорее всего, будет использоваться какой тип виртуализации?
3. Две виртуальные машины, клонированные из одного и того же шаблона и использующие D-Bus, работают нестабильно. У них обоих разные имена хостов и настройки конфигурации сети. С помощью какой команды можно определить, есть ли у каждой из виртуальных машин разные идентификаторы D-Bus?

### Исследовательские упражнения <a href="#sec.102.6_01-ee" id="sec.102.6_01-ee"></a>

1.  Выполните следующую команду, чтобы узнать, включены ли в вашей системе расширения процессора для запуска виртуальной машины (результаты могут отличаться в зависимости от вашего процессора):

    `grep --color -E "vmx|svm" /proc/cpuinfo`

    В зависимости от результата вы можете увидеть `vmx` (для процессоров Intel с поддержкой VT-x) или `svm` (для процессоров AMD с поддержкой SVM). Если вы не получили результатов, обратитесь к инструкциям по включению виртуализации для вашего процессора в BIOS или UEFI.
2. Если ваш процессор поддерживает виртуализацию, обратитесь к документации вашего дистрибутива для запуска гипервизора KVM.
   * Установите необходимые пакеты для запуска гипервизора KVM.
   * Если вы используете графическую среду рабочего стола, рекомендуется также установить приложение `virt-manager` — графический интерфейс, который можно использовать при установке KVM. Это упростит установку виртуальных машин и управление ими.
   * Скачайте ISO-образ дистрибутива Linux по вашему выбору и, следуя документации вашего дистрибутива, создайте новую виртуальную машину с помощью этого ISO-образа.

## Краткие сведения <a href="#sec.102.6_01-su" id="sec.102.6_01-su"></a>

В этом уроке мы рассмотрели концептуальные основы виртуальных машин и контейнеров, а также то, как эти технологии можно использовать в Linux.

Мы кратко описали следующие команды:

`dbus-uuidgen`

Используется для проверки и просмотра системного идентификатора DBus ID.

`ssh-keygen`

Используется для создания пары открытого и закрытого ключей SSH для доступа к удалённым облачным системам.

`ssh-copy-id`

Используется для копирования открытого SSH-ключа системы в удалённую систему для упрощения удалённой аутентификации.

`cloud-init`

Используется для настройки и развёртывания виртуальных машин и контейнеров в облачной среде.

       ```bash
       $ sudo apt install virt-manager
       ```
   *   Скачайте ISO-образ дистрибутива Linux по вашему выбору и, следуя документации вашего дистрибутива, создайте новую виртуальную машину с помощью этого ISO-образа.

       С этой задачей легко справится пакет `virt-manager` . Однако виртуальную машину можно создать из командной строки с помощью команды `virt-install` . Попробуйте оба способа, чтобы понять, как развёртываются виртуальные машины.
