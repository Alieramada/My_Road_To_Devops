# Урок 2.3.

### Введение <a href="#sec.102.3_01-in" id="sec.102.3_01-in"></a>

В этом уроке мы обсудим _общие библиотеки_, также известные как _общие объекты_: фрагменты скомпилированного кода многократного использования, такие как функции или классы, которые регулярно используются различными программами.

Для начала мы объясним, что такое общие библиотеки, как их идентифицировать и где они находятся. Затем мы расскажем, как настроить их расположение. Наконец, мы покажем, как искать общие библиотеки, от которых зависит конкретная программа.

## Концепция разделяемых библиотек <a href="#concept_of_shared_libraries" id="concept_of_shared_libraries"></a>

Как и их физические аналоги, программные библиотеки — это наборы кода, предназначенные для использования множеством различных программ, подобно тому, как в физических библиотеках хранятся книги и другие ресурсы, которыми могут пользоваться разные люди.

Чтобы создать исполняемый файл из исходного кода программы, необходимо выполнить два важных шага. Во-первых, _компилятор_ преобразует исходный код в машинный код, который хранится в так называемых _объектных файлах_. Во-вторых, _компоновщик_ объединяет объектные файлы и _связывает_ их с библиотеками, чтобы создать конечный исполняемый файл. Эта связь может быть _статической_ или _динамической_. В зависимости от выбранного метода мы будем говорить о статических библиотеках или, в случае динамической связи, о разделяемых библиотеках. Давайте объясним их различия.

_**Статические библиотеки**_

Статическая библиотека объединяется с программой во время компоновки. Копия кода библиотеки встраивается в программу и становится её частью. Таким образом, программа не зависит от библиотеки во время выполнения, поскольку она уже содержит код библиотеки. Отсутствие зависимостей можно считать преимуществом, поскольку вам не нужно беспокоиться о том, что используемые библиотеки всегда доступны. С другой стороны, статически связанные программы тяжелее.

_**Общие (или динамические) библиотеки**_

В случае с общими библиотеками компоновщик просто следит за тем, чтобы программа правильно ссылалась на библиотеки. Однако компоновщик не копирует код библиотеки в файл программы. Однако во время выполнения программы общая библиотека должна быть доступна для удовлетворения зависимостей программы. Это экономичный подход к управлению системными ресурсами, поскольку он помогает уменьшить размер файлов программы и в память загружается только одна копия библиотеки, даже если она используется несколькими программами.

## Соглашения об именовании общих объектных файлов <a href="#shared_object_file_naming_conventions" id="shared_object_file_naming_conventions"></a>

Имя общей библиотеки, также известное как _soname_, состоит из трёх элементов:

* Название библиотеки (обычно с префиксом `lib`)
* `so` (что расшифровывается как “общий объект”)
* Номер версии библиотеки

Вот пример: `libpthread.so.0`

Напротив, имена статических библиотек заканчиваются на `.a`, например `libpthread.a`.

{% hint style="info" %}
Поскольку файлы, содержащие общие библиотеки, должны быть доступны во время выполнения программы, большинство систем Linux содержат общие библиотеки. Поскольку статические библиотеки требуются только в специальном файле при связывании программы, они могут отсутствовать в системе конечного пользователя.
{% endhint %}

`glibc` (Библиотека GNU C) — хороший пример общей библиотеки. В системе Debian GNU/Linux 9.9 её файл называется `libc.so.6`. Такие довольно общие имена файлов обычно являются символическими ссылками, которые указывают на фактический файл, содержащий библиотеку, имя которой содержит точный номер версии. В случае `glibc` эта символическая ссылка выглядит так:

```bash
$ ls -l /lib/x86_64-linux-gnu/libc.so.6
lrwxrwxrwx 1 root root 12 feb  6 22:17 /lib/x86_64-linux-gnu/libc.so.6 -> libc-2.24.so
```

Такая схема ссылок на файлы общей библиотеки, названные по конкретной версии, с помощью более общих имён файлов является распространённой практикой.

Другие примеры общих библиотек: `libreadline` (которая позволяет пользователям редактировать строки команд по мере их ввода и поддерживает режимы редактирования Emacs и vi), `libcrypt` (которая содержит функции, связанные с шифрованием, хешированием и кодированием) или `libcurl` (которая представляет собой многопротокольную библиотеку передачи файлов).

Распространенными местами размещения разделяемых библиотек в системе Linux являются:

* `/lib`
* `/lib32`
* `/lib64`
* `/usr/lib`
* `/usr/local/lib`

{% hint style="info" %}
Концепция общих библиотек характерна не только для Linux. В Windows, например, они называются DLL, что означает _динамически подключаемые библиотеки_.
{% endhint %}

## Настройка путей к общим библиотекам <a href="#configuration_of_shared_library_paths" id="configuration_of_shared_library_paths"></a>

Ссылки, содержащиеся в программах с динамической компоновкой, разрешаются динамическим компоновщиком (`ld.so` или `ld-linux.so`) при запуске программы. Динамический компоновщик ищет библиотеки в нескольких каталогах. Эти каталоги указываются в _пути к библиотеке_. Путь к библиотеке настраивается в каталоге `/etc`, а именно в файле `/etc/ld.so.conf` и, что более распространено в настоящее время, в файлах, находящихся в каталоге `/etc/ld.so.conf.d`. Обычно первый включает только одну `include` строку для `*.conf` файлов во втором:

```bash
$ cat /etc/ld.so.conf
include /etc/ld.so.conf.d/*.conf
```

/etc/ld.so.conf.d Каталог содержит \*.conf файлы:

```bash
$ ls /etc/ld.so.conf.d/
libc.conf x86_64-linux-gnu.conf
```

Эти `*.conf` файлы должны содержать абсолютные пути к каталогам общих библиотек:

```bash
$ cat /etc/ld.so.conf.d/x86_64-linux-gnu.conf
# Multiarch support
/lib/x86_64-linux-gnu
/usr/lib/x86_64-linux-gnu
```

Команда `ldconfig` отвечает за чтение этих файлов конфигурации, создание вышеупомянутого набора символических ссылок, которые помогают найти отдельные библиотеки, и, наконец, за обновление файла кэша `/etc/ld.so.cache`. Таким образом, `ldconfig` необходимо запускать каждый раз, когда добавляются или обновляются файлы конфигурации.

Полезными опциями для `ldconfig` являются:

`-v`, `--verbose`

Отобразите номера версий библиотеки, названия каждого каталога и созданные ссылки:

```bash
$ sudo ldconfig -v
/usr/local/lib:
/lib/x86_64-linux-gnu:
 libnss_myhostname.so.2 -> libnss_myhostname.so.2
 libfuse.so.2 -> libfuse.so.2.9.7
 libidn.so.11 -> libidn.so.11.6.16
 libnss_mdns4.so.2 -> libnss_mdns4.so.2
 libparted.so.2 -> libparted.so.2.0.1
 (...)
```

Таким образом, мы можем увидеть, например, как `libfuse.so.2` связан с фактическим файлом общего объекта `libfuse.so.2.9.7`.

`-p`, `--print-cache`

Распечатайте списки каталогов и библиотек-кандидатов, хранящихся в текущем кэше:

```bash
$ sudo ldconfig -p
1094 libs found in the cache `/etc/ld.so.cache'
    libzvbi.so.0 (libc6,x86-64) => /usr/lib/x86_64-linux-gnu/libzvbi.so.0
	libzvbi-chains.so.0 (libc6,x86-64) => /usr/lib/x86_64-linux-gnu/libzvbi-chains.so.0
	libzmq.so.5 (libc6,x86-64) => /usr/lib/x86_64-linux-gnu/libzmq.so.5
	libzeitgeist-2.0.so.0 (libc6,x86-64) => /usr/lib/x86_64-linux-gnu/libzeitgeist-2.0.so.0
	(...)
```

Обратите внимание, как кэш использует полное название ссылок:

```bash
$ sudo ldconfig -p |grep libfuse
 libfuse.so.2 (libc6,x86-64) => /lib/x86_64-linux-gnu/libfuse.so.2
```

Если мы пролистаем список `/lib/x86_64-linux-gnu/libfuse.so.2`, то найдём ссылку на фактический файл общего объекта `libfuse.so.2.9.7`, который хранится в том же каталоге:

```bash
$ ls -l /lib/x86_64-linux-gnu/libfuse.so.2
lrwxrwxrwx 1 root root 16 Aug 21  2018 /lib/x86_64-linux-gnu/libfuse.so.2 -> libfuse.so.2.9.7
```

{% hint style="info" %}
Поскольку для этого требуется доступ на запись в `/etc/ld.so.cache` (принадлежащий пользователю root), вы должны либо быть пользователем root, либо использовать `sudo` для вызова `ldconfig`. Дополнительную информацию о переключателях `ldconfig` можно найти в руководстве.
{% endhint %}

&#x20;В дополнение к файлам конфигурации, описанным выше, `LD_LIBRARY_PATH` переменная среды может использоваться для временного добавления новых путей к разделяемым библиотекам. Он состоит из набора каталогов, разделенных двоеточием (`:`), в которых осуществляется поиск библиотек. Чтобы добавить, например, `/usr/local/mylib` к пути к библиотеке в текущем сеансе командной строки, вы могли бы ввести:

```bash
$ LD_LIBRARY_PATH=/usr/local/mylib
```

Теперь вы можете проверить его значение:

```bash
$ echo $LD_LIBRARY_PATH
/usr/local/mylib
```

Чтобы добавить `/usr/local/mylib` в путь к библиотеке в текущем сеансе оболочки и экспортировать его во все дочерние процессы, запущенные из этой оболочки, введите:

```bash
$ export LD_LIBRARY_PATH=/usr/local/mylib
```

Чтобы удалить `LD_LIBRARY_PATH` переменную окружения, просто введите:

```bash
$ unset LD_LIBRARY_PATH
```

Чтобы сделать изменения постоянными, вы можете написать строку

```bash
export LD_LIBRARY_PATH=/usr/local/mylib
```

в одном из скриптов инициализации Bash, таком как `/etc/bash.bashrc` или `~/.bashrc`.

`LD_LIBRARY_PATH` для разделяемых библиотек это то же самое, что `PATH` для исполняемых файлов. Для получения дополнительной информации о переменных среды и конфигурации оболочки обратитесь к соответствующим урокам.

## Поиск зависимостей конкретного исполняемого файла <a href="#searching_for_the_dependencies_of_a_particular_executable" id="searching_for_the_dependencies_of_a_particular_executable"></a>

Чтобы найти общие библиотеки, необходимые для конкретной программы, используйте команду `ldd` с абсолютным путём к программе. В результате будет показан путь к файлу общей библиотеки, а также шестнадцатеричный адрес памяти, по которому она загружается:

```bash
$ ldd /usr/bin/git
 linux-vdso.so.1 => (0x00007ffcbb310000)
 libpcre.so.3 => /lib/x86_64-linux-gnu/libpcre.so.3 (0x00007f18241eb000)
 libz.so.1 => /lib/x86_64-linux-gnu/libz.so.1 (0x00007f1823fd1000)
 libresolv.so.2 => /lib/x86_64-linux-gnu/libresolv.so.2 (0x00007f1823db6000)
 libpthread.so.0 => /lib/x86_64-linux-gnu/libpthread.so.0 (0x00007f1823b99000)
 librt.so.1 => /lib/x86_64-linux-gnu/librt.so.1 (0x00007f1823991000)
 libc.so.6 => /lib/x86_64-linux-gnu/libc.so.6 (0x00007f18235c7000)
 /lib64/ld-linux-x86-64.so.2 (0x00007f182445b000)
```

Аналогично, мы используем `ldd` для поиска зависимостей совместно используемого объекта:

```bash
$ ldd /lib/x86_64-linux-gnu/libc.so.6
 /lib64/ld-linux-x86-64.so.2 (0x00007fbfed578000)
 linux-vdso.so.1 (0x00007fffb7bf5000)
```

С опцией `-u` (или `--unused`) `ldd` выводит неиспользуемые прямые зависимости (если они существуют):

```bash
$ ldd -u /usr/bin/git
Unused direct dependencies:
	/lib/x86_64-linux-gnu/libz.so.1
	/lib/x86_64-linux-gnu/libpthread.so.0
	/lib/x86_64-linux-gnu/librt.so.1
```

Причина использования неиспользуемых зависимостей связана с параметрами, используемыми компоновщиком при сборке двоичного файла. Несмотря на то, что программе не нужна неиспользуемая библиотека, она всё равно была связана с ней и помечена как `NEEDED` в информации об объектном файле. Вы можете изучить это с помощью таких команд, как `readelf` или `objdump`, которые вы вскоре будете использовать в исследовательском упражнении.

## Ответы на исследовательские упражнения <a href="#sec.102.3_01-aee" id="sec.102.3_01-aee"></a>

1. `objdump` Это утилита командной строки, которая отображает информацию из объектных файлов. Проверьте, установлена ли она в вашей системе с помощью `which objdump`. Если нет, пожалуйста, установите её.
   *   Используйте `objdump` с опцией `-p` (или `--private-headers`) и `grep` для вывода зависимостей `glibc`:

       `objdump -p /lib/x86_64-linux-gnu/libc.so.6 | grep SONAME`
   *   Используйте `objdump` с опцией `-p` (или `--private-headers`) и `grep` для вывода зависимостей Bash:

       `objdump -p /bin/bash | grep NEEDED`
