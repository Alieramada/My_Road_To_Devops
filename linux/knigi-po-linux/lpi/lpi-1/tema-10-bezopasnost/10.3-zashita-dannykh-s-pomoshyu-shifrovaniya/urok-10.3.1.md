# Урок 10.3.1

## Введение <a href="#sec.110.3_01-in" id="sec.110.3_01-in"></a>

Защита данных с помощью шифрования имеет первостепенное значение во многих аспектах современного системного администрирования — особенно когда речь идёт об удалённом доступе к системам. В отличие от небезопасных решений, таких как _telnet_, _rlogin_ или _FTP_, протокол _SSH_ (_Secure Shell_) был разработан с учётом требований безопасности. Используя криптографию с открытым ключом, он аутентифицирует как хосты, так и пользователей и шифрует весь последующий обмен информацией. Кроме того, SSH можно использовать для создания _туннелей через порты_, которые, помимо прочего, позволяют передавать данные по незашифрованному протоколу через зашифрованное соединение SSH. Текущая рекомендуемая версия протокола SSH — 2.0. _OpenSSH_ — это бесплатная реализация протокола SSH с открытым исходным кодом.

В этом уроке мы рассмотрим базовую конфигурацию клиента _OpenSSH_, а также роль ключей хоста _OpenSSH_ на сервере. Также мы обсудим концепцию туннелей SSH-портов. Мы будем использовать два компьютера со следующей конфигурацией:

## Базовая Конфигурация и использование клиента OpenSSH <a href="#basic_openssh_client_configuration_and_usage" id="basic_openssh_client_configuration_and_usage"></a>

Хотя сервер и клиент OpenSSH поставляются в отдельных пакетах, обычно можно установить метапакет, который предоставит и то, и другое одновременно. Чтобы установить удалённый сеанс с SSH-сервером, используйте команду `ssh` и укажите пользователя, от имени которого вы хотите подключиться к удалённому компьютеру, а также IP-адрес или имя удалённого компьютера. При первом подключении к удалённому хосту вы получите такое сообщение:

```bash
carol@debian:~$ ssh ina@192.168.1.77
The authenticity of host '192.168.1.77 (192.168.1.77)' can't be established.
ECDSA key fingerprint is SHA256:5JF7anupYipByCQm2BPvDHRVFJJixeslmppi2NwATYI.
Are you sure you want to continue connecting (yes/no)?
```

После ввода `yes` и нажатия клавиши Enter вам будет предложено ввести пароль удалённого пользователя. При успешном вводе вам будет показано предупреждающее сообщение, а затем вы войдёте в систему удалённого хоста:

```bash
Warning: Permanently added '192.168.1.77' (ECDSA) to the list of known hosts.
Password:
Last login: Sat Jun 20 10:52:45 2020 from 192.168.1.4
Have a lot of fun...
ina@halof:~>
```

Сообщения говорят сами за себя: поскольку вы впервые установили соединение с `192.168.1.77` удалённым сервером, его подлинность не могла быть проверена по какой-либо базе данных. Таким образом, удалённый сервер предоставил `ECDSA key fingerprint` своего открытого ключа (с помощью `SHA256` хэш-функции). Как только вы приняли соединение, открытый ключ удалённого сервера был добавлен в базу данных _известных хостов_, что позволило аутентифицировать сервер для будущих подключений. Этот список открытых ключей _известных хостов_ хранится в файле `known_hosts`, который находится в `~/.ssh`:

```bash
ina@halof:~> exit
logout
Connection to 192.168.1.77 closed.
carol@debian:~$ ls .ssh/
known_hosts
```

И `.ssh` и `known_hosts` были созданы после установления первого удалённого подключения. `~/.ssh` — это каталог по умолчанию для пользовательских настроек и информации об аутентификации.

{% hint style="info" %}
Вы также можете использовать `ssh` для выполнения одной команды на удалённом хосте, а затем вернуться в свой локальный терминал (например, запустив `ssh ina@halof ls`).
{% endhint %}

Если вы используете одного и того же пользователя на локальном и удалённом хостах, нет необходимости указывать имя пользователя при установлении SSH-соединения. Например, если вы вошли в систему как пользователь `carol` на `debian` и хотите подключиться к `halof` также как пользователь `carol`, вы можете просто ввести `ssh 192.168.1.77` или `ssh halof` (если имя можно разрешить):

```bash
carol@debian:~$ ssh halof
Password:
Last login: Wed Jul  1 23:45:02 2020 from 192.168.1.55
Have a lot of fun...
carol@halof:~>
```

Теперь предположим, что вы устанавливаете новое удалённое соединение с хостом, у которого тот же IP-адрес, что и у `halof` (это часто случается, если вы используете DHCP в своей локальной сети). Вы получите предупреждение о возможности атаки _«человек посередине»_:

Поскольку вы не имеете дело с атакой _«человек посередине»_, вы можете спокойно добавить отпечаток открытого ключа нового хоста в `.ssh/known_hosts`. Как указано в сообщении, вы можете сначала использовать команду `ssh-keygen -f "/home/carol/.ssh/known_hosts" -R "192.168.1.77"` для удаления _неподходящего_ ключа (в качестве альтернативы вы можете использовать `ssh-keygen -R 192.168.1.77` для удаления всех ключей, принадлежащих `192.168.1.77` из `~/.ssh/known_hosts`). Затем вы сможете установить соединение с новым хостом.

## Вход в систему по ssh ключу

Вы можете настроить свой SSH-клиент так, чтобы при входе в систему не вводить пароль, а использовать вместо него открытые ключи. Это предпочтительный способ подключения к удалённому серверу по SSH, так как он гораздо безопаснее. Первое, что вам нужно сделать, — это создать пару ключей на клиентском компьютере. Для этого вы будете использовать `ssh-keygen` с опцией `-t` для указания нужного типа шифрования (_алгоритм цифровой подписи эллиптической кривой_ в нашем случае). Затем вам будет предложено указать путь для сохранения пары ключей (`~/.ssh/` — это удобно, так как это расположение по умолчанию) и кодовую фразу. Кодовая фраза не является обязательной, но настоятельно рекомендуется использовать её.

```bash
carol@debian:~/.ssh$ ssh-keygen -t ecdsa
Generating public/private ecdsa key pair.
Enter file in which to save the key (/home/carol/.ssh/id_ecdsa):
Enter passphrase (empty for no passphrase):
Enter same passphrase again:
Your identification has been saved in /home/carol/.ssh/id_ecdsa.
Your public key has been saved in /home/carol/.ssh/id_ecdsa.pub.
The key fingerprint is:
SHA256:tlamD0SaTquPZYdNepwj8XN4xvqmHCbe8g5FKKUfMo8 carol@debian
The key's randomart image is:
+---[ECDSA 256]---+
|      .          |
|     o .         |
|    = o o        |
|     B *         |
|    E B S o      |
|     o & O       |
|      @ ^ =      |
|     *.@ @.      |
|    o.o+B+o      |
+----[SHA256]-----+
```

{% hint style="info" %}
При создании пары ключей вы можете передать `ssh-keygen` параметр `-b` для указания размера ключа в битах (например, `ssh-keygen -t ecdsa -b 521`).
{% endhint %}

Предыдущая команда создала еще два файла в вашем `~/.ssh` каталоге:

```bash
carol@debian:~/.ssh$ ls
id_ecdsa  id_ecdsa.pub  known_hosts
```

`id_ecdsa`

Это ваш закрытый ключ.

`id_ecdsa.pub`

Это ваш открытый ключ.

\
Следующее, что вам нужно сделать, — это добавить свой открытый ключ в файл `~/.ssh/authorized_keys` пользователя, от имени которого вы хотите войти на удалённый хост (если каталог `~/.ssh` ещё не существует, вам нужно будет создать его). Вы можете скопировать свой открытый ключ на удалённый сервер несколькими способами: с помощью USB-накопителя, с помощью команды `scp` — которая перенесёт файл с помощью SSH — или _выведя_ содержимое вашего открытого ключа и передав его в `ssh` следующим образом:

```bash
carol@debian:~/.ssh$ cat id_ecdsa.pub |ssh ina@192.168.1.77 'cat >> .ssh/authorized_keys'
Password:
```

*   Если вы не указали кодовую фразу при создании пары ключей, вы войдёте в систему автоматически. Несмотря на удобство, этот метод может быть небезопасным в зависимости от ситуации:

    ```bash
    carol@debian:~$ ssh ina@192.168.1.77
    Last login: Thu Jun 25 20:31:03 2020 from 192.168.1.55
    Have a lot of fun...
    ina@halof:~>
    ```
*   Если при создании пары ключей вы указали парольную фразу, вам придется вводить ее при каждом подключении так же, как если бы это был пароль. Помимо открытого ключа, этот метод обеспечивает дополнительный уровень безопасности в виде парольной фразы и, следовательно, может считаться более безопасным. Однако с точки зрения удобства это то же самое, что вводить пароль при каждом подключении. Если вы не используете парольную фразу и кому-то удастся получить ваш закрытый ключ SSH, он получит доступ ко всем серверам, на которых установлен ваш открытый ключ.

    <pre class="language-bash"><code class="lang-bash"><strong>carol@debian:~/.ssh$ ssh ina@192.168.1.77
    </strong>Enter passphrase for key '/home/carol/.ssh/id_ecdsa':
    Last login: Thu Jun 25 20:39:30 2020 from 192.168.1.55
    Have a lot of fun...
    ina@halof:~>
    </code></pre>

Однако есть способ, который сочетает в себе безопасность и удобство: использование _агента аутентификации SSH_ (`ssh-agent`). Агент аутентификации должен создать собственную оболочку и хранить ваши закрытые ключи — для аутентификации по открытому ключу — в памяти до конца сеанса. Давайте рассмотрим, как это работает, подробнее:

1.  Используйте `ssh-agent` для запуска новой оболочки Bash:

    ```bash
    carol@debian:~/.ssh$ ssh-agent /bin/bash
    carol@debian:~/.ssh$
    ```
2.  Используйте команду `ssh-add`, чтобы добавить свой закрытый ключ в защищенную область памяти. Если вы указали кодовую фразу при создании пары ключей, что рекомендуется для дополнительной безопасности, вас попросят ввести ее.:

    <pre><code><strong>carol@debian:~/.ssh$ ssh-add
    </strong>Enter passphrase for /home/carol/.ssh/id_ecdsa:
    Identity added: /home/carol/.ssh/id_ecdsa (carol@debian)
    </code></pre>

После добавления вашей учётной записи вы сможете войти на любой удалённый сервер, на котором есть ваш открытый ключ, без необходимости повторно вводить парольную фразу. На современных компьютерах принято выполнять эту команду при загрузке компьютера, так как она будет оставаться в памяти до выключения компьютера (или до выгрузки ключа вручную).

Давайте завершим этот раздел, перечислив четыре типа алгоритмов с открытым ключом, которые можно указать с помощью `ssh-keygen`:

`RSA`

Он был опубликован в 1977 году и назван в честь своих создателей Рона Ривеста, Ади Шамира и Леонарда Адлемана. Он считается безопасным и до сих пор широко используется. Минимальный размер ключа составляет 1024 бита (по умолчанию — 2048).

`DSA`

_Алгоритм цифровой подписи_ _Digital Signature Algorithm_ оказался небезопасным, и в OpenSSH 7.0 он был удалён. Ключи DSA должны быть ровно 1024 бита в длину.

`ecdsa`

_Алгоритм цифровой подписи на эллиптических кривых_ является усовершенствованной версией DSA и, следовательно, считается более безопасным. Он использует криптографию на эллиптических кривых. Длина ключа ECDSA определяется одним из трёх возможных размеров эллиптической кривой в битах: 256, 384 или 521.

`ed25519`

Это реализация `EdDSA` — _алгоритма цифровой подписи Эдвардс-кривой_ — которая использует более надёжную кривую 25519. Она считается самой безопасной из всех. Все ключи Ed25519 имеют фиксированную длину 256 бит.

{% hint style="info" %}
и не указать `-t` при вызове, `ssh-keygen` по умолчанию создаст пару ключей `RSA`
{% endhint %}

## Роль ключей хоста сервера OpenSSH <a href="#the_role_of_openssh_server_host_keys" id="the_role_of_openssh_server_host_keys"></a>

Глобальный каталог конфигурации для OpenSSH находится в `/etc` каталоге:

```bash
alof:~ # tree /etc/ssh
/etc/ssh
├── moduli
├── ssh_config
├── ssh_host_dsa_key
├── ssh_host_dsa_key.pub
├── ssh_host_ecdsa_key
├── ssh_host_ecdsa_key.pub
├── ssh_host_ed25519_key
├── ssh_host_ed25519_key.pub
├── ssh_host_rsa_key
├── ssh_host_rsa_key.pub
└── sshd_config

0 directories, 11 files
```

Помимо `moduli` и файлов конфигурации для клиента (`ssh_config`) и сервера (`sshd_config`), вы найдёте четыре пары ключей — по паре ключей для каждого поддерживаемого алгоритма, — которые создаются при установке сервера _OpenSSH_. Как уже отмечалось, сервер использует эти _ключи хоста_ для идентификации себя перед клиентами по мере необходимости. Их имена имеют следующий шаблон:

Закрытые ключи

`ssh_host_` префикс + _алгоритм_ + `key` суффикс (например: `ssh_host_rsa_key`)

Открытые ключи (или отпечатки пальцев открытого ключа)

`ssh_host_` префикс + _алгоритм_ + `key.pub` суффикс (например: `ssh_host_rsa_key.pub`)

{% hint style="info" %}
Отпечаток создаётся путём применения криптографической хэш-функции к открытому ключу. Поскольку отпечатки короче ключей, к которым они относятся, они упрощают некоторые задачи по управлению ключами.
{% endhint %}

Права доступа к файлам, содержащим закрытые ключи, — `0600` или `-rw-------`: только чтение и запись для владельца (`root`). С другой стороны, все файлы открытых ключей также доступны для чтения членам группы владельцев и всем остальным (`0644` или `-rw-r—​r--`):

```bash
halof:~ # ls -l /etc/ssh/ssh_host_*
-rw------- 1 root root 1381 Dec 21 20:35 /etc/ssh/ssh_host_dsa_key
-rw-r--r-- 1 root root  605 Dec 21 20:35 /etc/ssh/ssh_host_dsa_key.pub
-rw------- 1 root root  505 Dec 21 20:35 /etc/ssh/ssh_host_ecdsa_key
-rw-r--r-- 1 root root  177 Dec 21 20:35 /etc/ssh/ssh_host_ecdsa_key.pub
-rw------- 1 root root  411 Dec 21 20:35 /etc/ssh/ssh_host_ed25519_key
-rw-r--r-- 1 root root   97 Dec 21 20:35 /etc/ssh/ssh_host_ed25519_key.pub
-rw------- 1 root root 1823 Dec 21 20:35 /etc/ssh/ssh_host_rsa_key
-rw-r--r-- 1 root root  397 Dec 21 20:35 /etc/ssh/ssh_host_rsa_key.pub
```

Вы можете просмотреть отпечатки ключей, передав `ssh-keygen` параметр `-l` . Вы также должны указать `-f` для определения пути к файлу ключа:

```bash
halof:~ # ssh-keygen -l -f /etc/ssh/ssh_host_ed25519_key
256 SHA256:8cnPrinC49ZHc+/9Ai5pV+1JfZ4WBRZhd3rDOsc2zlA root@halof (ED25519)
halof:~ # ssh-keygen -l -f /etc/ssh/ssh_host_ed25519_key.pub
256 SHA256:8cnPrinC49ZHc+/9Ai5pV+1JfZ4WBRZhd3rDOsc2zlA root@halof (ED25519)
```

Чтобы просмотреть отпечаток ключа, а также его случайное изображение, просто добавьте переключатель `-v` следующим образом:

```bash
halof:~ # ssh-keygen -lv -f /etc/ssh/ssh_host_ed25519_key.pub
256 SHA256:8cnPrinC49ZHc+/9Ai5pV+1JfZ4WBRZhd3rDOsc2zlA root@halof (ED25519)
+--[ED25519 256]--+
| +oo|
| .+o.|
| . ..E.|
| + . +.o|
| S + + *o|
| ooo Oo=|
| . . . =o+.==|
| = o =oo o=o|
| o.o +o+..o.+|
+----[SHA256]-----+
```

## Туннели портов SSH <a href="#ssh_port_tunnels" id="ssh_port_tunnels"></a>

В OpenSSH есть очень мощная функция переадресации, с помощью которой трафик на исходном порту туннелируется и шифруется с помощью процесса SSH, который затем перенаправляет его на порт на целевом хосте. Этот механизм известен как _туннелирование портов_ или _переадресация портов_ и имеет следующие важные преимущества:

* Это позволяет вам обходить брандмауэры для доступа к портам на удаленных хостах.
* Это позволяет получить доступ извне к хосту в вашей частной сети.
* Он обеспечивает шифрование для всего обмена данными.

Грубо говоря, мы можем различать туннелирование локальных и удаленных портов.

## **Туннель Локального Порта**

Вы определяете локальный порт для переадресации трафика на целевой хост через промежуточный процесс SSH. Процесс SSH может выполняться на локальном хосте или на удалённом сервере. Например, если по какой-то причине вы хотите создать туннель для подключения к `www.gnu.org` через SSH с использованием порта `8585` на вашем локальном компьютере, вы можете сделать что-то вроде этого:

```bash
carol@debian:~$ ssh -L 8585:www.gnu.org:80 debian
carol@debian's password:
Linux debian 4.19.0-9-amd64 #1 SMP Debian 4.19.118-2 (2020-04-29) x86_64

The programs included with the Debian GNU/Linux system are free software;
(...)
Last login: Sun Jun 28 13:47:27 2020 from 127.0.0.1
```

Объяснение следующее: с помощью переключателя `-L` мы указываем локальный порт `8585` для подключения к _http_-порту `80` на `www.gnu.org` с помощью процесса SSH, запущенного на `debian` — нашем _локальном хосте_. Мы могли бы написать `ssh -L 8585:www.gnu.org:80 localhost` с тем же результатом. Если вы сейчас откроете веб-браузер и перейдёте по адресу `http://localhost:8585`, вы будете перенаправлены на `www.gnu.org`. Для демонстрации мы будем использовать `lynx` (классический веб-браузер в текстовом режиме):

```bash
carol@debian:~$ lynx http://localhost:8585
(...)

```

Если бы вы хотели сделать то же самое, но подключиться через процесс SSH, запущенный на `halof`, вы бы поступили следующим образом:

```
carol@debian:~$ ssh -L 8585:www.gnu.org:80 -Nf ina@192.168.1.77

carol@debian:~$
```

* Благодаря опции `-N` мы не входили в `halof` напрямую, а использовали переадресацию портов.
* Опция `-f` указала SSH работать в фоновом режиме.
* Мы указали пользователя `ina` для выполнения переадресации: `ina@192.168.1.77`

## **Туннель удаленного Порта**

При удалённом туннелировании портов (или обратной переадресации портов) трафик, поступающий на порт удалённого сервера, перенаправляется на процесс SSH, запущенный на вашем локальном хосте, а оттуда — на указанный порт на целевом сервере (который также может быть вашим локальным компьютером). Например, предположим, что вы хотите разрешить кому-то из-за пределов вашей сети доступ к веб-серверу Apache, запущенному на вашем локальном хосте, через порт `8585` сервера SSH, запущенного на `halof` (`192.168.1.77`). Для этого выполните следующую команду:

```bash
carol@debian:~$ ssh -R 8585:localhost:80 -Nf ina@192.168.1.77
Enter passphrase for key '/home/carol/.ssh/id_ecdsa':
carol@debian:~$
```

Теперь любой, кто установит соединение на хосте `halof` через порт 8585 на интерфейсе `localhost`, увидит домашнюю страницу Apache2 по умолчанию в Debian:

```bash
carol@halof:~$ lynx localhost:8585
(...)
                                                                 Apache2 Debian Default Page: It works (p1 of 3)
   Debian Logo Apache2 Debian Default Page
   It works!

   This is the default welcome page used to test the correct operation of the Apache2 server after
   installation on Debian systems. If you can read this page, it means that the Apache HTTP server
   installed at this site is working properly. You should replace this file (located at
   /var/www/html/index.html) before continuing to operate your HTTP server.
(...)
```

Чтобы разрешить удалённому хосту `halof` создать туннель со всеми его сетевыми интерфейсами на определённом порту, необходимо сначала убедиться, что параметр `GatewayPorts yes` настроен в файле `sshd_config` для сопоставления со всеми интерфейсами. По умолчанию для параметра установлено значение `no`, что приводит к сопоставлению с туннелем только интерфейса `localhost`.

```bash
carol@debian:~$ ssh -R 0.0.0.0:8585:localhost:80 -Nf ina@192.168.1.77
Enter passphrase for key '/home/carol/.ssh/id_ecdsa':
carol@debian:~$
```

Теперь любой, кто установит соединение с `halof` на порту 8585 по любому IP-адресу, увидит домашнюю страницу Apache2 по умолчанию в Debian:

```bash
carol@debian:~$ lynx 192.168.1.77:8585
(...)
                                                                 Apache2 Debian Default Page: It works (p1 of 3)
   Debian Logo Apache2 Debian Default Page
   It works!
(...)
```

{% hint style="info" %}
Существует третий, более сложный тип переадресации портов, который выходит за рамки этого урока: _динамическая переадресация портов_. Вместо взаимодействия с одним портом этот тип переадресации использует различные TCP-соединения по ряду портов.
{% endhint %}

## **Туннели X11**

Теперь, когда вы разобрались с туннелями портов, давайте завершим этот урок обсуждением туннелирования X11 (также известного как _переадресация X11_). Через туннель X11 _система X Window_ на удалённом хосте перенаправляется на ваш локальный компьютер. Для этого вам нужно просто передать `ssh` параметр `-X`:

```bash
carol@debian:~$ ssh -X ina@halof
...
```

Теперь вы можете запустить графическое приложение, например веб-браузер `firefox`, со следующим результатом: приложение будет работать на удалённом сервере, но его отображение будет передаваться на ваш локальный хост.

Если вместо этого вы запустите новый сеанс SSH с опцией `-x`, _переадресация X11_ будет отключена. Попробуйте запустить `firefox` сейчас, и вы получите сообщение об ошибке, подобное следующему:

```bash
carol@debian:~$ ssh -x ina@halof
carol@192.168.0.106's password:
(...)
ina@halof:~$ firefox

(firefox-esr:1779): Gtk-WARNING **: 18:45:45.603: Locale not supported by C library.
	Using the fallback 'C' locale.
Error: no DISPLAY environment variable specified
```

{% hint style="info" %}
Три директивы конфигурации, связанные с переадресацией локальных портов, переадресацией удалённых портов и переадресацией X11, — это `AllowTcpForwarding`, `GatewayPorts` и `X11Forwarding` соответственно. Для получения дополнительной информации введите `man ssh_config` и/или `man sshd_config`.
{% endhint %}
