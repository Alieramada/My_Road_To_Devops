# Урок 1.3.

## Введение <a href="#sec.101.3_01-in" id="sec.101.3_01-in"></a>

Общей чертой операционных систем, разработанных в соответствии с принципами Unix, является использование отдельных процессов для управления различными функциями системы. Эти процессы, называемые _демонами_ (или, в более общем смысле, _сервисами_), также отвечают за расширенные функции, лежащие в основе операционной системы, такие как сетевые прикладные сервисы (HTTP-сервер, общий доступ к файлам, электронная почта и т. д.), базы данных, настройка по требованию (конфигурация по требованию) — это подход к управлению настройками и конфигурациями, при котором изменения в системе происходят только тогда, когда они необходимы. и т. д. Хотя в Linux используется монолитное ядро, многие низкоуровневые аспекты операционной системы зависят от демонов, например, балансировка нагрузки и настройка брандмауэра.

Какие демоны должны быть активны, зависит от назначения системы. Набор активных демонов также должен быть изменяемым во время работы, чтобы службы можно было запускать и останавливать без перезагрузки всей системы. Для решения этой проблемы в каждом крупном дистрибутиве Linux есть та или иная утилита для управления службами.

Управление службами может осуществляться с помощью сценариев оболочки или программы и поддерживающих её файлов конфигурации. Первый метод реализован в стандарте _SysVinit_, также известном как _System V_ или просто _SysV_. Второй метод реализован в _systemd_ и _Upstart_. Исторически сложилось так, что менеджеры служб на основе SysV чаще всего использовались в дистрибутивах Linux. Сегодня в большинстве дистрибутивов Linux чаще используются менеджеры служб на основе systemd. Диспетчер служб — это первая программа, запускаемая ядром в процессе загрузки, поэтому её PID (идентификационный номер процесса) всегда равен `1`.

## SysVinit <a href="#sec.101.3_01-sv" id="sec.101.3_01-sv"></a>

Диспетчер служб, основанный на стандарте SysVinit, предоставляет предопределённые наборы системных состояний, называемые _уровнями выполнения_, и соответствующие им файлы сценариев служб для выполнения. Уровни выполнения пронумерованы от `0` до `6` и обычно назначаются для следующих целей:

Уровень выполнения 0

Завершение работы системы.

Уровень выполнения 1, s single или одиночный

Однопользовательский режим без доступа к сети и другим необязательным функциям (режим обслуживания).

Уровень выполнения 2, 3 или 4

Многопользовательский режим. Пользователи могут входить в систему через консоль или сеть. Уровни выполнения 2 и 4 используются нечасто.

Уровень выполнения 5

Многопользовательский режим. Он аналогичен режиму 3, плюс вход в графический режим.

Уровень выполнения 6

Перезагрузка системы.

Программа, отвечающая за управление уровнями выполнения и связанными с ними демонами/ресурсами, — это `/sbin/init`. Во время инициализации системы программа `init` определяет запрошенный уровень выполнения, заданный параметром ядра или в файле `/etc/inittab`, и загружает связанные с ним сценарии, перечисленные в этом файле для заданного уровня выполнения. С каждым уровнем выполнения может быть связано множество служебных файлов, обычно это сценарии в каталоге `/etc/init.d/`. Поскольку не все уровни выполнения эквивалентны в разных дистрибутивах Linux, краткое описание назначения уровня выполнения также можно найти в дистрибутивах на основе SysV.

Синтаксис `/etc/inittab` файла использует этот формат:

```
идентификатор: уровни выполнения: действие: процесс
id:runlevels:action:process
```

`id` — это общее название длиной до четырёх символов, используемое для идентификации записи. Запись `runlevels` — это список номеров уровней выполнения, для которых должно быть выполнено указанное действие. Термин `action` определяет, как `init` будет выполнять процесс, обозначенный термином `process`. Доступные действия:

`boot`

Процесс будет запущен во время инициализации системы. Поле `runlevels` игнорируется.

`bootwait`

Процесс будет выполняться во время инициализации системы, и `init` будет ожидать завершения процесса, чтобы продолжить. Поле `runlevels` игнорируется.

`sysinit`

Процесс будет запущен после инициализации системы, независимо от уровня выполнения. Поле `runlevels` игнорируется.

`wait`

Процесс будет выполняться для заданных уровней выполнения, и `init` будет ожидать его завершения, чтобы продолжить.

`respawn`

Процесс будет перезапущен, если он будет завершен.

`ctrlaltdel`

Процесс будет запущен, когда процесс инициализации получит сигнал `SIGINT`, который срабатывает при нажатии последовательности клавиш Ctrl+Alt+Del.

Уровень выполнения по умолчанию — тот, который будет выбран, если не указан другой уровень в качестве параметра ядра, — также определяется в `/etc/inittab` в записи `id:x:initdefault`.`x` — это номер уровня выполнения по умолчанию. Этот номер никогда не должен быть `0` или `6`, так как это приведёт к выключению или перезагрузке системы сразу после завершения процесса загрузки. Типичный файл `/etc/inittab` показан ниже:

```bash
# Default runlevel
id:3:initdefault:

# Configuration script executed during boot
si::sysinit:/etc/init.d/rcS

# Action taken on runlevel S (single user)
~:S:wait:/sbin/sulogin

# Configuration for each execution level
l0:0:wait:/etc/init.d/rc 0
l1:1:wait:/etc/init.d/rc 1
l2:2:wait:/etc/init.d/rc 2
l3:3:wait:/etc/init.d/rc 3
l4:4:wait:/etc/init.d/rc 4
l5:5:wait:/etc/init.d/rc 5
l6:6:wait:/etc/init.d/rc 6

# Action taken upon ctrl+alt+del keystroke
ca::ctrlaltdel:/sbin/shutdown -r now

# Enable consoles for runlevels 2 and 3
1:23:respawn:/sbin/getty tty1 VC linux
2:23:respawn:/sbin/getty tty2 VC linux
3:23:respawn:/sbin/getty tty3 VC linux
4:23:respawn:/sbin/getty tty4 VC linux

# For runlevel 3, also enable serial
# terminals ttyS0 and ttyS1 (modem) consoles
S0:3:respawn:/sbin/getty -L 9600 ttyS0 vt320
S1:3:respawn:/sbin/mgetty -x0 -D ttyS1
```

Аргумент `q` (или `Q`) указывает init на необходимость перезагрузки конфигурации. Этот шаг важен для предотвращения остановки системы из-за неправильной конфигурации в `/etc/inittab`.

Сценарии, используемые `init` для настройки каждого уровня выполнения, хранятся в каталоге `/etc/init.d/`. С каждым уровнем выполнения в `/etc/` связан каталог с именем `/etc/rc0.d/`, `/etc/rc1.d/`, `/etc/rc2.d/` и т. д., в котором хранятся сценарии, которые должны выполняться при запуске соответствующего уровня выполнения. Поскольку один и тот же сценарий может использоваться разными уровнями выполнения, файлы в этих каталогах являются просто символическими ссылками на фактические сценарии в `/etc/init.d/`. Кроме того, первая буква в имени ссылки в каталоге уровня выполнения указывает, следует ли запускать или останавливать службу для соответствующего уровня выполнения. Имя ссылки, начинающееся с буквы `K`, указывает на то, что служба будет остановлена при входе в уровень выполнения (остановка). Если имя ссылки начинается с буквы `S`, служба будет запущена при входе в уровень выполнения (запуск). Например, в каталоге `/etc/rc1.d/` будет много ссылок на сетевые сценарии, начинающиеся с буквы `K`, учитывая, что уровень выполнения 1 — это уровень выполнения для одного пользователя без подключения к сети.

Команда `runlevel` показывает текущий уровень выполнения системы. Команда `runlevel` показывает два значения: первое — предыдущий уровень выполнения, а второе — текущий уровень выполнения:

```bash
$ runlevel
N 3
```

Буква `N` в выводе показывает, что уровень выполнения не изменился с момента последней загрузки. В этом примере `runlevel 3` — это текущий уровень выполнения системы.

Одна и та же `init` программа может использоваться для чередования уровней выполнения в работающей системе без необходимости перезагрузки. Команда `telinit` также может использоваться для чередования уровней выполнения. Например, команды `telinit 1`, `telinit s` или `telinit S` переведут систему на уровень выполнения 1.

## systemd <a href="#sec.101.3_01-sy" id="sec.101.3_01-sy"></a>

В настоящее время systemd является наиболее широко используемым набором инструментов для управления системными ресурсами и службами, которые в systemd называются _модулями_. Модуль состоит из имени, типа и соответствующего файла конфигурации. Например, модуль для процесса _httpd_ (например, веб-сервера Apache) в дистрибутивах на базе Red Hat будет называться `httpd.service` и его файл конфигурации также будет называться `httpd.service` (в дистрибутивах на базе Debian этот модуль называется `apache2.service`).

Существует семь различных типов модулей systemd:

`service`

Наиболее распространённый тип устройств для активных системных ресурсов, которые можно запускать, останавливать и перезагружать.

`socket`

Тип сокета может быть сокетом файловой системы или сетевым сокетом. Все сокеты имеют соответствующий служебный модуль, загружаемый при получении сокетом запроса.

`device`

Блок устройства связан с аппаратным устройством, идентифицированным ядром. Устройство будет восприниматься как блок systemd только в том случае, если для этого существует правило udev. Блок устройства можно использовать для разрешения зависимостей конфигурации при обнаружении определённого оборудования, учитывая, что свойства из правила udev можно использовать в качестве параметров для блока устройства.

`mount`

Блок монтирования — это определение точки монтирования в файловой системе, аналогичное записи в `/etc/fstab`.

`automount`

Модуль автомонтирования — это тоже определение точки монтирования в файловой системе, но монтируется он автоматически. У каждого модуля автомонтирования есть соответствующий модуль монтирования, который запускается при обращении к точке монтирования.

`target`

Целевая единица — это группа других единиц, управляемая как единое целое.

`snapshot`

Блок моментальных снимков — это сохранённое состояние менеджера systemd (доступно не во всех дистрибутивах Linux).

Основная команда для управления модулями systemd — `systemctl`. Команда `systemctl` используется для выполнения всех задач, связанных с активацией, деактивацией, выполнением, прерыванием, мониторингом и т. д. модулей. Например, для вымышленного модуля с именем `unit.service` наиболее распространёнными действиями `systemctl` будут:

`systemctl start unit.service`

Начинает `unit`.

`systemctl stop unit.service`

Остановка `unit`.

`systemctl restart unit.service`

Перезапуск `unit`.

`systemctl status unit.service`

Показывает состояние `unit`, в том числе, запущено оно или нет.

`systemctl is-active unit.service`

Показывает, _активен_, если `unit` запущен, или неактивен в противном случае.

`systemctl enable unit.service`

Включает, `unit` то есть `unit` будет загружаться во время инициализации системы.

`systemctl disable unit.service`

`unit` не запустится вместе с системой.

`systemctl is-enabled unit.service`

Проверяет, начинается ли `unit` с системы. Ответ сохраняется в переменной `$?`. Значение `0` указывает на то, что `unit` запускается вместе с системой системы, а значение `1` указывает на то, что `unit` не запускается вместе с системой.

{% hint style="info" %}
В более новых версиях systemd при загрузке отображается конфигурация модуля. Например:

```sh
$ systemctl is-enabled apparmor.service
enabled
```
{% endhint %}

Если в системе нет других единиц измерения с таким же названием, то суффикс после точки можно опустить. Если, например, есть только одна единица измерения `httpd` типа `service`, то в качестве параметра единицы измерения для `httpd` достаточно только `systemctl`.

Команда `systemctl` также может управлять _системными целями_. Например, блок `multi-user.target` объединяет все блоки, необходимые для многопользовательской системы. Он аналогичен уровню выполнения 3 в системе, использующей SysV.

Команда `systemctl isolate` переключает между различными целями. Итак, чтобы вручную переключиться на цель `multi-user`:

```sh
# systemctl isolate multi-user.target
```

Для уровней выполнения SysV существуют соответствующие цели, начиная с `runlevelO.target` и заканчивая `runlevel6.target`. Однако systemd не использует файл `/etc/inittab`. Чтобы изменить системную цель по умолчанию, в список параметров ядра можно добавить опцию `systemd.unit`. Например, чтобы использовать `multi-user.target` в качестве стандартной цели, параметр ядра должен быть `systemd.unit=multi-user.target`. Все параметры ядра можно сделать постоянными, изменив конфигурацию загрузчика.

Другой способ изменить цель по умолчанию — изменить символическую ссылку `/etc/systemd/system/default.target` так, чтобы она указывала на нужную цель. Переопределить ссылку можно с помощью команды `systemctl`:

```sh
# systemctl set-default multi-user.target
```

Аналогичным образом вы можете определить целевую систему загрузки по умолчанию с помощью следующей команды:

```
$ systemctl get-default
graphical.target
```

Как и в системах, использующих SysV, цель по умолчанию никогда не должна указывать на `shutdown.target`, так как это соответствует уровню выполнения 0 (завершение работы).

Файлы конфигурации, связанные с каждым устройством, можно найти в каталоге `/lib/systemd/system/`. Команда `systemctl list-unit-files` выводит список всех доступных устройств и показывает, включены ли они для запуска при загрузке системы. Опция `--type` позволяет выбрать только устройства определенного типа, например `systemctl list-unit-files --type=service` и `systemctl list-unit-files --type=target`.

Активные устройства или устройства, которые были активны во время текущего сеанса работы системы, можно вывести на экран с помощью команды `systemctl list-units`. Как и опция `list-unit-files`, команда `systemctl list-units --type=service` выберет только устройства типа `service`, а команда `systemctl list-units --type=target` выберет только устройства типа `target`.

systemd также отвечает за запуск и обработку событий, связанных с питанием. Команда `systemctl suspend` переведёт систему в режим пониженного энергопотребления, сохранив текущие данные в памяти. Команда `systemctl hibernate` скопирует все данные из памяти на диск, чтобы текущее состояние системы можно было восстановить после выключения. Действия, связанные с такими событиями, определяются в файле `/etc/systemd/logind.conf` или в отдельных файлах в каталоге `/etc/systemd/logind.conf.d/`. Однако эту функцию systemd можно использовать только в том случае, если в системе не запущен другой менеджер питания, например демон `acpid`. Демон `acpid` является основным диспетчером питания для Linux и позволяет более точно настраивать действия, выполняемые после событий, связанных с питанием, таких как закрытие крышки ноутбука, низкий уровень заряда батареи или уровень зарядки аккумулятора.

#### Upstart <a href="#sec.101.3_01-up" id="sec.101.3_01-up"></a>

Сценарии инициализации, используемые Upstart, находятся в каталоге `/etc/init/`. Системные службы можно вывести с помощью команды `initctl list`, которая также показывает текущее состояние служб и, если доступно, их номер PID.

```sh
# initctl list
avahi-cups-reload stop/waiting
avahi-daemon start/running, process 1123
mountall-net stop/waiting
mountnfs-bootclean.sh start/running
nmbd start/running, process 3085
passwd stop/waiting
rc stop/waiting
rsyslog start/running, process 1095
tty4 start/running, process 1761
udev start/running, process 1073
upstart-udev-bridge start/running, process 1066
console-setup stop/waiting
irqbalance start/running, process 1842
plymouth-log stop/waiting
smbd start/running, process 1457
tty5 start/running, process 1764
failsafe stop/waiting
```

У каждого действия Upstart есть своя независимая команда. Например, команда `start` может использоваться для запуска шестого виртуального терминала:

```sh
# start tty6
```

Текущее состояние ресурса можно проверить с помощью команды `status`:

```sh
# status tty6
tty6 start/running, process 3282
```

И завершение выполняется командой `stop`:

```sh
# stop tty6
```

Upstart не использует файл `/etc/inittab` для определения уровней запуска, но устаревшие команды `runlevel` и `telinit` по-прежнему можно использовать для проверки и переключения между уровнями запуска.

{% hint style="info" %}
Upstart был разработан для дистрибутива Ubuntu Linux, чтобы упростить параллельный запуск процессов. Ubuntu перестала использовать Upstart в 2015 году, когда перешла с Upstart на systemd.
{% endhint %}

## Завершение работы и перезапуск <a href="#sec.101.3_01-sr" id="sec.101.3_01-sr"></a>

Очень традиционная команда, используемая для выключения или перезапуска системы, как и следовало ожидать, называется `shutdown`. Команда `shutdown` добавляет дополнительные функции к процессу выключения: она автоматически уведомляет всех вошедших в систему пользователей предупреждающим сообщением в их сеансах командной строки, а также предотвращает новые входы в систему. Команда `shutdown` выступает в качестве посредника для процедур SysV или systemd, то есть она выполняет запрошенное действие, вызывая соответствующее действие в менеджере служб, используемом системой.

После выполнения `shutdown` все процессы получают сигнал `SIGTERM`, за которым следует сигнал `SIGKILL`, после чего система завершает работу или меняет уровень выполнения. По умолчанию, если не используются параметры `-h` или `-r`, система переключается на уровень выполнения 1, то есть в однопользовательский режим. Чтобы изменить параметры по умолчанию для `shutdown`, команда должна быть выполнена в следующем синтаксисе:

```sh
$ shutdown [option] time [message]
```

Требуется только параметр `time`. Параметр `time` определяет, когда будет выполнено запрошенное действие, принимая следующие форматы:

`hh:mm`

Этот формат определяет время выполнения в виде часов и минут.

`+m`

Этот формат определяет, сколько минут нужно ждать перед выполнением.

`now` или `+0`

Этот формат определяет немедленное выполнение.

Параметр `message` — это текст предупреждения, отправляемый во все сеансы терминала вошедших в систему пользователей.

Реализация SysV позволяет ограничить число пользователей, которые смогут перезагрузить компьютер нажатием Ctrl+Alt+Del. Это можно сделать, добавив параметр `-a` для команды `shutdown` в строку `ctrlaltdel` в файле `/etc/inittab`. Таким образом, только пользователи, имена которых указаны в файле `/etc/shutdown.allow`, смогут перезагрузить систему нажатием Ctrl+Alt+Del.

Команда `systemctl` также может использоваться для выключения или перезапуска компьютера в системах, использующих systemd. Для перезапуска системы следует использовать команду `systemctl reboot`. Для выключения системы следует использовать команду `systemctl poweroff`. Для выполнения обеих команд требуются права суперпользователя, поскольку обычные пользователи не могут выполнять такие процедуры.

{% hint style="info" %}
В некоторых дистрибутивах Linux `poweroff` и `reboot` будут связаны с `systemctl` как отдельные команды. Например:

```
$ sudo which poweroff
/usr/sbin/poweroff
$ sudo ls -l /usr/sbin/poweroff
lrwxrwxrwx 1 root root 14 авг 20 07:50 /usr/sbin/poweroff -> /bin/systemctl
```
{% endhint %}

Не все действия по обслуживанию требуют отключения или перезапуска системы. Однако, когда необходимо перевести систему в однопользовательский режим, важно предупредить вошедших в систему пользователей, чтобы они не пострадали от внезапного завершения работы.

Подобно тому, что делает команда `shutdown` при выключении или перезагрузке системы, команда `wall` может отправлять сообщения в сеансы терминала всех вошедших в систему пользователей. Для этого системному администратору нужно только предоставить файл или напрямую ввести сообщение в качестве параметра команды `wall`.

## Краткие сведения <a href="#sec.101.3_01-su" id="sec.101.3_01-su"></a>

В этом уроке рассматриваются основные утилиты, используемые в качестве менеджеров служб в дистрибутивах Linux. Утилиты SysVinit, systemd и Upstart используют разные подходы к управлению системными службами и состояниями системы. В уроке рассматриваются следующие темы:

* Что такое системные службы и их роль в операционной системе.
* Концепции и основы использования команд SysVinit, systemd и Upstart.
* Как правильно запускать, останавливать и перезапускать системные службы и саму систему.

Были рассмотрены следующие команды и процедуры:

* Команды и файлы, связанные с SysVinit, такие как `init`, `/etc/inittab` и `telinit`.
* Основная команда systemd: `systemctl`.
* Команды upstart: `initctl`, `status`, `start`, `stop`.
* Традиционные команды управления питанием, такие как `shutdown` и `wall`.

## Ответы на упражнения с руководством <a href="#sec.101.3_01-age" id="sec.101.3_01-age"></a>

1.  Как можно использовать команду `telinit` для перезагрузки системы?

    Команда `telinit 6` будет переключена на уровень выполнения 6, то есть на перезагрузку системы.
2.  Что произойдёт со службами, связанными с файлом `/etc/rc1.d/K90network`, когда система перейдёт в режим работы 1?

    Из-за буквы `K` в начале имени файла связанные с ним службы будут остановлены.
3.  Используя command `systemctl`, как пользователь может проверить, работает ли устройство `sshd.service`?

    С помощью команды `systemctl status sshd.service` или `systemctl is-active sshd.service`.
4.  В системе на базе systemd, какую команду необходимо выполнить, чтобы активировать модуль `sshd.service` во время инициализации системы?

    Команда `systemctl enable sshd.service`, выполняемая пользователем root.

### Ответы на исследовательские упражнения <a href="#sec.101.3_01-aee" id="sec.101.3_01-aee"></a>

1.  Предположим, что в системе на базе SysV уровень выполнения по умолчанию, заданный в `/etc/inittab` равен 3, но система всегда запускается с уровнем выполнения 1. В чём может быть причина этого?

    Параметры `1` или `S` могут присутствовать в списке параметров ядра.
2.  Хотя файл `/sbin/init` можно найти в системах на базе systemd, это всего лишь символическая ссылка на другой исполняемый файл. В таких системах на какой файл указывает `/sbin/init`?

    Основной двоичный файл systemd: `/lib/systemd/systemd`.
3.  Как можно проверить целевую систему по умолчанию в системе на базе systemd?

    Символическая ссылка `/etc/systemd/system/default.target` будет указывать на файл модуля, заданный в качестве цели по умолчанию. Также можно использовать команду `systemctl get-default`.
4.  Как можно отменить перезагрузку системы, запланированную с помощью команды `shutdown`?

    Следует использовать команду `shutdown -c`.
