# 1.2. Урок 1

## Введение <a href="#sec.101.2_01-in" id="sec.101.2_01-in"></a>

Чтобы управлять компьютером, основной компонент операционной системы — ядро — должен быть загружен программой, называемой _загрузчиком_, которая, в свою очередь, загружается предустановленной прошивкой, такой как BIOS или UEFI. Загрузчик можно настроить так, чтобы он передавал ядру параметры, например, какой раздел содержит корневую файловую систему или в каком режиме должна выполняться операционная система. После загрузки ядро продолжает процесс загрузки, определяя и настраивая оборудование. Наконец, ядро вызывает утилиту, отвечающую за запуск и управление системными службами.

{% hint style="info" %}
В некоторых дистрибутивах Linux для команд, выполняемых в этом уроке, могут потребоваться права root.
{% endhint %}

## BIOS или UEFI <a href="#sec.101.2_01-bu" id="sec.101.2_01-bu"></a>

Процедуры, выполняемые компьютерами с архитектурой x86 для запуска загрузчика, различаются в зависимости от того, используют ли они BIOS или UEFI. BIOS, сокращение от _базовой системы ввода-вывода Basic Input/Output System_, — это программа, хранящаяся в микросхеме энергонезависимой памяти, подключённой к материнской плате, которая выполняется при каждом включении компьютера. Этот тип программы называется _прошивкой_, и её хранилище отделено от других устройств хранения данных, которые могут быть в системе. BIOS предполагает, что первые 440 байт на первом запоминающем устройстве — в порядке, заданном в утилите настройки BIOS, — являются первым этапом загрузчика (также называемого _bootstrap_). Первые 512 байт запоминающего устройства называются MBR (_главная загрузочная запись Master Boot Record_)) и, помимо первого этапа загрузчика, содержат таблицу разделов. Если MBR не содержит корректных данных, система не сможет загрузиться, если не будет использован альтернативный метод.

В целом, для загрузки системы, оснащенной BIOS, необходимо выполнить следующие действия:

1. Процесс POST (_самотестирование при включении питания power-on self-test_) выполняется для выявления простых аппаратных сбоев сразу после включения устройства.
2. BIOS активирует основные компоненты для загрузки системы, такие как видеовыход, клавиатура и накопители.
3. BIOS загружает первую ступень загрузчика из MBR (первые 440 байт первого устройства, как указано в утилите настройки BIOS).
4. Первый этап загрузчика вызывает второй этап загрузчика, отвечающий за представление вариантов загрузки и загрузку ядра.

UEFI, сокращение от _Unified Extensible Firmware Interface_, отличается от BIOS в некоторых ключевых моментах. Как и BIOS, UEFI — это встроенное ПО, но оно может распознавать разделы и считывать многие файловые системы, которые в них находятся. UEFI не полагается на MBR, а учитывает только настройки, хранящиеся в энергонезависимой памяти (_NVRAM_), подключённой к материнской плате. Эти настройки указывают расположение программ, совместимых с UEFI, называемых _приложениями EFI_, которые будут выполняться автоматически или вызываться из меню загрузки. Приложениями EFI могут быть загрузчики, средства выбора операционной системы, инструменты для диагностики и ремонта системы и т.д. Они должны находиться в обычном разделе устройства хранения данных и в совместимой файловой системе. Стандартными совместимыми файловыми системами являются FAT12, FAT16 и FAT32 для блочных устройств и ISO-9660 для оптических носителей. Такой подход позволяет реализовать гораздо более сложные инструменты, чем те, которые возможны с BIOS.

Раздел, содержащий приложения EFI, называется _системным разделом EFI EFI System Partition_ или просто ESP. Этот раздел не должен использоваться совместно с другими системными файловыми системами, такими как корневая файловая система или файловые системы пользовательских данных. Каталог EFI в разделе ESP содержит приложения, на которые указывают записи, сохранённые в NVRAM.

В целом, этапы загрузки системы с UEFI до запуска операционной системы выглядят следующим образом:

1. Процесс POST (_самотестирование при включении питания power-on self-test_) выполняется для выявления простых аппаратных сбоев сразу после включения устройства.
2. UEFI активирует основные компоненты для загрузки системы, такие как видеовыход, клавиатура и накопители.
3. Прошивка UEFI считывает определения, хранящиеся в NVRAM, для выполнения заранее заданного приложения EFI, хранящегося в файловой системе раздела ESP. Обычно заранее заданным приложением EFI является загрузчик.
4. Если предварительно заданное приложение EFI является загрузчиком, оно загрузит ядро для запуска операционной системы.

Стандарт UEFI также поддерживает функцию _безопасной загрузки_, которая позволяет запускать только подписанные приложения EFI, то есть приложения EFI, одобренные производителем оборудования. Эта функция повышает защиту от вредоносного программного обеспечения, но может затруднить установку операционных систем, на которые не распространяется гарантия производителя.

## Загрузчик <a href="#sec.101.2_01-bl" id="sec.101.2_01-bl"></a>

Самый популярный загрузчик для Linux на архитектуре x86 — это GRUB (_Grand Unified Bootloader_). Как только он вызывается BIOS или UEFI, GRUB отображает список доступных для загрузки операционных систем. Иногда список не отображается автоматически, но его можно вызвать, нажав Shift во время вызова GRUB BIOS. В системах UEFI вместо этого следует использовать клавишу Esc.

В меню GRUB можно выбрать, какое из установленных ядер следует загрузить, и передать ему новые параметры. Большинство параметров ядра имеют формат `option=value`. Вот некоторые из наиболее полезных параметров ядра:

`acpi`

Включает/отключает поддержку ACPI. `acpi=off` отключит поддержку ACPI.

`init`

Устанавливает альтернативный системный инициатор. Например, `init=/bin/bash` установит оболочку Bash в качестве инициатора. Это означает, что сеанс оболочки запустится сразу после загрузки ядра.

`systemd.unit`

Задаёт целевую систему _systemd_ для активации. Например, `systemd.unit=graphical.target`. Systemd также поддерживает числовые уровни запуска, определённые для _SysV_. Например, чтобы активировать уровень запуска 1, достаточно указать число `1` или букву `S` (сокращение от «single») в качестве параметра ядра.

`mem`

Задаёт объём доступной оперативной памяти для системы. Этот параметр полезен для виртуальных машин, так как позволяет ограничить объём оперативной памяти, доступной для каждого гостя. Использование `mem=512M` ограничит объём оперативной памяти, доступной для конкретной гостевой системы, до 512 мегабайт.

`maxcpus`

Ограничивает количество процессоров (или ядер процессора), доступных системе на симметричных многопроцессорных машинах. Это также полезно для виртуальных машин. Значение `0` отключает поддержку многопроцессорных машин и имеет тот же эффект, что и параметр ядра `nosmp`. Параметр `maxcpus=2` ограничивает количество процессоров, доступных операционной системе, двумя.

`quiet`

Скрывает большинство загрузочных сообщений.

`vga`

Выберите режим видео. Параметр `vga=ask` отобразит список доступных режимов для выбора.

`root`

Устанавливает корневой раздел, отличный от того, который предварительно настроен в загрузчике. Например, `root=/dev/sda3`.

`rootflags`

Параметры монтирования для корневой файловой системы.

`ro`

Делает начальное монтирование корневой файловой системы доступным только для чтения.

`rw`

Позволяет выполнять запись в корневую файловую систему во время первоначального монтирования.

Изменение параметров ядра обычно не требуется, но может быть полезно для выявления и решения проблем, связанных с операционной системой. Параметры ядра необходимо добавить в файл `/etc/default/grub` в строке `GRUB_CMDLINE_LINUX`, чтобы они сохранялись при перезагрузке. Каждый раз при изменении `/etc/default/grub` необходимо создавать новый файл конфигурации загрузчика с помощью команды `grub-mkconfig -o /boot/grub/grub.cfg`. После запуска операционной системы параметры ядра, используемые для загрузки текущего сеанса, доступны для чтения в файле `/proc/cmdline`.

{% hint style="info" %}
Настройка GRUB будет подробно рассмотрена в следующем уроке.
{% endhint %}

## Инициализация системы <a href="#sec.101.2_01-si" id="sec.101.2_01-si"></a>

Помимо ядра, операционная система зависит от других компонентов, которые обеспечивают ожидаемые функции. Многие из этих компонентов загружаются в процессе инициализации системы и варьируются от простых сценариев оболочки до более сложных служебных программ. Скрипты часто используются для выполнения кратковременных задач, которые запускаются и завершаются в процессе инициализации системы. Службы, также известные как _демоны_, могут быть активны постоянно, поскольку они могут отвечать за внутренние аспекты операционной системы.

Существует огромное разнообразие способов, с помощью которых в дистрибутив Linux можно встроить скрипты запуска и демоны с самыми разными характеристиками. Этот факт исторически препятствовал разработке единого решения, которое соответствовало бы ожиданиям разработчиков и пользователей всех дистрибутивов Linux. Однако любой инструмент, выбранный разработчиками дистрибутива для выполнения этой функции, по крайней мере, сможет запускать, останавливать и перезапускать системные службы. Эти действия часто выполняются самой системой, например, после обновления программного обеспечения, но системному администратору почти всегда приходится вручную перезапускать службу после внесения изменений в файл конфигурации.

Системному администратору также удобно иметь возможность активировать определённый набор демонов в зависимости от обстоятельств. Например, можно запустить только минимальный набор служб для выполнения задач по обслуживанию системы.\


{% hint style="info" %}
Строго говоря, операционная система — это просто ядро и его компоненты, которые управляют аппаратным обеспечением и всеми процессами. Однако термин «операционная система» часто используется в более широком смысле для обозначения целой группы отдельных программ, которые составляют программную среду, в которой пользователь может выполнять основные вычислительные задачи.
{% endhint %}

Инициализация операционной системы начинается, когда загрузчик загружает ядро в оперативную память. Затем ядро берёт на себя управление центральным процессором и начинает определять и настраивать основные аспекты операционной системы, такие как базовая конфигурация оборудования и адресация памяти.

Затем ядро откроет _initramfs_ (_начальную файловую систему RAM initial RAM filesystem_). Initramfs — это архив, содержащий файловую систему, которая используется в качестве временной корневой файловой системы во время загрузки. Основная цель файла initramfs — предоставить необходимые модули, чтобы ядро могло получить доступ к «реальной» корневой файловой системе операционной системы.

Как только корневая файловая система станет доступной, ядро смонтирует все файловые системы, настроенные в `/etc/fstab`, а затем запустит первую программу — утилиту под названием `init`. Программа `init` отвечает за запуск всех сценариев инициализации и системных демонов. Помимо традиционного init существуют другие реализации таких системных инициализаторов, например _systemd_ и _Upstart_. После загрузки программы init initramfs удаляется из оперативной памяти.

SysV

Менеджер служб, основанный на стандарте SysVinit, управляет тем, какие демоны и ресурсы будут доступны, используя концепцию _уровней запуска_. Уровни запуска пронумерованы от 0 до 6 и разработаны разработчиками дистрибутивов для конкретных целей. Единственными общими для всех дистрибутивов уровнями запуска являются уровни 0, 1 и 6.

systemd

systemd — это современный менеджер системы и сервисов с уровнем совместимости с командами и уровнями выполнения SysV. systemd имеет параллельную структуру, использует сокеты и D-Bus для активации сервисов, запуска демонов по требованию, мониторинга процессов с помощью _cgroups_, поддержки моментальных снимков, восстановления системных сеансов, управления точками монтирования и управления сервисами на основе зависимостей. В последние годы большинство основных дистрибутивов Linux постепенно перешли на systemd в качестве системного менеджера по умолчанию.

Upstart

Как и systemd, Upstart является заменой init. Основная задача Upstart — ускорить процесс загрузки за счёт параллельной загрузки системных служб. Upstart использовался в дистрибутивах на основе Ubuntu в предыдущих версиях, но сегодня уступил место systemd.

## Проверка инициализации <a href="#sec.101.2_01-ii" id="sec.101.2_01-ii"></a>

Ошибки могут возникать в процессе загрузки, но они могут быть не настолько критичными, чтобы полностью остановить работу операционной системы. Тем не менее, эти ошибки могут повлиять на ожидаемое поведение системы. Все ошибки приводят к появлению сообщений, которые можно использовать для будущих исследований, поскольку они содержат ценную информацию о том, когда и как произошла ошибка. Даже если сообщения об ошибках не появляются, информация, собранная в процессе загрузки, может быть полезна для настройки и конфигурирования.

Пространство памяти, в котором ядро хранит свои сообщения, в том числе сообщения о загрузке, называется _буфером кольцевого буфера ядра kernel ring buffer_. Сообщения хранятся в _kernel ring buffer_, даже если они не отображаются во время процесса инициализации, например, когда вместо них отображается анимация. Однако _kernel ring buffer_ теряет все сообщения при выключении системы или выполнении команды `dmesg --clear`. Без параметров команда `dmesg` отображает текущие сообщения в _kernel ring buffer_:

Команда `journalctl --list-boots` показывает список номеров загрузок относительно текущей загрузки, их идентификационный хэш и временные метки первого и последнего соответствующих сообщений:

## Ответы на упражнения с руководством <a href="#sec.101.2_01-age" id="sec.101.2_01-age"></a>

1.  Где находится двоичный файл начальной загрузки на компьютере с прошивкой BIOS?

    В MBR первого запоминающего устройства, как указано в утилите настройки BIOS.
2.  Встроенная прошивка UEFI поддерживает расширенные функции, предоставляемые внешними программами, которые называются приложениями EFI. Однако эти приложения имеют собственное специальное расположение. Где в системе будут находиться приложения EFI?

    Приложения EFI хранятся в системном разделе EFI (ESP), расположенном в любом доступном блоке памяти с совместимой файловой системой (обычно это файловая система FAT32).
3.  Загрузчики позволяют передавать пользовательские параметры ядра перед его загрузкой. Предположим, что система не может загрузиться из-за неверного указания местоположения корневой файловой системы. Как передать правильную корневую файловую систему, расположенную по адресу `/dev/sda3`, в качестве параметра ядра?

    Параметр `root` следует использовать, как в `root=/dev/sda3`.
4.  Процесс загрузки компьютера с Linux завершается следующим сообщением:

    ```sh
    ALERT! /dev/sda3 does not exist. Dropping to a shell!
    ```

    Какова вероятная причина этой проблемы?

    Ядру не удалось найти устройство `/dev/sda3`, указанное как корневая файловая система.

## Ответы на исследовательские упражнения <a href="#sec.101.2_01-aee" id="sec.101.2_01-aee"></a>

1.  Если на компьютере установлено несколько операционных систем, загрузчик представит список операционных систем для выбора. Однако недавно установленная операционная система может перезаписать MBR на жёстком диске, стерев первую ступень загрузчика и сделав недоступной другую операционную систему. Почему этого не происходит на компьютере с прошивкой UEFI?

    Компьютеры с UEFI не используют MBR жёсткого диска для хранения первой стадии загрузчика.
2.  Каковы типичные последствия установки пользовательского ядра без соответствующего образа initramfs?

    Корневая файловая система может быть недоступна, если она была скомпилирована как внешний модуль ядра.
3.  Журнал инициализации состоит из сотен строк, поэтому вывод команды `dmesg` часто перенаправляется в команду пейджера — например, команду `less` — для удобства чтения. Какая опция `dmesg` автоматически разбивает вывод на страницы, избавляя от необходимости явно использовать команду пейджера?

    Команды `dmesg -H` или `dmesg --human` активируют пейджер по умолчанию.
4.  Жесткий диск, содержащий всю файловую систему отключенного компьютера, был извлечен и подключен к работающему компьютеру в качестве дополнительного диска. Если предположить, что его точка монтирования — `/mnt/hd`, то как можно использовать `journalctl` для просмотра содержимого файлов журнала, расположенных по адресу `/mnt/hd/var/log/journal/`?

    С помощью команд `journalctl -D /mnt/hd/var/log/journal` или `journalctl --directory=/mnt/hd/var/log/journal`
