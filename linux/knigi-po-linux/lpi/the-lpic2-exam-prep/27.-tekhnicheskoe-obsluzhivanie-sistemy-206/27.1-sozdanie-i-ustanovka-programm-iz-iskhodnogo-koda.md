# 27.1 Создание и установка программ из исходного кода

Кандидаты должны уметь создавать и устанавливать исполняемую программу из исходного кода. Эта задача включает в себя умение распаковывать файл с исходным кодом.

### **Ключевые области знаний**

* Распаковать исходный код с помощью обычных утилит сжатия и архивирования
* Понимать основы вызова make для компиляции программ
* Применение параметров к сценарию настройки
* Знать, где хранятся исходники по умолчанию

## **Термины и утилиты**

## **Распаковка исходного кода**

Большинство программ с открытым исходным кодом распространяются в виде сжатых архивов, содержащих исходный код и сценарии сборки для компиляции и установки программы. Желательно, чтобы исходный код извлекался и компилировался в `/usr/src/` но подойдёт любое другое место.

Эти архивы обычно сжимаются с помощью gzip, bzip2 или xz. GNU tar поддерживает эти форматы сжатия и позволяет легко распаковывать такие файлы. Например, чтобы распаковать архив, сжатый с помощью gzip:

```bash
 $ tar zxvf /path/to/tarball.tar.gz
```

Опция `z` указывает tar использовать алгоритм gzip, а `x`опция указывает tar извлечь файл. Чтобы извлечь сжатый файл bzip2, используйте `j` &#x20;

```bash
$ tar jxvf /path/to/tarball.tar.bz2
```

Чтобы распаковать сжатый файл xz, используйте опцию `J` GNU tar:

```bash
$ tar Jxvf /path/to/tarball.tar.xz
```

Хотя GNU tar поддерживает эти алгоритмы сжатия, некоторые другие реализации tar их не поддерживают. Чтобы извлечь сжатые архивы на компьютерах с такими реализациями tar, сначала нужно распаковать файл, а затем извлечь содержимое.

Для архива, сжатого в gzip формате:

```bash
$ gunzip /path/to/tarball.tar.gz
```

Для файла архива, сжатого в bzip2:

```bash
 $ bunzip2 /path/to/tarball.tar.bz2
```

xz Для файла со сжатым архивом xz:

```bash
  $ unxz /path/to/tarball.tar.xz
```

В качестве альтернативы вы также можете использовать аргумент «-d» (распаковать) для команд `gzip`, `bzip2` и `xz`.

После распаковки вы можете извлечь содержимое, вызвав команду tar без указания аргумента сжатия:

```bash
  $ tar xvf /path/to/tarball.tar
```

#### Дополнительные заметки:

1. **Скорость vs. Сжатие**:
   * `gzip` — быстрее всех, но хуже сжимает.
   * `bzip2` — медленнее gzip, но лучше сжимает (особенно тексты).
   * `xz` — самое медленное, но максимальное сжатие (часто используется для дистрибутивов Linux).
2.  **Совместимость**:

    * `.gz` поддерживается везде, `.bz2` и `.xz` — менее распространены в старых системах

    **Потоки (xz)**:

    * Например, `xz -T4 file` — использовать 4 потока для сжатия.

### **Создание и установка программ из исходных кодов**

Как вы знаете, в любом современном дистрибутиве Linux есть собственный репозиторий, в котором мы можем легко найти программу, получить информацию о ней и установить её. Хотя установка программы из репозитория проста и обеспечивает определённую безопасность, она ограничивает доступ к исходному коду программы конкретным дистрибутивом. Поэтому многие разработчики предпочитают публиковать исходный код программы и позволять другим людям настраивать и компилировать её в соответствии со своим дистрибутивом и потребностями.

Команда `./configure` проверит наличие как дополнительных, так и обязательных зависимостей. Она также адаптирует исходный код к целевой системе (учитывая архитектуру системы, установленные библиотеки, флаги компилятора, каталоги установки и т. д.). Если дополнительная зависимость отсутствует, она отключит компиляцию для этой зависимости. В случае отсутствия обязательных зависимостей она выведет сообщение об ошибке и завершит работу.

Команда configure также генерирует файлы Makefile, которые `make` используются для компиляции и установки программного обеспечения. Файл `Makefile` обычно содержит несколько «целей сборки», которые можно вызвать, передав их в качестве аргумента команде make. Часто используемые цели включают «all», которая обычно является действием по умолчанию, «clean» для очистки (удаления) скомпилированных объектных файлов из исходного кода и «install» для установки программного обеспечения после этапа сборки.

Компилируем программу:

```
make -j$(nproc)
```

И проверяем


Копируем бинарник в систему:

```
sudo make install
```

### Патчинг&#x20;

Хотим, чтобы `nano` при запуске писал `"Hello from patched nano!"`&#x20;

Находим функцию `main(...` и добавляем в начало

```bash
printf("Hello from patched nano!\n");
```

Затем

```bash
make clean      # Удаляем предыдущую сборку
make -j$(nproc) # Компилируем заново
sudo make install
```

**Используя patch**

```
cp src/nano.c src/nano.c.orig
Редактируем
nano src/nano.c
В функцию main
    printf(_("Hello from PPP patched nano!\n"));
```

Создаем патч-файл:

```bash
pirog@pirog:/opt/nano-7.2$ diff -u src/nano.c.orig src/nano.c > nano-mod.patch

```

Применяем патч:

```bash
pirog@pirog:/opt/nano-7.2$ patch -p1 < nano-mod.patch
```

```
./configure --prefix=/usr/local
make -j$(nproc)
sudo make install

```

Проверяем:

```
pirog@pirog:~$ nano
Hello from PPP patched nano!
```

```
patch -R -p1 < nano-mod.patch  # Откат патча
make clean && make && sudo make install
```

### **В исходниках которые вы скачали нет configure?**

Всегда читайте Readme который идёт с исходниками.

Это может быть Autotools-проект без предсгенерированного configure.

* Есть `configure.ac`, но нет `configure`

```
autoreconf -ivf  # генерирует configure
./configure
```

**Проект не использует autotools/cmake**

Некоторые проекты работают с другими системами сборки:

*   **Чистый Makefile**:\
    Если разработчик написал `Makefile` вручную, файл `.config` не нужен.\
    Пример:

    bashCopy

    ```
    wget https://example.com/project.tar.gz
    tar -xzf project.tar.gz
    cd project
    make  # Сразу собирает без конфигурации
    ```
*   **Языковые пакетные менеджеры** (Go, Rust, Python):\
    Например, в Go-проектах сборка выполняется через:

    bashCopy

    ```
    go build
    ```

    Без этапа конфигурации.

**Современные альтернативы Autotools:**

*   **CMake**: Вместо `configure` есть `CMakeLists.txt`

    ```
    mkdir build && cd build
    cmake ..  # аналог ./configure
    make
    ```

    _Примеры: FFmpeg, KDE-приложения_
*   **Meson**: Файл `meson.build`

    ```
    meson setup builddir
    ninja -C builddir
    ```

### **Сравнение систем сборки**

| Характеристика           | Autotools          | CMake                | Meson                     |
| ------------------------ | ------------------ | -------------------- | ------------------------- |
| **Конфигурация**         | `./configure`      | `cmake`              | `meson setup`             |
| **Язык**                 | Shell + M4         | CMakeLists.txt (DSL) | Meson.build (Python-like) |
| **Скорость**             | Медленная          | Быстрая              | Очень быстрая (Ninja)     |
| **Кроссплатформенность** | UNIX-ориентирована | Windows/macOS/Linux  | Windows/macOS/Linux       |
| **Сложность**            | Высокая            | Средняя              | Низкая                    |
| **Популярность**         | Устаревает         | Стандарт для C++     | Набирает популярность     |

### **Сборка проектов**

#### **CMake (Пример: сборка FFmpeg)**

```
# 1. Скачиваем исходники
git clone https://github.com/FFmpeg/FFmpeg.git
cd FFmpeg

# 2. Конфигурация
mkdir build && cd build
cmake .. -DCMAKE_INSTALL_PREFIX=/usr/local

# 3. Сборка и установка
make -j$(nproc)
sudo make install
```

#### **Meson (Пример: сборка GTK)**

```
# 1. Скачиваем исходники
git clone https://gitlab.gnome.org/GNOME/gtk.git
cd gtk

# 2. Конфигурация
meson setup builddir --prefix=/usr/local
cd builddir

# 3. Сборка и установка
ninja
sudo ninja install
```

#### **Патчинг в CMake-проектах**

1.  **Создаем патч** (пример для изменения кода в `main.c`):

    ```
    cp src/main.c src/main.c.orig
    nano src/main.c  # Вносим изменения
    diff -u src/main.c.orig src/main.c > mypatch.patch
    ```
2.  **Применяем патч**:

    ```
    patch -p1 < mypatch.patch
    ```
3.  **Пересобираем**:



    ```
    cd build
    cmake --build .  # Или make
    ```

#### **Патчинг в Meson-проектах**

1.  **Аналогично создаем патч**:

    ```
    diff -u src/original.c src/modified.c > fix-feature.patch
    ```
2.  **Применяем и пересобираем**:

    ```
    patch -p1 < fix-feature.patch
    cd builddir
    ninja
    ```
