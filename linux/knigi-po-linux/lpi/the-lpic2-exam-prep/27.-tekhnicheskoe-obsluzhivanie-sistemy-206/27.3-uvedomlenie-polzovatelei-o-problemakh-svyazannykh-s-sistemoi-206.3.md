# 27.3 Уведомление пользователей о проблемах, связанных с системой (206.3)

## **Уведомление пользователей о проблемах, связанных с системой**  <a href="#notifying-users-on-system-related-issues-2063" id="notifying-users-on-system-related-issues-2063"></a>

Кандидаты должны уметь уведомлять пользователей о текущих проблемах, связанных с системой.

## **Ключевые области знаний**

* Автоматизация общения с пользователями с помощью сообщений для входа в систему
* Информирование активных пользователей о техническом обслуживании системы

## **Термины и утилиты**

* `/etc/issue`
* `/etc/issue.net`
* `/etc/motd`
* `wall`
* `/sbin/shutdown`
* `/bin/systemctl`

### **Файлы `/etc/issue`, `/etc/issue.net` и `/etc/motd`**  <a href="#the-etcissue-etcissuenet-and-etcmotd-files" id="the-etcissue-etcissuenet-and-etcmotd-files"></a>

Файлы `/etc/issue`, `/etc/issue.net` и `/etc/motd` используются для отправки простых сообщений пользователям, которые входят в систему. `/etc/motd` используется для отображения сообщения после успешной аутентификации пользователя. С другой стороны `/etc/issue`, используется для отправки сообщения пользователю перед входом в систему. Это сообщение отображается только пользователям, которые входят в систему с помощью консоли, и часто содержит некоторую информацию о системе, такую как версия ядра и архитектура. Файл `/etc/issue.net` имеет то же назначение, что и `/etc/issue` файл, но используется для небезопасных входов в систему с помощью `telnet`. Можно использовать файл `/etc/issue.net` и для `ssh` . Для этого нужно добавить или изменить следующую строку в `/etc/ssh/sshd_config`:

```
  Banner /etc/issue.net
```

`issue.net`  не поддерживает escape-коды (\n,\r  и т. д.).

```bash
[root@server1 ~]# find /etc/ -name issue.net
/etc/issue.net
[root@server1 ~]# cat /etc/issue.net 
\S
Kernel \r on an \m

[root@server1 ~]# echo "This is from /etc/issue.net" >> /etc/issue.net 
[root@server1 ~]# cat /etc/issue.net 
\S
Kernel \r on an \m
This is from /etc/issue.net

```

Теперь внутри `/etc/ssh/sshd_config` файла нам нужно отредактировать `Banner /some/path` следующее:

```
Banner /etc/issue.net
```

```bash
root@server2:~# ssh root@192.168.10.132
The authenticity of host '192.168.10.132 (192.168.10.132)' can't be established.
ECDSA key fingerprint is SHA256:QtfM2iXh5pxZeFdAUXEBEnRXNSP40MWIhnSYvpOBMoY.
Are you sure you want to continue connecting (yes/no)? yes
Warning: Permanently added '192.168.10.132' (ECDSA) to the list of known hosts.
\S
Kernel \r on an \m
This is from /etc/issue.net
root@192.168.10.132's password:
```

## **wall**

wall отображает сообщение, содержимое файла или стандартный ввод на терминалах всех пользователей, вошедших в систему в данный момент.

```bash
pirog@pirog:~$ sudo wall  "Sorry, $USER, this server will be restarted after 5 min, please stop important processes and save needed file cnages"
                                                                               
Broadcast message from root@pirog (pts/2) (Tue Apr 22 16:09:31 2025):          
                                                                               
Sorry, pirog, this server will be restarted after 5 min, please stop important 
processes and save needed file cnages

```

Команда wall `wall` используется для трансляции сообщения, состоящего не более чем из 22 строк, на все интерактивные терминалы. По умолчанию эту команду может использовать любой пользователь, но часто её перенастраивают так, чтобы её мог использовать только пользователь root. Пользователь, не желающий получать сообщения о трансляции, может использовать `mesg` для отключения своих терминалов от записи. Пользователь, осуществляющий трансляцию, может использовать `finger` для просмотра отключённых от записи терминалов.

С помощью команды `wall` можно указать два параметра: параметр `-n` работает только для пользователя root и само сообщение. Параметр `-n` подавляет стандартный баннер трансляции и заменяет его на баннер удалённой трансляции. Этот параметр имеет смысл только при использовании `wall` поверх демона `rpc.walld` . Второй аргумент, само сообщение, также можно ввести с помощью `stdin`, в этом случае оно должно заканчиваться символом EOF (конец файла, в большинстве случаев \[Ctrl+D]

**Shutdown**

Команды `shutdown` и `reboot` по умолчанию отправляют сообщение через `wall`.

```bash
# Shut down in 10 minutes with a warning
sudo shutdown -h +10 "Server maintenance in 10 minutes. Save your work!"

# Immediate reboot with a custom message
sudo shutdown -r now "Emergency reboot! All sessions will be terminated."
```

&#x20;**Настройка `shutdown`-хуков (systemd)**

```bash
sudo nano /etc/systemd/system/shutdown-notify.service
```

```
[Unit]
Description=Send notification before shutdown
DefaultDependencies=no
Before=shutdown.target reboot.target

[Service]
Type=oneshot
ExecStart=/usr/local/bin/shutdown-notify.sh

[Install]
WantedBy=shutdown.target reboot.target
```

```
sudo nano /usr/local/bin/shutdown-notify.sh
```

```bash
#!/bin/bash
wall "Server shutting down! All sessions will be closed."
logger "System shutdown initiated"
# Add extra actions (e.g., email alerts, API calls)
```

**Systemctl**&#x20;

systemctl — это  центральный инструмент управления системой инициализации systemd. `systemctl` может использоваться для управления службами, состояниями системы (уровнями запуска) и файлами конфигурации.

**Управление службами**

**Запуск и остановка служб**

Там, где вы использовали команду `service` в sysVinit, теперь вы будете использовать команду systemctl для управления службами. Если вы используете команду от имени пользователя, не являющегося пользователем root, вам придется использовать sudo. В следующем примере показано, как запустить службу с помощью команды `start`&#x20;

```bash
    $ systemctl start application.service
```

Поскольку systemd знает, что вы запускаете команды управления системой для сервисов, вы также можете оставить суффикс .service. Для ясности мы будем использовать суффикс в командах.

```
$ systemctl start application
```

Для некоторых программ можно запустить приложение несколько раз с разными файлами конфигурации. В этом случае вы можете передать имя файла конфигурации в команду с помощью @. Например, чтобы запустить службу OpenVPN дважды с разными файлами конфигурации, вы можете использовать следующие команды:

```
    $ systemctl start openvpn@config1.service
    $ systemctl start openvpn@config2.service
```

Вы также можете запускать и останавливать несколько служб одновременно. В следующем примере показано, как остановить несколько служб с помощью `stop` команды:

```
    $ systemctl stop application1.service application2.service
```

**Перезапуск и перезагрузка служб**

Для перезапуска службы вы можете использовать `restart` :

```
$ systemctl restart application.service
```

Если приложение способно перезагрузить свою конфигурацию, вы также можете использовать команду `reload`:

```
 $ systemctl reload application.server
```



Если вы не уверены, что служба может перезагрузить свою конфигурацию, вы также можете использовать `reload-or-restart` команду. Это позволит перезагрузить конфигурацию, если она доступна, в противном случае приложение будет перезапущено:

```
 $ systemctl reload-or-restart application.service
```



**Включение и выключение сервиса**

Предыдущие команды полезны для запуска и остановки служб в текущем сеансе. Если вы хотите, чтобы служба запускалась при загрузке, для чего в sysVinit используется команда `chkconfig`, вам нужно включить их с помощью `systemctl`:

```
    $ systemctl enable application.service
```

Эта команда создаст символическую ссылку из системной копии файла службы (который обычно находится в /lib/systemd/system или /etc/systemd/system) в каталог, где systemd ищет файлы автозапуска (обычно /etc/systemd/system/some\_target.target.wants). Чтобы отключить запуск службы при загрузке, используйте `disable` :

```
    $ systemctl disable application.service
```

Это приведёт к удалению символической ссылки, указывающей на то, что служба должна запускаться при загрузке.

{% hint style="info" %}
Помните, что включение службы не запустит ее в текущем сеансе. Чтобы запустить и включить службу, вам нужно будет выполнить команды запуска и включения
{% endhint %}

**Проверка состояния служб**

Чтобы проверить текущее состояние службы, вы можете использовать команду  `status` :&#x20;

```
    $ systemctl status application.service
```

Эта команда покажет текущее состояние службы, иерархию cgroup и первые несколько строк журнала. Она дает хорошее представление о текущем состоянии и уведомляет о любых проблемах. Например, следующий вывод для службы sshd:

           Docs: man:sshd(8)
                 man:sshd_config(5)

       Main PID: 1067 (sshd)

Также доступны команды для проверки определённых состояний, которые могут быть особенно полезны для использования в скриптах. Например, чтобы проверить, активна ли служба в данный момент, вы можете использовать команду `is-active`:

```
    $ systemctl is-active application.service
```

Эта команда отображается, если приложение активно или неактивно. Если приложение активно он будет возвращать код завершения "0". Чтобы увидеть, если в приложение будет активировано, вы можете использовать `is-enabled` команда:

```
    $ systemctl is-enabled application.service
```

Эта команда вернет значение, указывающее, включено или отключено приложение, и вернет код завершения «0», если приложение включено. Чтобы проверить, несбойно ли работает приложение, вы можете использовать `is-failed` команду:

```
    $ systemctl is-failed application.service
```

Эта команда вернет значение «активно», если приложение запущено, «неудачно», если произошла ошибка, и «неактивно» или «неизвестно», если служба была намеренно остановлена. Она вернет код завершения «0», если служба не работает.

**Обзор состояния системы**

До сих пор эти команды были полезны для управления отдельными службами. Для изучения текущего состояния системы существует ряд команд systemctl, которые предоставляют больше информации.

**list-units**

Чтобы получить список всех активных модулей, о которых знает systemd, вы можете использовать `list-units` команду:

```
$ systemctl list-units
```

Эта команда показывает только список активных в данный момент устройств. Затем выводятся следующие столбцы:

```bash
  UNIT: The systemd unit name
    LOAD: Whether the unit's configuration has been parsed by systemd. The
          configuration of loaded units is kept in memory.
    ACTIVE: A summary state about whether the unit is active. This is usually a
            fairly basic way to tell if the unit has started successfully or not.
    SUB: This is a lower-level state that indicates more detailed information
         about the unit This often varies by unit type, state, and the actual
         method in which the unit runs.
    DESCRIPTION: A short textual description of what the unit is/does/
```

Поскольку команда `list-units` по умолчанию отображает только активные юниты, все приведенные выше записи будут отображать "LOAD" и " "ACTIVE " . Это также поведение systemctl при вызове без дополнительных команд, поэтому вы увидите тот же результат, если вы вызовете systemctl без аргументов.

```
$ systemcl
```

Вы также можете указать systemctl выводить различную информацию, добавив дополнительные флаги. Например, чтобы отобразить все модули, загруженные systemd, независимо от того, активны они или нет, вы можете использовать `--all` :

```
    $ systemctl list-units --all
```

При этом будут показаны все устройства, которые systemd загрузил или пытался загрузить, независимо от их текущего состояния в системе. Также возможно фильтровать устройства по текущему состоянию, для этого вы можете использовать `--state=` .&#x20;

```
    $ systemctl list-units --all --state=inactive
```

Другой фильтр, который вы можете использовать, — это `--type=` флаг. Вы можете указать systemctl отображать только интересующие вас типы модулей. Например, чтобы отображать только активные модули, вы можете использовать следующую команду:

```
    $ systemctl list-units --type=service
```

Можно посмотреть зависимости юнита.

```
systemctl list-dependencies <unit>
```
