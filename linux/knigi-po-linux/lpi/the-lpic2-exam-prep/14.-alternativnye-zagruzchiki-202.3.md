### 14.1.3 LILO

Загрузчик  LILO состоит из двух этапов. Во время двухэтапной загрузки LILO отображает ход выполнения, выводя на консоль BIOS последовательные буквы из слова "LILO", по одной букве в начале и в конце каждого этапа.&#x20;

Ошибки на обоих этапах приводят к тому, что печатаются только части слова, за которыми, при необходимости, следует цифровой код ошибки BIOS или один символ. Например, LIL- или LIL? .&#x20;

В интерактивном режиме (запрос ключевого слова в файле /etc/lilo.conf ) LILO предоставляет пользователю на выбор до 16 записей. Если нет если указано timeout=nnn (nnn в десятках секунд), загрузчик будет ждать бесконечно. Если время ожидания истекло или запрос не был включен, LILO продолжит загрузку первого образа из списка. Это можно отменить с помощью ключевого слова default=name.

#### /etc/lilo.conf and /sbin/lilo

За исключением современных загрузчиков, ни один из этапов LILO на самом деле не знает о содержимом файла /etc/lilo.conf . Вместо этого файл используется только как спецификация для установщика LILO, обычно в /sbin/lilo . Без дополнительных настроек /sbin/lilo установит загрузчик в MBR и обработает содержимое /etc/lilo.conf, создав сопоставление любых файлов, указанных для сохранения в / boot/map .

Пожалуйста, обратитесь к справочной странице lilo.conf(5) в Интернете для получения подробного описания /etc/lilo.conf .

Пример /etc/lilo.conf (из более старого дистрибутива debian)

```
# lilo.conf
 #
 # global options:
 boot=/dev/hda
 prompt
 timeout=150
 lba32
 compact
 vga=normal
 root=/dev/hda1
 read-only
 menu-title=" John's Computer "
 #
 # bootable kernel images:
 image=/boot/zImage-1.5.99
 label=try
 image=/boot/zImage-1.0.9
 label=1.0.9
 image=/tamu/vmlinuz
 label=tamu
 initrd=initramdisk.img
 root=/dev/hdb2
 vga=ask
 #
 # other operating systems:
 other=/dev/hda3
 label=dos
 boot-as=0x80 # must be C:
 other=/dev/hdb1
 label=Win98
 boot-as=0x80 # must be C:
 other=/dev/hdb5
 label=os2
 loader=os2_d
 table=E: # os2 sees as E:
```

### 14.1.4 SYSLINUX, ISOLINUX, PXELINUX: Проект Syslinux

SYSLINUX - это загрузчик для Linux, предназначенный для запуска из файловой системы MS-DOS/Windows FAT. Он доступен только на оборудовании Intel/AMD.

Со временем проект Syslinux ([https://syslinux.org)](https://syslinux.org/) расширился, включив поддержку начальной загрузки с компакт-дисков (ISOLINUX), файловых систем Linux (EXTLINUX) и через PXE (PXELINUX).

Это краткое изложение касается конкретных задач LPIC-2. Полное описание можно найти в syslinux wiki по адресу [https://www.syslinux.org/wiki/index.php/SYSLINUX](https://www.syslinux.org/wiki/index.php/SYSLINUX)

#### **SYSLINUX**

SYSLINUX - это загрузчик  Intel Linux, который может загружаться из файловых систем на базе FAT под управлением Windows/MS-DOS. Его можно установить с помощью одноименной команды из Windows, MS-DOS или Linux.

Система syslinux состоит из собственно загрузчика и его установщика. Сам загрузчик представляет собой 32-разрядный двоичный файл, написанный на ассемблере.

Команда установки syslinux доступна в разных версиях: syslinux.exe для Windows, syslinux для Linux. Есть даже команда syslinux.com для систем на базе DOS.

#### **опции установщика SYSLINUX**

```
--offset     -t     Offset of the file system on the device
--directory  -d     Directory for installation target
--install    -i     Install over the current bootsector
--update     -U     Update a previous installationу
--sectors=#  -S     Force the number of sectors per track
--heads=#    -H     Force number of heads
--stupid     -s     Slow, safe and stupid mode
--raid       -r     Fall back to the next device on boot failure
--once=...          Execute a command once upon boot
--clear-once -O     Clear the boot-once command
--reset-adv         Reset auxilliary data
--menu-save= -M     Set the label to select as default on the next boot
--force      -f     Ignore precautions
```

#### **MSDOS опции**

```
-m     MBR: install a bootable MBR sector to the beginning of the drive.
-a     Active: marks the partition used active (=bootable)
```

#### **только для Linux**

```
-t     (-o on older systems) Specifies the byte offset of the filesystem
         image in the file. It has to be used with a disk image file.
```

#### **Исключения для ISOLINUX, EXTLINUX, PXELINUX**

#### &#x20;**ISOLINUX Installer**

В то время как syslinux ожидает, что целевое устройство запишет загрузчик, установщик isolinux генерирует ISO-образ из структуры каталогов. Каталог должен содержать подкаталог isolinux, который, в свою очередь, должен содержать фактический загрузчик isolinux.bin.

#### **EXTLINUX Installer**

Установщик extlinux ожидает, что для установки загрузчика будет установлена смонтированная файловая система.

### **PXELINUX**

is treated in PXELINUX.

#### **Syslinux Boot Configuration**

Загрузчики, установленные с помощью этих утилит, будут искать файл syslinux.cfg в следующих трех каталогах: /boot/syslinux , /syslinux , /(root).&#x20;

Загрузчик ISOLINUX сначала выполнит поиск в /boot/isolinux и /isolinux .&#x20;

Загрузчик EXTLINUX сначала выполнит поиск в /boot/extlinux и /extlinuxx.&#x20;

Каталог, в котором находится конфигурационный файл, будет каталогом по умолчанию для дальнейших указаний путей в процессе загрузки.

&#x20;Ключевое слово CONFIG перезапустит процесс загрузки с новым конфигурационным файлом. Если указаны два пути, второй параметр переопределяет каталог по умолчанию.&#x20;

Процесс загрузки будет искать в файле syslinux.cfg строку с надписью "linux". Когда она будет найдена, она будет использовать все последующие ключевые слова для управления процессом загрузки. (DEFAULT label может использоваться для переопределения метки "linux".)&#x20;

Типичные ключевые слова в конфигурации загрузки:

_**KERNEL image**_

Ключевое слово KERNEL указывает файл образа. Это не обязательно должен быть реальный образ ядра, но может быть именем программы загрузки следующего этапа. Например, в SYSLINUX при выборе формата файла следует руководствоваться расширениями имен файлов.

_.0_

используется с PXELINUX для PXE NBP (программы сетевой загрузки), по умолчанию используется pxelinux.0.

_.bin_

обратитесь к (пропатченым) загрузочным секторам DOS \[SYSLINUX].

.com , .cbt , и .c32

это загрузочные образы COMBOOT (DOS, не-DOS, 32-разрядные). В версиях 5.00 и более поздних c32 изменен с COMBOOT на двоичный формат ELF

.img

это образ диска ISOLINUX.

Любое другое расширение файла (или вообще его отсутствие) указывает на образ ядра Linux..

Тип файла также можно изменить, используя один из псевдонимов  KERNEL: LINUX , BOOT , BSS , PXE , FD IMAGE , COMBOOT или COM32 .

_**APPEND**_&#x20;

Ключевое слово APPEND указывает строку параметров загрузки, которая добавляется в командную строку ядра. Будет применена только последняя строка добавления.

_**SYSAPPEND**_

Ключевое слово SYSAPPEND ожидает числовой аргумент, который интерпретируется как растровое изображение. Каждый бит в этом растровом изображении добавит определенную автоматически сгенерированную строку в командную строку ядра.

1.Добавляет строку с информацией о сети: ip=client:bootserver:gw:netmask

2.Добавляет BOOT IF= ..., идентифицирующий активный сетевой интерфейс по его mac-адресу.

4.Добавляет строку SYS UUID= ...

8.Добавляет CPU= ...

Биты более высокого порядка (от 0x00010 до 0x10000) управляют дополнительными строками из DMI/SMBIOS, если они доступны. Полный список можно найти в Syslinux wiki: [https://www.syslinux.org/wiki/index.php/SYSLINUX ](https://www.syslinux.org/wiki/index.php/SYSLINUX).

_**INITRD filename**_

Ключевое слово INITRD эквивалентно добавлению initrd=filename .

_**TIMEOUT num**_

Для интерактивного использования параметр TIMEOUT указывает количество десятков секунд, в течение которых SYSLINUX должен ожидать ввода данных с консоли или последовательного порта.

### **PXELINUX**

Загрузчик PXELINUX используется в качестве второго этапа сетевой загрузки PXE. Механизм сетевой загрузки PXE более подробно описан в разделе "Общие сведения о PXE".

PXELINUX ожидает стандартный TFTP-сервер с каталогом /tftpboot, содержащим загрузчик pxelinux.0 syslinux и библиотечный модуль ldlinux.c32.

Кроме того, для получения дополнительных сведений о конфигурации должен существовать каталог /tftpboot/pxelinux.cfg.

Загрузочный сервер PXE TFTP может обслуживать множество различных клиентов, и ему необходим способ поддерживать разные файлы конфигурации для разных (категорий) клиентов. Существует множество различных способов указания имени файла конфигурации.

**Объедините опции DHCP 209 и 210**

Опция  209 ( pxelinux.config-file) указывает имя файла конфигурации.

Опция  210 ( pxelinux.pathprefix ) определяет путь поиска (префикс каталога) в пространстве имен сервера TFTP (заканчивается символом-разделителем, определенным для файловой системы).

**Жёсткое кодирование pxelinux.0 image.**

Команда pxelinux-options может быть использована для жесткого кодирования параметров, как показано в этой таблице.

| Номер | Опция               |
| ----- | ------------------- |
| 6     | domain-name-servers |
| 15    | domain-name         |
| 54    | next-server         |
| 209   | config-file         |
| 210   | path-prefix         |
| 211   | reboottime          |

Опции могут быть указаны как "before-options", где DHCP имеет приоритет, или как "after-options", которые переопределяют DHCP.

**Доставка по UUID, MAC, или IP**

Если конфигурационный файл не указан, имя файла берется из списка переменных. Будет использоваться первый файл в списке, который действительно существует на сервере TFTP.&#x20;

Список переменных:&#x20;

UUID клиента, написанный строчными буквами.&#x20;

MAC-адрес клиента, записанный строчными буквами в шестнадцатеричном формате, с байтами, разделенными тире ("-").&#x20;

Максимально длинный префикс шестнадцатеричного представления ipv4-адреса клиента в верхнем регистре. Каждый раз, когда строка не совпадает, PXELINUX удаляет последний символ из строки и повторяет попытку до тех пор, пока результат содержит хотя бы один символ.&#x20;

В качестве последнего средства PXELINUX попытается извлечь файл с именем "default".

### **Понимание PXE**

PXE - это спецификация, созданная Intel для улучшения исходных сетевых протоколов загрузки: BOOTP, TFTP и DHCP.&#x20;

Протоколы BOOTP, RARP и TFTP были созданы IETF для того, чтобы позволить системам автоматически получать конфигурацию сети и начальный загрузчик с сервера.&#x20;

Первоначальный стандарт BOOTP был ограничен несколькими фиксированными полями, в которых клиент и сервер могли обмениваться информацией. Клиент может указать свой аппаратный адрес в `cheddar` и запросить файл определенного типа , после чего получит свой ip-адрес в виде `yiaddr` и имя сервера . В сочетании с полем IP-адреса сервера ( `siaddr` ) и полем IP-адреса шлюза, а также возвращаемым именем загрузочного файла ( file ) это сообщит загрузочному клиенту, где получить его загрузочный образ, используя протокол TFTP.

### **поля BOOTP**&#x20;

```
ciaddr 4     client IP address
yiaddr 4     your IP address
siaddr 4     server IP address
giaddr 4     gateway IP address
chaddr 16    client hardware address
sname  64    optional server host name, null terminated string.
file   128   boot file name, null terminated string;
vend   n     n=64 in original BOOTP, starts with the 4 byte
                DHCP   'magic' number.
```

Со временем сети и ИТ-инфраструктура стали более сложными, а требования - более требовательными. Чтобы клиенты могли предоставлять больше информации о себе и получать индивидуальную информацию, BOOTP получил информацию о поставщике BOOTP Расширения \[RFC 1048], которые, в свою очередь, были дополнены новым протоколом DHCP. DHCP расширил BOOTP с помощью ряда стандартных опций, определяющих различные типы сообщений. Некоторые параметры DHCP могут совпадать со стандартными полями BOOTP и в этом случае должны содержать одно и то же значение.

{% hint style="info" %}
DHCP-сообщение - это BOOTP-пакет (запрос или ответ) со специальным 4-байтовым значением (DHCP magic cookie) в поле BOOTP "Информация о поставщике". Далее следуют параметры DHCP, состоящие из однобайтового типа параметра, поля длины и байт длины содержимого параметра.
{% endhint %}

Из этого правила есть два исключения: параметры заполнения ( 0 ) и окончания ( 255 ) имеют длину всего в один байт и не содержат поля длины.

Наконец, Intel представила PXE, чтобы еще больше усовершенствовать протокол BOOTP/DHCP и стандартизировать способы идентификации клиентов. Это позволяет загрузочным клиентам и серверам свести к минимуму количество пакетов, которыми необходимо обменяться , прежде чем они смогут выбрать правильные параметры и программу загрузки, необходимую для запуска.

Запрос на загрузку по протоколу PXE начинается с сообщения DHCP Discover, содержащего как минимум пять параметров, три из которых относятся к протоколу PXE:

```bash
(53) DHCP Message type (DHCP Discover),
(55) Parameter Request List,
(93) Client System Architecture,
(94) Client Network Device Interface,
(97) UUID/GUID-based Client Identifier
```

Параметры 93, 94 и 97 определены в спецификации PXE. Кроме того, параметр 55, список запросов параметров, также должен запрашивать параметры с 128 по 135, даже если сервер не обязан предоставлять ответ на них. Этот список и три опции, перечисленные выше, помогают идентифицировать клиента как осведомленного о PXE.

### **DHCP-прокси для PXE**

Не каждый DHCP-сервер (особенно встроенный в сетевое оборудование) сможет обработать запрос PXE.&#x20;

Спецификация PXE позволяет DHCP-серверам, поддерживающим PXE, сосуществовать с простыми DHCP-серверами, где DHCP-сервер по умолчанию предоставляет основные сведения о сети.&#x20;

Сервер, поддерживающий PXE, может затем предоставить дополнительные сведения о фактическом процессе загрузки по протоколу TFTP.&#x20;

Это называется прокси-DHCP. Возможно даже разделить службы DHCP на одном сервере, на котором прокси-служба DHCP, как ожидается, будет прослушивать UDP -порт 4011.
