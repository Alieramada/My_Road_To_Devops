### 17.1.3 Проверка дисков

Для надлежащего обслуживания диска требуется периодическая проверка диска. Ваш лучший инструмент - fsck, и его следует запускать не реже одного раза в месяц. Проверки по умолчанию обычно выполняются после 20 перезагрузок системы, но если ваша система не работает в течение нескольких недель или месяцев, вам потребуется время от времени выполнять принудительную проверку. Лучше всего выполнять рутинное резервное копирование системы и время от времени проверять свои потерянные и найденные каталоги .&#x20;

Частоту проверок при перезагрузке системы можно изменить с помощью tune2fs. Эта утилита также может быть использована для изменения настроек tune2fs , что избавит систему от необходимости проверять все файловые системы при 20-й перезагрузке (что может занять много времени).&#x20;

Утилита dumpe2fs предоставит важную информацию о рабочих параметрах жесткого диска, которые находятся в суперблоке, а badblocks выполнит проверку поверхности. Наконец, хирургические процедуры по удалению поврежденных участков диска могут быть выполнены с помощью debugfs .

### **fsck (fsck.\*)**

fsck - это утилита для проверки и восстановления файловой системы fsck Linux. На самом деле fsck - это просто интерфейс для различных средств проверки файловой системы (fsck.fstype), доступных в Linux.

```bash
root@pirog:~# ls /sbin/ | grep 'fsck'
dosfsck
e2fsck
fsck
fsck.cramfs
fsck.ext2
fsck.ext3
fsck.ext4
fsck.fat
fsck.minix
fsck.msdos
fsck.vfat
```



fsck вызывается автоматически при запуске системы. Если файловая система помечена как "не очищенная", или достигнуто максимальное количество монтирований, или\
превышено время между проверками, файловая система проверяется. Чтобы изменить максимальное количество монтирований или время между проверками, используйте tune2fs.

Часто используемые опции fsck включают:

-s

Сериализуйте операции fsck. Это хорошая идея, если вы проверяете несколько файловых систем и средства проверки находятся в интерактивном режиме.

-A

Просмотреть файл /etc/fstab  и попробовать проверить все файловые системы за один запуск. Эта опция обычно используется из файла инициализации системы /etc/rc вместо нескольких команд для проверки одной файловой системы.

Сначала будет проверена корневая файловая система. После этого файловые системы будут проверены в порядке, указанном в поле fs\_pass no (шестом) в файле /etc/fstab. Файловые системы, для которых значение fs\_pass не равно 0, пропускаются и вообще не проверяются. Если имеется несколько файловых систем с одинаковым номером доступа, fsck попытается проверить их параллельно, хотя это позволит избежать выполнения нескольких проверок файловой системы на одном физическом диске.

-R

При проверке всех файловых систем с флагом -A пропустить fsck -R для корневой файловой системы (в случае, если она уже подключена для чтения и записи).

Параметры, которые не понятны fsck, передаются в специфичные средства проверки файловой системы. Эти аргументы(=options) не должны принимать аргументы, поскольку fsck не может правильно определить, какие аргументы принимают параметры, а какие нет. Параметры и аргументы, которые следуют за --, рассматриваются как параметры, зависящие от файловой системы, которые передаются в средство проверки, зависящее от файловой системы.

-a

Этот параметр выполняет те же функции, что и параметр -p. Он предусмотрен только для обеспечения обратной совместимости; рекомендуется использовать параметр -p, когда это возможно.

-c

Эта опция заставляет e2fsck запускать программу fsck-c badblocks(8) для поиска любых поврежденных блоков, которые основаны на файловой системе, а затем помечает их как поврежденные, добавляя в inode поврежденного блока.

-C

Этот параметр заставляет e2fsck записывать информацию о завершении fsck-C в указанный файловый дескриптор, чтобы можно было отслеживать ход проверки файловой системы. Этот параметр обычно используется программами, на которых запущен e2fsck. Если указанный файловый дескриптор равен 0, e2fsck по мере выполнения своей работы будет выводить строку завершения. Для этого требуется, чтобы e2fsck был запущен на видеоконсоли или терминале.

-f

Принудительная проверка, даже если файловая система кажется чистой. fsck-f

-n

Открыть файловую систему только для чтения и применить ответ fsck-n "no" на все вопросы. Позволяет использовать e2fsck неинтерактивно. (Примечание: если в дополнение к параметру -n указаны параметры -c, -l или -L, то файловая система будет открыта для чтения и записи, чтобы\
можно было обновить список неисправных блоков. Однако никакие другие изменения в файловую систему внесены не будут.)

-p

Автоматическое восстановление ("чистка") файловой системы без каких-либо вопросов

-y

Предполагает, ответ "yes" на все вопросы; позволяет использовать fsck-y e2fsck неинтерактивно.

{% hint style="info" %}
Не забывайте, что вы не можете проверить файловую систему, пока она используется, поэтому не забудьте отмонтировать её!!!
{% endhint %}

коды выхода fsck:

```bash
0-No errors
1-Filesystem errors corrected
2-System should be rebooted
4-Filesystem errors left uncorrected
8-Operational error
16-Usage or syntax error
32-Checking canceled by user request
128-Shared-library error
```

### tune2fs

tune2fs используется для "настройки" файловой системы. В основном это используется для настройки параметров проверки файловой системы, таких как максимальное количество подключений и время между проверками файловой системы.

Также можно установить количество монтирований на определенное значение. Это можно использовать для "разбивки" количества монтирований в разных файловых системах, что гарантирует, что при перезагрузке не все файловые системы будут проверены одновременно.

Итак, для системы, которая содержит 5 разделов и загружается примерно раз в месяц, вы могли бы сделать следующее, чтобы увеличить количество монтирований:

```
tune2fs -c 5 -C 0
 partition1
 tune2fs -c 5 -C 1
 partition2
 tune2fs -c 5 -C 2
 partition3
 tune2fs -c 5 -C 3
 partition4
 tune2fs -c 5 -C 4
 partition5
```

Максимальное количество монтирований равно 20, но для системы, которая не часто перезагружается, рекомендуется меньшее значение.

Часто используемые опции включают в себя:

-c max-mount-counts

Отрегулируйте максимальное количество монтирований между двумя проверками файловой системы tunefs-c. Если значение max-mount-counts равно 0, то e2fsck(8) и ядро не будут учитывать количество монтирований файловой системы. Увеличение количества монтирований, при которых\
принудительно проверяются файловые системы, позволит избежать одновременной проверки всех файловых систем при использовании журналируемых файловых систем.

Вам следует серьезно подумать о последствиях полного отключения проверки, зависящей от количества монтирований. Неисправные диски, кабели, память и ошибки ядра - все это может привести к повреждению файловой системы, при этом файловая система не будет помечена как загрязненная или с ошибкой. Если вы используете ведение журнала в своей файловой системе, ваша файловая система никогда не будет помечена как грязная, поэтому обычно она не проверяется. Ошибка файловой системы, обнаруженная ядром, по-прежнему приведет к принудительной перезагрузке fsck при следующей перезагрузке, но в этот момент может быть уже слишком поздно предотвращать потерю данных.

-C mount-count

Задайте количество раз, когда файловая система монтировалась. Если значение параметра больше, чем значение параметра max-mount-counts, заданного параметром -c, e2fsck(8) проверит файловую систему при следующей перезагрузке.

-i interval-between-checks\[d|m|w]

Настройте максимальное время между двумя проверками файловой системы tunefs-i. В днях не указывается суффикс или d,  m - месяцы, а w - недели. Нулевое значение отключит проверку, зависящую от времени.

Настоятельно рекомендуется включить проверку -c (зависящую от количества подключений) или -i (зависящую от времени), чтобы принудительно выполнять периодическую полную проверку файловой системы на e2fsck(8). Несоблюдение этого требования может привести к повреждению файловой системы из-за неисправных дисков, кабелей или памяти, а также к тому, что ошибки ядра останутся незамеченными, пока не приведут к потере или повреждению данных.

-m reserved-blocks-percentage

Установите процент зарезервированных блоков файловой системы.&#x20;

-r reserved-blocks-count

Установите количество зарезервированных блоков файловой системы.&#x20;

### **dumpe2fs**

dumpe2fs показывает информацию обо всех суперблоках. Суперблоки — это своего рода метаданные файловой системы, которые содержат информацию о размере, размере блоков, пустых и заполненных блоках, размере и расположении индексных дескрипторов и многое другое. dumpe2fs можно использовать, пока раздел смонтирован.

-b

-h

Поскольку суперблоки настолько важны, файловая система предназначена для их резервного копирования в нескольких местах на жёстком диске.

### **badblocks**

badblocks - это утилита для Linux, которая проверяет наличие поврежденных секторов на жестком диске. Она помечает эти сектора, чтобы они не использовались в будущем и, следовательно, не приводили к повреждению данных. Она является частью проекта e2fsprogs.

Настоятельно рекомендуется не запускать badblocks напрямую, а вызывать его с помощью параметра -c в e2fsck или mk2fs . Обычно используется следующий параметр:

-o output-file

записать список поврежденных блоков в выходной файл .

### debugfs

С помощью debugfs вы можете изменять диск с помощью прямой записи на диск. Поскольку эта утилита очень мощная, обычно вы хотите использовать ее только для чтения, пока не будете готовы внести изменения и записать их на диск. Чтобы вызвать debugfs в режиме только для чтения,\
не используйте никаких опций. Для открытия в режиме чтения-записи добавьте параметр -w. Вы также можете указать в командной строке устройство, с которым хотите работать, например, /dev/hda1 или /dev/sda1 и т.д. Как только оно будет запущено, вы увидите приглашение debugfs.

Если суперблок раздела поврежден, вы можете указать местоположение суперблока, используя другой суперблок:

```bash
debugfs -b 1024 -s 8193 /dev/hda1
```

Это означает, что будет использоваться суперблок в блоке 8193, а размер блока равен 1024. Обратите внимание, что вам необходимо указать размер блока, если вы хотите использовать другой суперблок. Информацию о размере блока и резервных суперблоках можно найти в:

```bash
dumpe2fs /dev/hda1
```

Первая команда, которую нужно попробовать после вызова debugfs, - это параметры, показывающие режим (только для чтения или записи) и текущую файловую\

### **ext4**

Ext4 - это эволюция наиболее используемой файловой системы Linux, Ext3. Во многих отношениях Ext4 является более глубоким улучшением по сравнению с тем как Ext3 был улучшен по сравнению с Ext2.  В Ext3 в основном речь шла о добавлении журналирования в Ext2, но Ext4 изменяет важные структуры данных файловой системы, например, те, которые предназначены для хранения файловых данных. В результате получилась файловая система с улучшенным дизайном, более высокой производительностью, надежностью и функциональными возможностями. Поэтому преобразование ext3 в ext4 не так просто, как это было при преобразовании ext2 в ext3.

Чтобы создать разделы ext4 с нуля, используйте:

```bash
mkfs.ext4 /dev/sdxY
```

Имейте в виду, что по умолчанию mkfs.ext4 использует довольно низкое соотношение байт на inode для расчета фиксированного количества создаваемых inode.

Особенно для современных жестких дисков (750 ГБ+) это обычно приводит к слишком большому количеству индексных дескрипторов и, следовательно, к потере большого количества ГБ. Соотношение может быть задано непосредственно с помощью опции -i;&#x20;

В остальном с ext4 можно работать, используя все те же инструменты, которые доступны для файловых систем типа ext2/ext3, таких как badblocks,dumpe2fs, e2fsck и tune2fs

### btrfs

Btrfs (аббревиатура от: B Tree File System) - это новая файловая система copy on write (CoW) для Linux, предназначенная для реализации расширенных функций с акцентом на отказоустойчивость, ремонт и простоту администрирования. Программа Btrfs, разработанная совместно компаниями Oracle, Red Hat, Fujitsu, Intel,SUSE, STRATO и многими другими, имеет лицензию GPL и открыта для участия всех желающих. Btrfs обладает рядом особенностей, характерных для устройств хранения данных. Он предназначен для того, чтобы сделать файловую систему устойчивой к ошибкам и облегчить обнаружение и исправлять ошибки при их возникновении. Он использует контрольные суммы для проверки достоверности данных и метаданных и сохраняет снимки файловой системы, которые можно использовать для резервного копирования или восстановления. Основной структурой данных, используемой btrfs, является B-Tree - отсюда и название.

Btrfs все еще находится в стадии интенсивной разработки, но прилагаются все усилия для обеспечения стабильности и быстродействия файловой системы. Из-за\
скорости разработки вам следует использовать самое последнее ядро, какое только возможно (либо ядро последней версии из kernel.org, либо ядро последней версии)

По состоянию на начало 2013 года Btrfs была включена в ядро по умолчанию, а его инструменты (btrfs-progs) являются частью установки по умолчанию. GRUB 2, mkinitcpio и Syslinux поддерживают Btrfs и не требуют дополнительной настройки.

* поддержка SSD (флеш-накопителей) и оптимизации (например, избежание ненужных операций поиска, отправка записей кластерами, даже если они из несвязанных файлов, что приводит к более крупным операциям записи и повышению пропускной способности записи);  \

#### **RAID functionality**

Файловая система Btrfs обеспечивает поддержку встроенных функций RAID и может быть создана поверх многих устройств. После создания файловой системы можно добавить дополнительные устройства. По умолчанию метаданные будут отображаться зеркально на двух устройствах, а данные будут распределены по всем присутствующим устройствам. Если присутствует только одно устройство, метаданные будут дублироваться на этом одном устройстве. Btrfs позволяет добавлять и удалять устройства в режиме онлайн, а также свободно переключаться между уровнями RAID после создания файловой системы.&#x20;

Btrfs поддерживает raid0, raid1, raid10, raid5 и raid6, а также может дублировать метаданные на одном шпинделе. При считывании блоков проверяются контрольные суммы. При возникновении каких-либо ошибок Btrfs попытается выполнить чтение из альтернативной копии и восстановит поврежденную копию, если альтернативная копия будет выполнена успешно.

mkfs.btrfs поддерживает доступ к нескольким устройствам в командной строке. В нем есть опции для управления конфигурацией raid для данных (-d) и метаданных (-m). Допустимыми вариантами являются raid0, raid1, raid10 и single. Опция -m single означает, что не выполняется дублирование\
метаданных, что может быть желательно при использовании аппаратного raid. вот несколько примеров создания файловой системы.

```bash
# Create a filesystem across four drives (metadata mirrored, linear data allocation)
mkfs.btrfs /dev/sdb /dev/sdc /dev/sdd /dev/sde

# Stripe the data without mirroring
mkfs.btrfs -d raid0 /dev/sdb /dev/sdc

# Use raid10 for both data and metadata

mkfs.btrfs -m raid10 -d raid10 /dev/sdb /dev/sdc /dev/sdd /dev/sde

# Don't duplicate metadata on a single drive (default on single SSDs)
mkfs.btrfs -m single /dev/sdb
```

После создания файловой системы ее можно смонтировать как любую другую файловую систему. Чтобы просмотреть устройства, используемые файловой системой, вы можете использовать\
следующую команду:

```bash

total devices 2 FS bytes used 383.00KiB

```

#### **Snapshotting**

Программа snapshotting Btrfs проста в использовании и понимании. Снимки будут отображаться как обычные каталоги в каталоге snapshotting, и вы сможете перейти в него cd , как и в любой другой каталог.

По умолчанию все снимки доступны для записи в Btrfs, но вы можете создавать снимки только для чтения, если выберете это. Снимки только для чтения отлично подходят, если вы просто собираетесь сделать снимок для резервного копирования, а затем удалить его после завершения резервного копирования. Моментальные снимки с возможностью записи удобны тем, что вы можете делать такие вещи, как создание моментального снимка вашей файловой системы перед выполнением обновления системы; если обновление приведет к сбою в работе вашей системы, вы можете перезагрузиться с помощью моментального снимка и использовать его как обычную файловую систему. При создании новой файловой системы Btrfs корневой каталог становится subolume. Снимки можно делать только для subolumes, потому что suvolume — это представление корня совершенно отдельного дерева файловой системы, а снимок можно сделать только для дерева файловой системы.

Проще всего было бы создать subvolume для /home , чтобы вы могли делать снимки / и /home независимо друг от друга. Таким образом, вы могли бы запустить следующую команду для создания subvolume:

```bash
btrfs subvolume create /home
```

А затем, в какой-то момент, когда вам понадобится сделать снимок / home для резервного копирования, вы просто запустите:

```
btrfs subvolume snapshot /home/ /home-snap
```

Как только вы закончите с резервным копированием, вы можете удалить моментальный снимок с помощью команды:

```
btrfs subvolume delete /home-snap/
```

Тяжелая работа по отключению привязки к дереву моментальных снимков выполняется в фоновом режиме, поэтому вы можете заметить, что ввод-вывод происходит в кажущемся незанятым\
окне; это просто Btrfs очищает старый моментальный снимок. Если у вас много моментальных снимков или вы не помните, какие каталоги вы создали в качестве вложенных, вы можете запустить команду:

```bash
# btrfs subvolume list /mnt/btrfs-test/
 ID 267 top level 5 path home
 ID 268 top level 5 path snap-home
 ID 270 top level 5 path home/josef
```

Она не делает различия между моментальным снимком и обычным subvolume, поэтому вам, вероятно, следует грамотно называть свои снимки, чтобы позже вы могли определить, что есть что.

#### **Subvolumes**

Вложенный том в btrfs - это не то же самое, что логический том LVM или вложенный том ZFS. В LVM логический том сам по себе является блочным устройством; в btrfs это не так.  Subvolume btrfs не является блочным устройством и не может рассматриваться как таковой.

Вместо subolume btrfs можно рассматривать как пространство имен файлов POSIX. К этому пространству имен можно получить доступ через subvolume файловой системы верхнего уровня или подключить его самостоятельно. Итак, учитывая структуру файловой системы, подобную этой:

```bash
toplevel
`--- dir_a * just a normal directory
 | `--- p
 | `--- q
 `--- subvol_z * a subvolume
`--- r
 `--- s
```

можно смонтировать корень файловой системы, и в точке монтирования будет видна полная структура файловой системы; в качестве альтернативы можно смонтировать subvolume (с опцией монтирования subvol=subvol\_z ), и в точке монтирования будут видны только файлы r и s.

Файловая система btrfs имеет subvolume по умолчанию, который изначально задан как subvolume верхнего уровня. Это subvolume, который монтируется, если для монтирования не передан параметр subvol или subvolid. Изменение вложенного тома по умолчанию на btrfs subvolume\
default сделает верхний уровень файловой системы недоступным, за исключением использования опции монтирования subvolid=0.

#### **Эффективные индексированные каталоги**

В Btrfs каталоги и файлы выглядят на диске одинаково, что соответствует принципам UNIX. Варианты файловой системы ext должны предварительно выделять пространство для инодов при создании файловой системы, поэтому количество файлов, которые вы можете создать, ограничено сразу после создания файловой системы.

В Btrfs при создании нового файла мы добавляем несколько элементов в B-tree, что ограничивает вас только объёмом пространства для метаданных в вашей файловой системе. Если вы когда-либо создавали тысячи файлов в каталоге файловой системы ext, а затем удаляли их, вы, возможно, заметили, что выполнение команды ls в каталоге занимает гораздо больше времени, чем вы ожидали, учитывая, что в каталоге может быть всего несколько файлов.

Возможно, вам даже приходилось запускать такую команду:

```basic
e2fsck -D /dev/sda1
```

Чтобы повторно оптимизировать каталоги в ext, приходится выполнять определённые действия. Это связано с недостатком в способе хранения индексов каталогов в ext: их нельзя уменьшить. Если вы добавили тысячи файлов и внутреннее дерево индексов каталогов выросло до большого размера, оно не сократится обратно при удалении файлов. В Btrfs ситуация обстоит иначе.

В Btrfs мы храним индекс файла рядом с инодом каталога в B-tree файловой системы. B-tree будет увеличиваться и уменьшаться по мере необходимости, так что если вы создадите миллиард файлов в каталоге, а затем удалите их все, выполнение команды ls займёт столько же времени, как если бы вы только что создали каталог.

В Btrfs также есть индекс для каждого файла, основанный на его имени. Это удобно, потому что вместо поиска соответствия в индексе файлов содержащего каталога мы просто вычисляем хэш имени файла и ищем в B-tree это значение хэша. Этот элемент хранится рядом с элементом инода файла, так что при поиске имени обычно считывается тот же блок, который содержит всю важную необходимую информацию. Опять же, это ограничивает объём операций ввода-вывода, необходимых для выполнения базовых задач.

#### **mkswap**

mkswap настраивает область подкачки Linux на устройстве или в файле. ((После создания области подкачки вам необходимо вызвать команду swap on, чтобы начать ее использовать. Обычно области подкачки перечислены в файле /etc/fstab, чтобы их можно было использовать во время загрузки с помощью swapon - команды в каком-нибудь загрузочном скрипте.)

#### **xfs\_info**

xfs\_info показывает геометрию файловой системы для файловой системы XFS. xfs\_info эквивалентен вызову xfs\_growfs с параметром -new

#### **xfs\_check**

xfs\_check проверяет, является ли файловая система XFS непротиворечивой. Это необходимо только в том случае, если есть основания полагать, что файловая система имеет проблемы с непротиворечивостью. Поскольку XFS - это файловая система с журналированием, что позволяет ей сохранять согласованность файловой системы, в запуске xfs\_check не должно быть необходимости.

**xfs\_repair**

xfs\_repair восстанавливает поврежденные файловые системы XFS. xfs\_repair попытается найти исходное устройство, связанное с указанным блочным устройством, и будет использовать вместо него исходное устройство. Как бы то ни было, файловая система, подлежащая восстановлению, должна быть размонтирована, в противном случае результирующая файловая система может стать несогласованной или поврежденной.

### **smartmontools: smartd и smartctl**

Две служебные программы, smartctl и smartd (доступны после установки пакета smartmontools), могут использоваться для мониторинга и управления системами хранения данных с помощью технологии Self-Monitoring, Analysis and Reporting Technology System (SMART). SMART встроен в большинство современных жёстких дисков ATA и SCSI, а также твердотельных накопителей. Цель SMART — отслеживать надёжность жёсткого диска, прогнозировать сбои дисков и проводить различные виды самотестов дисков.

_smartd_ — это демон, который пытается включить мониторинг SMART на устройствах ATA и опрашивает их и устройства SCSI каждые 30 минут (настраиваемо), регистрируя ошибки SMART и изменения атрибутов SMART через интерфейс SYSLOG. Smartd также можно настроить на отправку предупреждений по электронной почте при обнаружении проблем. В зависимости от типа проблемы может потребоваться запустить самотесты на диске, создать резервную копию диска, заменить диск или использовать утилиту производителя для принудительного перераспределения неисправных или нечитаемых секторов диска.

Smartd можно настроить при запуске с помощью файла конфигурации /etc/default/smartmontools. При отправке сигнала USR1 в smartd он немедленно проверит состояние дисков, а затем вернётся к опросу дисков каждые 30 минут. Для ознакомления с конкретными опциями конфигурации обратитесь к справочной странице smartd.

#### ZFS: zpool и zfs

ZFS, которая в настоящее время принадлежит корпорации Oracle, была разработана в Sun Microsystems как файловая система следующего поколения, нацеленная на практически бесконечную масштабируемость и свободную от традиционных проектных парадигм. На данный момент только Ubuntu предлагает интеграцию ядра для ZFS на Linux. Другие дистрибутивы Linux могут использовать ZFS в пользовательском пространстве с помощью Fuse.

Основные доступные на данный момент функции ZFS включают:

* высокую устойчивость к ошибкам и целостность данных;
* практически неограниченное хранилище благодаря 128-битной архитектуре;
* гибридное управление томами и файловыми системами с возможностями RAID;
* сжатие и дедупликация данных;
* снимки данных;
* предоставление томов (zvols);
* возможность использования разных устройств для кэширования и журналирования;
* возможность делегирования административных прав непривилегированным пользователям.

Благодаря высокой устойчивости к ошибкам и дизайну, обеспечивающему целостность данных, команда типа fsck не требуется. ZFS работает в режиме транзакций, при этом уберблок обновляется только после завершения всех операций. Копии предыдущих уберблоков (128) хранятся по принципу циклического перебора. Так называемые метки vdev, которые идентифицируют диски, используемые в пуле ZFS, также имеют несколько копий: две в начале диска и две в конце. Периодическая очистка пулов может выявить проблемы с целостностью данных, а если пул оснащён более чем одним устройством, то данные можно восстановить на лету.

ZFS позволяет использовать дополнительные алгоритмы контрольной суммы для блоков и может хранить несколько копий этих блоков. Это можно настроить для каждой файловой системы ZFS.

Пулы ZFS можно рассматривать как управление логическими томами, и они могут состоять из одного или нескольких дисков. К пулам могут быть подключены отдельные устройства кэширования и журналирования, чтобы чтение и запись данных выполнялись на более быстрых устройствах. Наличие нескольких дисков в пуле позволяет восстанавливать данные на лету.

Типичный zfs пул:

```bash
$ sudo zpool list -v
 NAME SIZE ALLOC FREE EXPANDSZ FRAG CAP DEDUP HEALTH ALTROOT
 tank 1.98G 448K 1.98G -       0%   0%  1.00x ONLINE -
 sdb  1.98G 448K 1.98G -       0%   0%
```

Статус пула:

```bash
$ sudo zpool status -v
    pool: tank
  state: ONLINE
    scan: none requested
 config:
       NAME   STATE READ WRITE CKSUM
       tank   ONLINE 0   0     0
```

```bash
$ sudo zpool history
History for 'tank':
2017-01-11.11:32:50 zpool create -f -m /tank tank /dev/sdb
2017-01-11.12:37:44 zpool scrub tank
```

Пул ZFS используется в качестве резервной копии для одной или нескольких файловых систем ZFS. По умолчанию сам пул имеет единую файловую систему, названную в честь пула. Файловые системы ZFS отличаются гибкостью по размеру и позволяют настраивать различные атрибуты, такие как сжатие, резервирование размера, квота, блочные копии и т.д. Полный набор атрибутов можно увидеть в zfs get all и, при необходимости, в файловой системе zfs, моментальном снимке или томе.

Типичный список файловой системы ZFS:

```bash
$ sudo zfs list
 NAME USED AVAIL REFER MOUNTPOINT
 tank 242K 1.92G 19K   /tank
```

Создание файловой системы ZFS "docu,ents" c использованием сжатия:

```bash
$ sudo zfs create -o compression=on tank/documents
$ sudo zfs list tank/documents
NAME           USED AVAIL REFER MOUNTPOINT
tank/documents 19K  1.92G 19K   /tank/documents
```

или

```
$ sudo zfs create tank/documents
$ sudo zfs set compression=on tank/documents
$ sudo zfs list tank/documents
NAME           USED AVAIL REFER MOUNTPOINT
tank/documents 19K  1.92G 19K   /tank/documents
```

При наличии некоторых данных в файле /tank/documents степень сжатия можно увидеть с помощью:

```
$ sudo zfs get compressratio tank/documents
 NAME           PROPERTY      VALUE SOURCE
 tank/documents compressratio 1.68x   -
```

Создание резервной копии файла /tank/documents может быть выполнено мгновенно и не займет много места, пока содержимое файла /tank/documents не изменится. Доступ к содержимому моментального снимка можно получить через каталог .zfs/snapshot файловой системы ZFS.

```
$ sudo zfs snap tank/documents@backup
$ sudo zfs list -t snapshot
NAME                 USED AVAIL REFER MOUNTPOINT
tank/documents@backup 0   -     45.0M -
```
