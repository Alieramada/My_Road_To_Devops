### 12.1.3 Создание initrd с помощью mkinitrd

{% hint style="info" %}
mkinitrd был рассмотрен в предыдущем разделе, где также обсуждается, как создать такой образ вручную.
{% endhint %}

Чтобы ограничить размер ядра, часто используются исходные образы ramdisk (initrd) для предварительной загрузки любых модулей, необходимых для доступа к корневой файловой системе.&#x20;

mkinitrd - это инструмент, предназначенный для дистрибутивов, основанных на RPM (таких как Red Hat, SuSE и т.д.). Этот инструмент автоматизирует процесс создания файла initrd, тем самым обеспечивая правильное выполнение этого относительно сложного процесса.

В большинстве крупных дистрибутивов Linux исходный образ содержит почти все необходимые модули ядра; очень немногие из них будут скомпилированы непосредственно в ядро. Это позволяет легко устанавливать исправления в ядро и его модули с помощью пакетов RPM: обновление одного модуля потребует не перекомпиляции или замены всего ядра, а только одного модуля или, в худшем случае, нескольких зависимых модулей. Поскольку эти модули содержатся в файле initrd, этот файл  необходимо обновлять каждый раз при повторной компиляции ядра (вручную) или установке исправления для ядра (модуля). Создание нового образа initrd очень просто, если вы используете стандартный инструмент, поставляемый во многих дистрибутивах:

```bash
# mkinitrd initrd-image kernel-version
```

Полезные опции для mkinitrd включают в себя:

\--version

Этот параметр отображает номер версии утилиты mkinitrd

-f

При указании этого параметра утилита перезапишет любой существующий файл образа с таким же именем

\--builtin=

Это приводит к тому, что mkinitrd предполагает, что указанный модуль был скомпилирован в ядро. Он не будет искать модуль и не выдаст никаких ошибок, если он не существует.

\--omit-lvm-modules , --omit-raid-modules , --omit-scsi-module

Используя эти опции, можно предотвратить включение, соответственно, модулей LVM, RAID или SCSI, даже если они присутствуют, или утилита обычно включает их на основе содержимого /etc/fstab и/или /etc/raidtab .

### 12.1.4 Создание initrd с помощью mkinitramfs

Недовольные инструментом, используемым в дистрибутивах на основе RPM (mkinitrd ), некоторые разработчики Debian написали другую утилиту для создания файла initrd. Этот инструмент называется mkinitramfs . Инструмент mkinitramfs - это скрипт оболочки, который генерирует сжатый cpio-образ. Он был разработан таким образом, чтобы быть намного проще (как в коде, так и в использовании), чем mkinitrd. Скрипт состоит примерно из 380 строк кода.

Настройка mkinitramfs осуществляется с помощью файла конфигурации: initramfs.conf . Этот файл обычно находится в /etc/initramfs-tools/initramfs.conf . Этот конфигурационный файл создается скриптом и содержит стандартные объявления bash. Перед комментариями ставится префикс #. Переменные задаются с помощью:

```
variable=value
```

Опции, которые можно использовать с mkinitramfs, включают:

-d confdir

Этот параметр устанавливает альтернативный каталог конфигурации.

-k

Сохранить" временный каталог, использованный для создания образа

-o outfile

Записать полученный образ в outfile

-r root

Переопределить параметр ROOT в файле initramfs.conf.

{% hint style="info" %}
В дистрибутивах на основе Debian вы всегда должны использовать mkinitramfs, поскольку mkinitrd там не работает для более поздних ядер.
{% endhint %}

### 12.1.5 Настройка корневого устройства

Настройка корневого устройства является одной из многих настроек ядра. Настройки ядра исходят из или могут быть перезаписаны с помощью:

* значения по умолчанию, заданные в исходном коде
* значения по умолчанию, заданные командой rdev
* значения, передаваемые ядру во время загрузки, например root=/dev/xyz&#x20;
* значения, указанные в файле конфигурации GRUB.

Наиболее очевидными для использования являются блочные устройства, такие как жесткие диски, хранилища SAN, CD или DVD-диски. У вас даже может быть подключен корневой диск NFS, для этого требуется использовать initrd и установить параметры загрузки nfs\_root\_name и nfs\_root\_addrs. Вы можете установить или изменить корневое устройство практически на любое из среды initrd. Для этого убедитесь, что файловая система /proc была смонтирована с помощью сценариев в образе initrd. В /proc доступны следующие файлы :

```bash
/proc/sys/kernel/real-root-dev
/proc/sys/kernel/nfs-root-name
/proc/sys/kernel/nfs-root-addrs
```

Значение real-root-dev относится к номеру узла устройства корневой файловой системы. Его можно легко изменить, записав в него новый номер :

```bash
# echo 0x301>/proc/sys/kernel/real-root-dev
```

Это изменит реальный root на файловую систему в /dev/hda1 . Если вы хотите использовать root, подключенный к NFS, для файлов nfs-root-name и nfs-root-addrs необходимо задать соответствующие значения, а для номера устройства - значение 0

```
# echo /var/nfsroot >/proc/sys/kernel/nfs-root-name
# echo 193.8.232.2:193.8.232.7::255.255.255.0:idefix \
>/proc/sys/kernel/nfs-root-addrs
# echo 255>/proc/sys/kernel/real-root-dev
```

{% hint style="info" %}
Если корневое устройство настроено на RAM-диск, корневая файловая система не перемещается в /initrd , а процедура загрузки просто продолжается путем запуска init на исходном RAM-диске.
{% endhint %}

### 12.1.7 Процесс инициализации

init является родительским для всех процессов, считывает файл /etc/inittab и создает процессы на основе его содержимого. Обычно он запускает gettys, позволяя пользователям входить в систему. Он также определяет "уровни выполнения".

"Уровень выполнения" - это программная конфигурация системы, которая позволяет существовать только выбранной группе процессов.&#x20;

* Уровень запуска 0 (зарезервирован)  используется для остановки системы. уровень запуска 1 (зарезервирован) &#x20;
* Уровень запуска 1 используется для перевода системы в однопользовательский режим.&#x20;
* Уровни запуска 2,3,4 и 5 являются многопользовательскими.&#x20;
* Уровень запуска 6 используется для перезагрузки системы.&#x20;
* Уровни запуска 7, 8 и 9 можно использовать по своему усмотрению. Большинство версий Unix(/Linux) не используют эти уровни запуска. В обычном Debian Например, в системе Linux каталоги /etc/rc<уровень выполнения>.d, которые мы обсудим позже, недоступны для этих уровней выполнения, хотя это было бы совершенно законно.&#x20;
* Уровни запуска s и S являются внутренне одинаковыми. Это переводит систему runlevel s в "однопользовательский режим". Скрипты в каталоге / etc/rcS.d выполняются при загрузке системы. Хотя уровень запуска S не предназначен для активации пользователем, он может быть активирован.&#x20;
* Уровни запуска A, B и C являются так называемыми уровнями запуска "по требованию". Например, если текущий уровень выполнения равен "2" и выполняется команда init A , выполняются сценарии для запуска или остановки процессов на уровне выполнения "A", но фактический уровень выполнения остается "2".

### 12.1.8 Настройка /etc/inittab

Как упоминалось ранее, init считывает файл /etc/inittab, чтобы определить, что он должен делать. Запись в этом файле имеет следующий формат:

```bash
id:runlevels:action:process
```

Ниже приведен пример файла /etc/inittab.

```bash
# The default runlevel.
id:2:initdefault:
# Boot-time system configuration/initialization script.
# This is run first except when booting in emergency (-b) mode.
si::sysinit:/etc/init.d/rcS
# What to do in single-user mode.
~~:S:wait:/sbin/sulogin
# /etc/init.d executes the S and K scripts upon change
# of runlevel.
#
# Runlevel 0 is halt.
# Runlevel 1 is single-user.
# Runlevels 2-5 are multi-user.
# Runlevel 6 is reboot.
l0:0:wait:/etc/init.d/rc 0
l1:1:wait:/etc/init.d/rc 1
l2:2:wait:/etc/init.d/rc 2
l3:3:wait:/etc/init.d/rc 3
l4:4:wait:/etc/init.d/rc 4
l5:5:wait:/etc/init.d/rc 5
l6:6:wait:/etc/init.d/rc 6
# Normally not reached, but fall through in case of emergency.
z6:6:respawn:/sbin/sulogin
# /sbin/getty invocations for the runlevels.
#
# The "id" field MUST be the same as the last
# characters of the device (after "tty").
#
# Format:
# <id>:<runlevels>:<action>:<process>
1:2345:respawn:/sbin/getty 38400 tty1
2:23:respawn:/sbin/getty 38400 tty2
```

* id

Поле id однозначно идентифицирует запись в файле /etc/inittab и может содержать 1-4 символа. Однако для gettys и других процессов входа в систему поле id должно содержать суффикс соответствующего идентификационного номера, в противном случае учет входа в систему может не сработать.

* Уровни выполнения&#x20;

Это поле содержит уровни выполнения, для которых должно быть выполнено указанное действие.

* Действие
* respawn

Процесс будет перезапущен всякий раз, когда он завершится, возродится (например, getty).&#x20;

* wait

Процесс будет запущен один раз, когда будет вызван указанный уровень выполнения ожидания, и init будет ожидать его завершения.

* once

Процесс будет выполнен один раз, когда будет вызван указанный  уровень выполнения.

* boot

Процесс будет запущен во время загрузки системы. Поле boot runlevels игнорируется

* bootwait

Процесс будет запущен во время загрузки системы, в то время как bootwait init ожидает его завершения (например, /etc/rc) . Поле runlevels игнорируется.

* off

Ничего не делать

* ondemand

Процесс, помеченный уровнем выполнения по требованию, будет выполняться по требованию при каждом вызове указанного уровня выполнения по требованию. Однако изменения уровня выполнения не произойдет (уровнями выполнения по требованию являются "a", "b" и "c").

* initdefault

В поле initdefault указывается уровень выполнения, который должен быть введен после загрузки системы. Если его не существует, init запросит уровень выполнения на консоли. Поле process игнорируется. В приведенном выше примере после загрузки система перейдет на уровень выполнения 2.

* sysinit

Процесс будет запущен во время загрузки системы. Он будет запущен автоматически перед выполнением любых операций boot или bootwait. Поле runlevels игнорируется.

* powerwait

Процесс будет запущен при отключении питания. Функция ожидания включения обычно информируется об этом процессом, связывающимся с ИБП, подключенным к компьютеру. ИБП в этой функции ожидает завершения процесса, прежде чем продолжить.

* powerfail

Так же как и powerwait за исключением того, что init не выполняет powerfail, не дожидаясь завершения процесса

* powerokwait

Этот процесс будет выполнен сразу после инициализации

powerokwait получает сообщение о том, что подача электроэнергии восстановлена

* powerfailnow

Этот процесс будет выполнен, когда в программе init powerfailnow появится сообщение о том, что батарея внешнего ИБП почти разряжена и питание отключено (при условии, что внешний ИБП и процесс мониторинга способны обнаружить это состояние).

* ctrlaltdel

Процесс будет запущен, когда init ctrlaltdel получит сигнал SIGINT. Это означает, что кто-то в системной консоли нажал комбинацию клавиш CTRL-ALT-DEL и CTRL-ALT-DELETE. Обычно требуется выполнить какое-либо завершение работы, либо для перехода на однопользовательский уровень, либо для перезагрузки компьютера.

* kbdrequest

Процесс будет запущен, когда init получит сигнал от обработчика клавиатуры о том, что на клавиатуре консоли была нажата специальная комбинация клавиш kbdrequest. По сути, вы хотите сопоставить некоторую комбинацию клавиш с действием "Сигнал клавиатуры". Например, чтобы сопоставить Alt-Uparrow для этой цели, используйте следующее в вашем файле keymaps: `alt keycode 103 = KeyboardSignal` .

* process

Это поле определяет процесс, который должен быть выполнен. Если поле process начинается с "+", в нем не будет выполняться учет по протоколам utmp и wtmp .&#x20;

### Сценарий /etc/init.d/rc

Для каждого из уровней выполнения 0-6 в /etc/inittab есть запись, которая выполняет /etc/init.d/rc ? где "?" равно 0-6, как вы можете видеть в следующей строке из /etc/init.d/rc в предыдущем примере выше:

```bash
l2:2:wait:/etc/init.d/rc 2
```

Итак, на самом деле происходит то, что файл /etc/init.d/rc вызывается с параметром runlevel в качестве параметра.

Каталог /etc содержит несколько каталогов, специфичных для уровня выполнения, которые, в свою очередь, содержат символические ссылки на скрипты, специфичные для уровня выполнения, в /etc/init.d/ . Эти каталоги являются:

```bash
 $ ls -d /etc/rc*
 /etc/rc.boot /etc/rc1.d /etc/rc3.d /etc/rc5.d /etc/rcS.d
 /etc/rc0.d /etc/rc2.d /etc/rc4.d /etc/rc6.d
```

Как вы можете видеть, там также есть каталог /etc/rc.boot. Этот каталог устарел и был заменен каталогом /etc/rcN.d /etc/rcS.d . Во время загрузки сначала сканируется каталог /etc/rcS.d, а затем, на предмет обратной совместимости, каталог /etc/rc.boot.

Название символьной ссылки начинается либо с "S", либо с "K". Давайте рассмотрим каталог /etc/rc2.d:

```bash
$ ls /etc/rc2.d
 K20gpm      S11pcmcia  S20logoutd S20ssh     S89cron
 S10ipchains S12kerneld S20lpd     S20xfs     S91apache
 S10sysklogd S14ppp     S20makedev S22ntpdate S99gdm
 S11klogd    S20inetd   S20mysql   S89atd     S99rmnologin
```



Если имя символьной ссылки начинается с "K", скрипт вызывается с "stop" в качестве параметра для остановки процесса. Это относится к K20gpm , поэтому команда становится K20gpm stop . Давайте выясним, как называется программа или скрипт:

```bash
$ ls -l /etc/rc2.d/K20gpm
lrwxrwxrwx 1 root root 13 Mar 23 2001 /etc/rc2.d/K20gpm -> ../init.d/gpm
```

Итак, остановка K20gpm приводит к остановке /etc/init.d/gpm . Давайте посмотрим, что происходит с параметром "stop", изучив часть скрипта: init script

```
#!/bin/sh
#
# Start Mouse event server
...
case "$1" in
start)
    gpm_start
    ;;
stop)
    gpm_stop
    ;;
force-reload|restart)
    gpm_stop
    sleep 3
    gpm_start
    ;;
*)
    echo "Usage: /etc/init.d/gpm {start|stop|restart|force-reload}"
    exit 1
esac
```

В case..esac проверяется первый параметр, $1, и в случае, если его значение равно "stop", выполняется gpm\_stop.

С другой стороны, если имя символьной ссылки начинается с буквы "S", скрипт вызывается с "start" в качестве параметра для запуска процесса.

Скрипты выполняются в порядке лексической сортировки имен файлов.

Допустим, у нас есть демон, некоторый Daemon, сопровождающий скрипт /etc/init.d/SD, и мы хотим, чтобы какой-нибудь демон запускался , когда система находится на уровне запуска 2, но не тогда, когда система находится на уровне запуска 3.

Как вы уже знаете, это означает, что нам нужна символическая ссылка, начинающаяся с "S", для уровня выполнения 2 и символическая ссылка, начинающаяся с "K", для уровня выполнения 3. Мы также определили, что демон Some Daemon должен быть запущен после S19 каким-то другим демоном, который подразумевает S20 и K80, поскольку запуск/остановка симметричны, то есть то, что запускается первым, останавливается последним. Это достигается с помощью следующего набора команд:

```
# cd /etc/rc2.d
# ln -s ../init.d/SDscript S20SomeDaemon
# cd /etc/rc3.d
# ln -s ../init.d/SDscript K80SomeDaemon
```

Если вы хотите вручную запустить, перезапустить или остановить процесс, рекомендуется использовать соответствующий скрипт в /etc/init.d/, например /etc/init.d/gpm restart, чтобы инициировать перезапуск процесса

### 12.1.9 update-rc.d

{% hint style="info" %}
Обратите внимание, что этот раздел применим только к дистрибутивам на базе Debian
{% endhint %}

В дистрибутивах Linux, производных от Debian, используется команда update-rc.d для установки и удаления ссылок на скрипты инициализации, упомянутых в предыдущем разделе.

Если у вас есть сценарий запуска под названием "foobar" в /etc/init.d/ и вы хотите добавить его к уровням запуска по умолчанию, вы можете использовать:

```
# update-rc.d foobar defaults
Adding system startup for /etc/init.d/foobar ...
/etc/rc0.d/K20foobar -> ../init.d/foobar
/etc/rc1.d/K20foobar -> ../init.d/foobar
/etc/rc6.d/K20foobar -> ../init.d/foobar
/etc/rc2.d/S20foobar -> ../init.d/foobar
/etc/rc3.d/S20foobar -> ../init.d/foobar
/etc/rc4.d/S20foobar -> ../init.d/foobar
/etc/rc5.d/S20foobar -> ../init.d/foobar
```

update-rc.d создаст K (стоповые) ссылки в rc0.d, rc1.d и rc6.d и S (стартовые) ссылки в rc2.d, rc3.d, rc4.d и rc5.d.

Если вы не хотите, чтобы установленный пакет запускался автоматически, используйте update-rc.d, чтобы удалить ссылки на загрузку, например, чтобы отключить запуск dovecot при загрузке:

```bash
# update-rc.d -f dovecot remove
Removing any system startup links for /etc/init.d/dovecot ...
/etc/rc2.d/S24dovecot
/etc/rc3.d/S24dovecot
/etc/rc4.d/S24dovecot
/etc/rc5.d/S24dovecot
```

Параметр -f (принудительно) необходим, если rc-скрипт все еще существует. Если вы установите обновленный пакет dovecot, ссылки будут восстановлены. Чтобы предотвратить это, создайте ссылки "stop" в каталогах уровня запуска.:

```bash
# update-rc.d -f dovecot stop 24 2 3 4 5 .
Adding system startup for /etc/init.d/dovecot ...
/etc/rc2.d/K24dovecot -> ../init.d/dovecot
/etc/rc3.d/K24dovecot -> ../init.d/dovecot
/etc/rc4.d/K24dovecot -> ../init.d/dovecot
/etc/rc5.d/K24dovecot -> ../init.d/dovecot
```

{% hint style="info" %}
Обратите внимание, не забудьте о точке в конце.
{% endhint %}

### 12.1.10 Использование таргетов в systemd

Вместо предопределенных уровней выполнения система использует таргеты для определения состояния системы. Эти целевые таргеты  представлены таргет юнитами. Таргет юниты заканчиваются расширениями файлов .target, и их единственное назначение - группировать другие системные модули посредством цепочки зависимостей. Это также означает, что, по сравнению с уровнями запуска init, несколько таргетов могут быть активны одновременно.

Например, модуль graphical.target запускает службы как диспетчер отображения GNOME, но также зависит от multi-user.target (который является неграфическим состоянием системы), которое, в свою очередь, зависит от basic.target.

Прежде чем мы продолжим управлять таргетами и использовать их, вы должны знать, какие каталоги используются для хранения таргет файлов по умолчанию и как вы можете их переопределить.&#x20;

Как и во всех устройствах, таргет файлы по умолчанию хранятся в каталоге /usr/lib/systemd , файлы в этом каталоге создаются поставщиком установленного вами программного обеспечения, и их нельзя изменять, кроме как с помощью сценариев установки. Каталог, в котором вы можете хранить свои пользовательские таргеты и переопределения , - это /etc/systemd , все, что записано в этом каталоге, имеет приоритет над файлами в /usr/ lib/systemd .&#x20;

Существует несколько способов переопределить или добавить свойства к файлам юнитов. Вы можете создать совершенно новый файл с таким же именем, например ssh.server, в каталоге /etc/systemd/system . Это переопределит полное определение юнит. Если вы хотите добавить или изменить только некоторые свойства, вы можете создать новый каталог в /etc/systemd/system с именем объекта, добавив .d, например, sshd.server.d. В этом каталоге вы можете создавать файлы с расширением .conf, в которые вы можете поместить нужные вам свойства для добавления или переопределения. Оба этих способа также могут быть выполнены с помощью команды systemctl, это описано далее в главе 20.6.3.&#x20;

Существует также третье доступное место, в которое вы можете поместить файлы, переопределяющие определения ваших модулей, - это каталог /run/systemd . Определения в этом каталоге имеют приоритет над файлами в /usr/lib/systemd , но не над файлами в /etc/systemd . Переопределения в /run/systemd будут использоваться только до перезагрузки системы, поскольку все файлы в /run/systemd будут удалены при перезагрузке системы.&#x20;

&#x20;Чтобы получить обзор всех активных переопределений, вы можете использовать команду systemd-delta. Эта команда может возвращать значения следующих типов:

* masked

Замаскированные юниты, юниты, которые невозможно запустить.

* equivalent

Переопределенные файлы, которые не отличаются по содержимому.

* redirected

Символические ссылки на другие юнит файлы.

* overridden

Переопределенные юнит файлов.

* extended

Расширенные файлы  юнитов с использованием файла .conf.

```bash
pirog@pirog:~$ systemd-delta

[EXTENDED]   /usr/lib/systemd/system/rc-local.service → /usr/lib/systemd/system>
[EXTENDED]   /usr/lib/systemd/system/systemd-journald.service → /usr/lib/system>
[EXTENDED]   /usr/lib/systemd/system/systemd-localed.service → /usr/lib/systemd>
[EXTENDED]   /usr/lib/systemd/system/systemd-logind.service → /usr/lib/systemd/>
[EXTENDED]   /usr/lib/systemd/system/systemd-udevd.service → /usr/lib/systemd/s>
[EXTENDED]   /usr/lib/systemd/system/user@.service → /usr/lib/systemd/system/us>

[EXTENDED]   /usr/lib/systemd/system/user@.service → /usr/lib/systemd/system/us>

```



Вы также можете выполнять фильтрацию по указанным выше типам, используя флаги -t или --type=, они отображают список указанных выше типов. Если вы также хотите видеть неизмененные файлы, вы можете добавить unchanged в качестве типа.&#x20;

Другими параметрами, которые вы можете использовать, являются --diff=false, если вы не хотите, чтобы systemd-delta отображал различия в переопределенных файлах, и --no-pager, если вы не хотите, чтобы выходные данные передавались на пейджер.&#x20;

Теперь, когда мы знаем, где хранятся файлы unit и как мы можем их переопределить, мы можем взглянуть на изменение состояний системы. Для получения и изменения состояния системы (по умолчанию) мы используем команду systemctl. Полное описание возможностей этой команды можно найти в главе 20.6.3.&#x20;

Вы также можете изменить состояние системы во время выполнения, это можно сделать с помощью команды systemctl isolate. Это остановит все службы, не определенные для выбранного тагета и запустит все службы, определенные для него.

Например, чтобы перейти в режим восстановления, вы можете выполнить следующую команду:

```bash
systemctl isolate rescue.target
(init 1)

```

Это приведет к остановке всех служб, кроме тех, которые определены для тагета восстановления. Обратите внимание, что эта команда не уведомит ни одного из зарегистрированных пользователей о выполнении действия.

Также доступно несколько сочетаний клавиш для изменения состояния системы, которые имеют дополнительный бонус в том, что они уведомляют о действии вошедших в систему пользователей. Например, еще один способ перевести систему в аварийный режим заключается в следующем:

```bash
$ systemctl rescue
```

Сначала это уведомит о действии зарегистрированных пользователей, а затем остановит все службы, не определенные в таргете. Если вы не хотите , чтобы пользователи получали уведомления, вы можете добавить флажок --no-wall.

Если ваша система слишком неисправна, чтобы использовать режим восстановления, также доступен аварийный режим. Его можно запустить с помощью следующей команды:

```bash
$ systemctl emergency
```

Если вы хотите запустить определенные службы при загрузке, вам необходимо включить их. Вы можете включить службы с помощью команды systemctl enable. Например, чтобы включить sshd, выполните следующую команду:

```bash
$ systemctl enable sshd.service
```

Чтобы снова отключить службу, вы используете systemctl disable . Например:

```bash
systemctl disable sshd.service
```

Unit файл службы определяет, в каком системном состоянии будет запущена служба. Это настраивается путем установки параметра Wanted By= в разделе \[Install]. Если для параметра установлено значение multi-user.target, то он будет запущен как в неграфическом, так и в графическом режиме.

### **The LSB standard**

Стандартная база Linux (LSB) определяет интерфейс для прикладных программ, которые компилируются и упаковываются для реализаций, соответствующих LSB. Следовательно, программа, которая была скомпилирована в среде, совместимой с LSB, будет работать в любом дистрибутиве, поддерживающем стандарт LSB. Программы, совместимые с LSB, могут полагаться на наличие определенных стандартных библиотек. Стандарт также включает список обязательных утилит и сценариев, которые определяют среду, подходящую для установки совместимых с LSB двоичных файлов.

Спецификация содержит информацию, относящуюся к архитектуре процессора. Это означает, что LSB представляет собой семейство спецификаций, а не одну. Другими словами, если ваш LSB-совместимый двоичный файл был скомпилирован для системы на базе Intel, он не будет работать, например, на LSB-совместимой системе на базе Alpha, но будет установлен и запущен на любой LSB-совместимой системе на базе Intel. Таким образом, спецификации LSB состоят из общей части и части, относящейся к конкретной архитектуре; "LSB-generic" или "generic LSB" и "LSB-arch" или "archLSB".

Стандарт LSB перечисляет, какие универсальные библиотеки должны быть доступны, например, libdl, libcrypt, libpthread и т.д., и предоставляет список библиотек, специфичных для процессора, таких как libc и libm. В стандарте также указаны пути поиска для этих библиотек, их названия и формат (ELF). В другом разделе описывается, как должна быть реализована динамическая компоновка. Для каждой стандартной библиотеки приведен список функций, а также перечислены определения данных и сопутствующие файлы заголовков.

LSB определяет список из более чем 130 команд, которые должны быть доступны в системе, совместимой с LSB, а также правила их вызова и поведение. В качестве примеров можно привести cp, tar, kill и gzip, а также языки выполнения perl и python.

Ожидаемое поведение системы, совместимой с LSB, во время инициализации системы является частью спецификации LSB. Также приводится определение системы cron, а также действия, функции и расположение сценариев инициализации. Любой сценарий инициализации, совместимый с LSB, должен уметь обрабатывать следующие параметры: зstart , stop , restart , force-reload и status. Параметры reload и try-restart являются необязательными. В стандарте также приведены определения уровней выполнения и списки имен пользователей и групп, а также соответствующие им идентификаторы UID's/ GID's.

Хотя можно установить программу, совместимую с LSB, без использования менеджера пакетов (применив сценарий, содержащий только команды, совместимые с LSB), спецификация LSB содержит описание программных пакетов и их соглашения об именовании.

{% hint style="info" %}
&#x20;В LSB используется стандарт Red Hat Package Manager. Дистрибутивы, совместимые с LSB на базе Debian, могут считывать пакеты RPM с помощью команды alien
{% endhint %}

Стандарты LSB часто ссылаются на другие хорошо известные стандарты, например ISO/IEC 9945-2009 (Portable OS base, очень Unix-подобный). Любая реализация, соответствующая стандарту LSB, должна обеспечивать обязательные элементы иерархии файловой системы, указанные в стандарте иерархии файловых систем (FHS), и ряд специфических требований к LSB. Смотрите также раздел, посвященный стандарту FHS.

### Среда bootscript и команды

Изначально Linux содержал лишь ограниченный набор сервисов и имел очень простую загрузочную среду. По мере старения Linux и увеличения количества сервисов в дистрибутиве, соответственно, росло и количество инициализирующих скриптов. Через некоторое время появился набор стандартов. Сценарии инициализации обычно включают в себя какой-либо другой сценарий, который содержит функции для запуска, остановки и проверки процесса.

В стандарте LSB перечислен ряд функций, которые должны быть доступны для сценариев уровня выполнения. Эти функции должны быть перечислены в файлах в каталоге /lib/lsb/init-functions и должны реализовывать (как минимум) следующие функции:

```
1. start_daemon [-f] [-n nicelevel]
 [-p pidfile] pathname [args...]
```

запускает указанную программу как демон. Функция start\_daemon проверит, запущена ли программа уже. Если это так, она не запустит другую копию демона, если не будет задан параметр -f. Параметр -n указывает допустимый уровень.

```
2. killproc [-ppidfile] pathname [signal]
```

остановит указанную программу, попытавшись сначала завершить ее, используя указанный сигнал. Если это не удастся, будет отправлен сигнал SIGTERM. Если программа была завершена, pid-файл должен быть удален, если завершенный процесс еще не сделал этого.

```
3. pidofproc [-p pidfile] pathname
```

возвращает один или несколько идентификаторов процесса для конкретного демона, как указано в имени пути. Несколько идентификаторов процесса разделены одним пробелом.

В некоторых случаях эти функции предоставляются в виде отдельных команд, и скрипты просто обеспечивают правильную установку пути к этим скриптам . Часто также включаются некоторые функции ведения журнала и отображения строк состояния.

### Изменение и настройка уровней выполнения

Изменение уровней выполнения на работающем компьютере требует сравнения служб, запущенных на текущем уровне выполнения, с теми, которые необходимо запустить на новом уровне выполнения. Впоследствии, вероятно, потребуется остановить некоторые процессы и запустить другие.

Напомним, что инициализаторы для уровня выполнения "X" сгруппированы в каталоге /etc/rc.d/rcX.d (или, в более новых системах (на базе LSB), в /etc/ init.d/rcX.d ). Имена файлов определяют способ вызова скриптов: если имя начинается с буквы "K", скрипт будет запущен с параметром stop, если имя начинается с буквы "S", скрипт будет запущен с параметром start. Обычная процедура при изменении уровня выполнения заключается в том, чтобы сначала остановить лишние процессы, а затем запустить новые.

Сами скрипты инициализации находятся в каталоге /etc/init.d . Файлы, которые вы найдете в каталоге rcX.d, являются символическими ссылками на эти файлы. Во многих случаях сценарии запуска и остановки являются символическими ссылками на один и тот же скрипт. Это означает, что такие скрипты инициализации должны быть способны обрабатывать, по крайней мере, параметры запуска и остановки.

Например, символическая ссылка с именем S06syslog в /etc/init.d/rc3.d может указывать на скрипт /etc/init.d/syslog , как и символическая ссылка с именем K17syslog , найденная в /etc/init.d/rc2.d.

Порядок, в котором службы останавливаются или запускаются, может иметь большое значение. Некоторые службы могут запускаться одновременно, другие должны запускаться в строгом порядке. Например, ваша сеть должна быть подключена, прежде чем вы сможете запустить httpd. Порядок определяется именами символических ссылок. Согласно правилам именования, имена сценариев инициализации (тех, что находятся в каталогах rcN.d) должны содержать две цифры сразу после начальной буквы. Они выполняются в алфавитном порядке.

В первые дни системные администраторы создавали эти ссылки вручную. Позже большинство дистрибутивов Linux решили предоставить команды/скрипты Linux, которые позволяют администратору отключать или включать определенные скрипты на определенных уровнях запуска и проверять, какие системы (команды) будут запущены на том или ином уровне запуска. Эти команды обычно управляют обеими вышеупомянутыми ссылками и присваивают им имена таким образом, чтобы скрипты запускались в правильном порядке.

### Команда chkconfig

Другим инструментом для управления правильной привязкой сценариев запуска (init) является checkconfig . В некоторых системах (например, SuSE/Novell) он служит интерфейсом для insserv и использует стандартный блок комментариев LSB для поддержки администрирования. В старых системах он поддерживает свой собственный специальный раздел комментариев, который имеет гораздо более простой и менее гибкий синтаксис. Этот старый синтаксис состоит из двух строк, одна из которых представляет собой описание сервиса, начинаются с ключевого слова description: . Другая строка начинается с ключевого слова chkconfig: и содержит список уровней выполнения, для которых запускается служба, и приоритет (который определяет, в каком порядке будут выполняться скрипты при изменении уровней выполнения). Например:

```bash
# Init script for foo daemon
#
# description: food, the foo daemon
# chkconfig: 2345 55 25
#
#
```

Это означает, что демон foo запустится на уровнях выполнения 2, 3, 4 и 5, будет иметь приоритет 55 в очереди инициализирующих скриптов, которые запускаются во время запуска, и приоритет 25 в очереди инициализирующих скриптов, которые запускаются, если демон необходимо остановить.

Утилиту chkconfig можно использовать для составления списка служб, которые будут запускаться на тех или иных уровнях выполнения, для добавления службы на уровень выполнения или ее удаления с него, а также для добавления всей службы в сценарии запуска или ее удаления из них.

{% hint style="info" %}
Обратите внимание, что мы приводим здесь несколько примеров, но имейте в виду: существуют различные версии chkconfig. Пожалуйста, сначала ознакомьтесь со страницами руководства по команде chkconfig в вашем дистрибутиве.
{% endhint %}

chkconfig не отключает и не включает службу автоматически, а просто изменяет символьные ссылки. Если запущен демон cron и вы используете систему на базе Red Hat, работающую на уровне выполнения 2, команда:

```bash
chkconfig --levels 2345 crond off
```

изменила бы администрирование, но не остановило бы демон cron немедленно. Также обратите внимание, что в системе Red Hat можно указать более одного уровня выполнения, как мы делали в нашем предыдущем примере. В системах Novell/SuSE вы можете использовать:

```bash
chkconfig food 2345
```

и чтобы изменить это так, чтобы оно запускалось только на уровне выполнения 1, просто используйте:

```bash
# chkconfig food 1
 
# chkconfig --list
```

отобразит текущее состояние служб и уровни выполнения, на которых они активны. Например, следующие две строки могут быть частью выходных данных:

```bash
xdm 0:off 1:off 2:off 3:off 4:off 5:on 6:off
 
xfs 0:off 1:off 2:off 3:off 4:off 5:off 6:off
```

Они указывают на то, что служба xfs не запущена ни на одном уровне выполнения, а служба xdm будет запущена только при переключении на уровень выполнения 5.

Чтобы добавить новую службу, скажем, демон foo, мы создаем новый скрипт инициализации и называем его в честь службы, в данном случае мы могли бы использовать food . Этот скрипт последовательно помещается в каталог /etc/init.d, после чего нам нужно вставить соответствующий заголовок в этот скрипт (либо старый заголовок chkconfig, либо более новый заголовок, совместимый с LSB), а затем запустить:

```bash
# chkconfig --add food
```

Чтобы удалить службу foo со всех уровней выполнения, вы можете ввести:

```bash
# chkconfig --del food
```

Обратите внимание, что скрипт food останется в каталоге /etc/init.d/.
