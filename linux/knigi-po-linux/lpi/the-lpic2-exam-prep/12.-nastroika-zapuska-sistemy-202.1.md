### 12.1.3 Создание initrd с помощью mkinitrd

{% hint style="info" %}
mkinitrd был рассмотрен в предыдущем разделе, где также обсуждается, как создать такой образ вручную.
{% endhint %}

Чтобы ограничить размер ядра, часто используются исходные образы ramdisk (initrd) для предварительной загрузки любых модулей, необходимых для доступа к корневой файловой системе.&#x20;

mkinitrd - это инструмент, предназначенный для дистрибутивов, основанных на RPM (таких как Red Hat, SuSE и т.д.). Этот инструмент автоматизирует процесс создания файла initrd, тем самым обеспечивая правильное выполнение этого относительно сложного процесса.

В большинстве крупных дистрибутивов Linux исходный образ содержит почти все необходимые модули ядра; очень немногие из них будут скомпилированы непосредственно в ядро. Это позволяет легко устанавливать исправления в ядро и его модули с помощью пакетов RPM: обновление одного модуля потребует не перекомпиляции или замены всего ядра, а только одного модуля или, в худшем случае, нескольких зависимых модулей. Поскольку эти модули содержатся в файле initrd, этот файл  необходимо обновлять каждый раз при повторной компиляции ядра (вручную) или установке исправления для ядра (модуля). Создание нового образа initrd очень просто, если вы используете стандартный инструмент, поставляемый во многих дистрибутивах:

```bash
# mkinitrd initrd-image kernel-version
```

Полезные опции для mkinitrd включают в себя:

\--version

Этот параметр отображает номер версии утилиты mkinitrd

-f

При указании этого параметра утилита перезапишет любой существующий файл образа с таким же именем

\--builtin=

Это приводит к тому, что mkinitrd предполагает, что указанный модуль был скомпилирован в ядро. Он не будет искать модуль и не выдаст никаких ошибок, если он не существует.

\--omit-lvm-modules , --omit-raid-modules , --omit-scsi-module

Используя эти опции, можно предотвратить включение, соответственно, модулей LVM, RAID или SCSI, даже если они присутствуют, или утилита обычно включает их на основе содержимого /etc/fstab и/или /etc/raidtab .

### 12.1.4 Создание initrd с помощью mkinitramfs

Недовольные инструментом, используемым в дистрибутивах на основе RPM (mkinitrd ), некоторые разработчики Debian написали другую утилиту для создания файла initrd. Этот инструмент называется mkinitramfs . Инструмент mkinitramfs - это скрипт оболочки, который генерирует сжатый cpio-образ. Он был разработан таким образом, чтобы быть намного проще (как в коде, так и в использовании), чем mkinitrd. Скрипт состоит примерно из 380 строк кода.

Настройка mkinitramfs осуществляется с помощью файла конфигурации: initramfs.conf . Этот файл обычно находится в /etc/initramfs-tools/initramfs.conf . Этот конфигурационный файл создается скриптом и содержит стандартные объявления bash. Перед комментариями ставится префикс #. Переменные задаются с помощью:

```
variable=value
```

Опции, которые можно использовать с mkinitramfs, включают:

-d confdir

Этот параметр устанавливает альтернативный каталог конфигурации.

-k

Сохранить" временный каталог, использованный для создания образа

-o outfile

Записать полученный образ в outfile

-r root

Переопределить параметр ROOT в файле initramfs.conf.

{% hint style="info" %}
В дистрибутивах на основе Debian вы всегда должны использовать mkinitramfs, поскольку mkinitrd там не работает для более поздних ядер.
{% endhint %}

### 12.1.5 Настройка корневого устройства

Настройка корневого устройства является одной из многих настроек ядра. Настройки ядра исходят из или могут быть перезаписаны с помощью:

* значения по умолчанию, заданные в исходном коде
* значения по умолчанию, заданные командой rdev
* значения, передаваемые ядру во время загрузки, например root=/dev/xyz&#x20;
* значения, указанные в файле конфигурации GRUB.

Наиболее очевидными для использования являются блочные устройства, такие как жесткие диски, хранилища SAN, CD или DVD-диски. У вас даже может быть подключен корневой диск NFS, для этого требуется использовать initrd и установить параметры загрузки nfs\_root\_name и nfs\_root\_addrs. Вы можете установить или изменить корневое устройство практически на любое из среды initrd. Для этого убедитесь, что файловая система /proc была смонтирована с помощью сценариев в образе initrd. В /proc доступны следующие файлы :

```bash
/proc/sys/kernel/real-root-dev
/proc/sys/kernel/nfs-root-name
/proc/sys/kernel/nfs-root-addrs
```

Значение real-root-dev относится к номеру узла устройства корневой файловой системы. Его можно легко изменить, записав в него новый номер :

```bash
# echo 0x301>/proc/sys/kernel/real-root-dev
```

Это изменит реальный root на файловую систему в /dev/hda1 . Если вы хотите использовать root, подключенный к NFS, для файлов nfs-root-name и nfs-root-addrs необходимо задать соответствующие значения, а для номера устройства - значение 0

```
# echo /var/nfsroot >/proc/sys/kernel/nfs-root-name
# echo 193.8.232.2:193.8.232.7::255.255.255.0:idefix \
>/proc/sys/kernel/nfs-root-addrs
# echo 255>/proc/sys/kernel/real-root-dev
```

{% hint style="info" %}
Если корневое устройство настроено на RAM-диск, корневая файловая система не перемещается в /initrd , а процедура загрузки просто продолжается путем запуска init на исходном RAM-диске.
{% endhint %}

### 12.1.7 Процесс инициализации

init является родительским для всех процессов, считывает файл /etc/inittab и создает процессы на основе его содержимого. Обычно он запускает gettys, позволяя пользователям входить в систему. Он также определяет "уровни выполнения".

"Уровень выполнения" - это программная конфигурация системы, которая позволяет существовать только выбранной группе процессов.&#x20;

* Уровень запуска 0 (зарезервирован)  используется для остановки системы. уровень запуска 1 (зарезервирован) &#x20;
* Уровень запуска 1 используется для перевода системы в однопользовательский режим.&#x20;
* Уровни запуска 2,3,4 и 5 являются многопользовательскими.&#x20;
* Уровень запуска 6 используется для перезагрузки системы.&#x20;
* Уровни запуска 7, 8 и 9 можно использовать по своему усмотрению. Большинство версий Unix(/Linux) не используют эти уровни запуска. В обычном Debian Например, в системе Linux каталоги /etc/rc<уровень выполнения>.d, которые мы обсудим позже, недоступны для этих уровней выполнения, хотя это было бы совершенно законно.&#x20;
* Уровни запуска s и S являются внутренне одинаковыми. Это переводит систему runlevel s в "однопользовательский режим". Скрипты в каталоге / etc/rcS.d выполняются при загрузке системы. Хотя уровень запуска S не предназначен для активации пользователем, он может быть активирован.&#x20;
* Уровни запуска A, B и C являются так называемыми уровнями запуска "по требованию". Например, если текущий уровень выполнения равен "2" и выполняется команда init A , выполняются сценарии для запуска или остановки процессов на уровне выполнения "A", но фактический уровень выполнения остается "2".

### 12.1.8 Настройка /etc/inittab

Как упоминалось ранее, init считывает файл /etc/inittab, чтобы определить, что он должен делать. Запись в этом файле имеет следующий формат:

```bash
id:runlevels:action:process
```

Ниже приведен пример файла /etc/inittab.

```bash
# The default runlevel.
id:2:initdefault:
# Boot-time system configuration/initialization script.
# This is run first except when booting in emergency (-b) mode.
si::sysinit:/etc/init.d/rcS
# What to do in single-user mode.
~~:S:wait:/sbin/sulogin
# /etc/init.d executes the S and K scripts upon change
# of runlevel.
#
# Runlevel 0 is halt.
# Runlevel 1 is single-user.
# Runlevels 2-5 are multi-user.
# Runlevel 6 is reboot.
l0:0:wait:/etc/init.d/rc 0
l1:1:wait:/etc/init.d/rc 1
l2:2:wait:/etc/init.d/rc 2
l3:3:wait:/etc/init.d/rc 3
l4:4:wait:/etc/init.d/rc 4
l5:5:wait:/etc/init.d/rc 5
l6:6:wait:/etc/init.d/rc 6
# Normally not reached, but fall through in case of emergency.
z6:6:respawn:/sbin/sulogin
# /sbin/getty invocations for the runlevels.
#
# The "id" field MUST be the same as the last
# characters of the device (after "tty").
#
# Format:
# <id>:<runlevels>:<action>:<process>
1:2345:respawn:/sbin/getty 38400 tty1
2:23:respawn:/sbin/getty 38400 tty2
```

* id

Поле id однозначно идентифицирует запись в файле /etc/inittab и может содержать 1-4 символа. Однако для gettys и других процессов входа в систему поле id должно содержать суффикс соответствующего идентификационного номера, в противном случае учет входа в систему может не сработать.

* Уровни выполнения&#x20;

Это поле содержит уровни выполнения, для которых должно быть выполнено указанное действие.

* Действие
* respawn

Процесс будет перезапущен всякий раз, когда он завершится, возродится (например, getty).&#x20;

* wait

Процесс будет запущен один раз, когда будет вызван указанный уровень выполнения ожидания, и init будет ожидать его завершения.

* once

Процесс будет выполнен один раз, когда будет вызван указанный  уровень выполнения.

* boot

Процесс будет запущен во время загрузки системы. Поле boot runlevels игнорируется

* bootwait

Процесс будет запущен во время загрузки системы, в то время как bootwait init ожидает его завершения (например, /etc/rc) . Поле runlevels игнорируется.

* off

Ничего не делать

* ondemand

Процесс, помеченный уровнем выполнения по требованию, будет выполняться по требованию при каждом вызове указанного уровня выполнения по требованию. Однако изменения уровня выполнения не произойдет (уровнями выполнения по требованию являются "a", "b" и "c").

* initdefault

В поле initdefault указывается уровень выполнения, который должен быть введен после загрузки системы. Если его не существует, init запросит уровень выполнения на консоли. Поле process игнорируется. В приведенном выше примере после загрузки система перейдет на уровень выполнения 2.

* sysinit

Процесс будет запущен во время загрузки системы. Он будет запущен автоматически перед выполнением любых операций boot или bootwait. Поле runlevels игнорируется.

* powerwait

Процесс будет запущен при отключении питания. Функция ожидания включения обычно информируется об этом процессом, связывающимся с ИБП, подключенным к компьютеру. ИБП в этой функции ожидает завершения процесса, прежде чем продолжить.

* powerfail

Так же как и powerwait за исключением того, что init не выполняет powerfail, не дожидаясь завершения процесса

* powerokwait

Этот процесс будет выполнен сразу после инициализации

powerokwait получает сообщение о том, что подача электроэнергии восстановлена

* powerfailnow

Этот процесс будет выполнен, когда в программе init powerfailnow появится сообщение о том, что батарея внешнего ИБП почти разряжена и питание отключено (при условии, что внешний ИБП и процесс мониторинга способны обнаружить это состояние).

* ctrlaltdel

Процесс будет запущен, когда init ctrlaltdel получит сигнал SIGINT. Это означает, что кто-то в системной консоли нажал комбинацию клавиш CTRL-ALT-DEL и CTRL-ALT-DELETE. Обычно требуется выполнить какое-либо завершение работы, либо для перехода на однопользовательский уровень, либо для перезагрузки компьютера.

* kbdrequest

Процесс будет запущен, когда init получит сигнал от обработчика клавиатуры о том, что на клавиатуре консоли была нажата специальная комбинация клавиш kbdrequest. По сути, вы хотите сопоставить некоторую комбинацию клавиш с действием "Сигнал клавиатуры". Например, чтобы сопоставить Alt-Uparrow для этой цели, используйте следующее в вашем файле keymaps: `alt keycode 103 = KeyboardSignal` .

* process

Это поле определяет процесс, который должен быть выполнен. Если поле process начинается с "+", в нем не будет выполняться учет по протоколам utmp и wtmp .&#x20;

### Сценарий /etc/init.d/rc

Для каждого из уровней выполнения 0-6 в /etc/inittab есть запись, которая выполняет /etc/init.d/rc ? где "?" равно 0-6, как вы можете видеть в следующей строке из /etc/init.d/rc в предыдущем примере выше:

```bash
l2:2:wait:/etc/init.d/rc 2
```

Итак, на самом деле происходит то, что файл /etc/init.d/rc вызывается с параметром runlevel в качестве параметра.

Каталог /etc содержит несколько каталогов, специфичных для уровня выполнения, которые, в свою очередь, содержат символические ссылки на скрипты, специфичные для уровня выполнения, в /etc/init.d/ . Эти каталоги являются:

```bash
 $ ls -d /etc/rc*
 /etc/rc.boot /etc/rc1.d /etc/rc3.d /etc/rc5.d /etc/rcS.d
 /etc/rc0.d /etc/rc2.d /etc/rc4.d /etc/rc6.d
```

Как вы можете видеть, там также есть каталог /etc/rc.boot. Этот каталог устарел и был заменен каталогом /etc/rcN.d /etc/rcS.d . Во время загрузки сначала сканируется каталог /etc/rcS.d, а затем, на предмет обратной совместимости, каталог /etc/rc.boot.

Название символьной ссылки начинается либо с "S", либо с "K". Давайте рассмотрим каталог /etc/rc2.d:

```bash
$ ls /etc/rc2.d
 K20gpm      S11pcmcia  S20logoutd S20ssh     S89cron
 S10ipchains S12kerneld S20lpd     S20xfs     S91apache
 S10sysklogd S14ppp     S20makedev S22ntpdate S99gdm
 S11klogd    S20inetd   S20mysql   S89atd     S99rmnologin
```



Если имя символьной ссылки начинается с "K", скрипт вызывается с "stop" в качестве параметра для остановки процесса. Это относится к K20gpm , поэтому команда становится K20gpm stop . Давайте выясним, как называется программа или скрипт:

```bash
$ ls -l /etc/rc2.d/K20gpm
lrwxrwxrwx 1 root root 13 Mar 23 2001 /etc/rc2.d/K20gpm -> ../init.d/gpm
```

Итак, остановка K20gpm приводит к остановке /etc/init.d/gpm . Давайте посмотрим, что происходит с параметром "stop", изучив часть скрипта: init script

```
#!/bin/sh
#
# Start Mouse event server
...
case "$1" in
start)
    gpm_start
    ;;
stop)
    gpm_stop
    ;;
force-reload|restart)
    gpm_stop
    sleep 3
    gpm_start
    ;;
*)
    echo "Usage: /etc/init.d/gpm {start|stop|restart|force-reload}"
    exit 1
esac
```

В case..esac проверяется первый параметр, $1, и в случае, если его значение равно "stop", выполняется gpm\_stop.

С другой стороны, если имя символьной ссылки начинается с буквы "S", скрипт вызывается с "start" в качестве параметра для запуска процесса.

Скрипты выполняются в порядке лексической сортировки имен файлов.

Допустим, у нас есть демон, некоторый Daemon, сопровождающий скрипт /etc/init.d/SD, и мы хотим, чтобы какой-нибудь демон запускался , когда система находится на уровне запуска 2, но не тогда, когда система находится на уровне запуска 3.

Как вы уже знаете, это означает, что нам нужна символическая ссылка, начинающаяся с "S", для уровня выполнения 2 и символическая ссылка, начинающаяся с "K", для уровня выполнения 3. Мы также определили, что демон Some Daemon должен быть запущен после S19 каким-то другим демоном, который подразумевает S20 и K80, поскольку запуск/остановка симметричны, то есть то, что запускается первым, останавливается последним. Это достигается с помощью следующего набора команд:

```
# cd /etc/rc2.d
# ln -s ../init.d/SDscript S20SomeDaemon
# cd /etc/rc3.d
# ln -s ../init.d/SDscript K80SomeDaemon
```

Если вы хотите вручную запустить, перезапустить или остановить процесс, рекомендуется использовать соответствующий скрипт в /etc/init.d/, например /etc/init.d/gpm restart, чтобы инициировать перезапуск процесса

### 12.1.9 update-rc.d

{% hint style="info" %}
Обратите внимание, что этот раздел применим только к дистрибутивам на базе Debian
{% endhint %}

В дистрибутивах Linux, производных от Debian, используется команда update-rc.d для установки и удаления ссылок на скрипты инициализации, упомянутых в предыдущем разделе.

Если у вас есть сценарий запуска под названием "foobar" в /etc/init.d/ и вы хотите добавить его к уровням запуска по умолчанию, вы можете использовать:

```
# update-rc.d foobar defaults
Adding system startup for /etc/init.d/foobar ...
/etc/rc0.d/K20foobar -> ../init.d/foobar
/etc/rc1.d/K20foobar -> ../init.d/foobar
/etc/rc6.d/K20foobar -> ../init.d/foobar
/etc/rc2.d/S20foobar -> ../init.d/foobar
/etc/rc3.d/S20foobar -> ../init.d/foobar
/etc/rc4.d/S20foobar -> ../init.d/foobar
/etc/rc5.d/S20foobar -> ../init.d/foobar
```

update-rc.d создаст K (стоповые) ссылки в rc0.d, rc1.d и rc6.d и S (стартовые) ссылки в rc2.d, rc3.d, rc4.d и rc5.d.

Если вы не хотите, чтобы установленный пакет запускался автоматически, используйте update-rc.d, чтобы удалить ссылки на загрузку, например, чтобы отключить запуск dovecot при загрузке:

```bash
# update-rc.d -f dovecot remove
Removing any system startup links for /etc/init.d/dovecot ...
/etc/rc2.d/S24dovecot
/etc/rc3.d/S24dovecot
/etc/rc4.d/S24dovecot
/etc/rc5.d/S24dovecot
```

Параметр -f (принудительно) необходим, если rc-скрипт все еще существует. Если вы установите обновленный пакет dovecot, ссылки будут восстановлены. Чтобы предотвратить это, создайте ссылки "stop" в каталогах уровня запуска.:

```bash
# update-rc.d -f dovecot stop 24 2 3 4 5 .
Adding system startup for /etc/init.d/dovecot ...
/etc/rc2.d/K24dovecot -> ../init.d/dovecot
/etc/rc3.d/K24dovecot -> ../init.d/dovecot
/etc/rc4.d/K24dovecot -> ../init.d/dovecot
/etc/rc5.d/K24dovecot -> ../init.d/dovecot
```

{% hint style="info" %}
Обратите внимание, не забудьте о точке в конце.
{% endhint %}
